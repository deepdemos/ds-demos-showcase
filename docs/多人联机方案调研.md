# 多人联机方案调研（让上传的 demo 支持联机）

> 作用域：`web/` 仓库。**本文只做调研与方案比选，不含实现**。
> 配套引用清单：[`docs/参考-联机基建外部事实调研.md`](./参考-联机基建外部事实调研.md)（外部生态、价格、法规的逐条来源）。

## 0. 结论速览

| 档 | 机制 | 基建成本 | 连通率（实测/文献） | 适合的场景 | 本站适配度 |
|---|---|---|---|---|---|
| **A 服务器中继** | 你的后端 WebSocket 房间（wss 经 CF） | 低（回合制几 KB/s） | **100%** | 棋牌、回合制、协作编辑、异步对战、聊天 | ★★★★★ 建议先做 |
| **B P2P（你的想法）** | 你服务器只做信令，`RTCPeerConnection` DataChannel 直连 | 中（STUN 免费 + **TURN 必需**） | 直连 ~80%；**不打 TURN 会稳定损失 ~1/5** | 60fps 实时、语音、大文件 | ★★★★☆ 第二步 |
| **C 虚拟局域网** | WireGuard/headscale，玩家装客户端 | 高（内核 TUN + 各端安装 + 证书） | 100%（但要装软件） | **非网页** demo（Unity 原生/Python/需 UDP 广播） | ★☆☆☆☆ 仅在有此类作品时 |
| **A0 本地同机** | `BroadcastChannel` 同机多标签 | 零 | 100%（**仅预览子域拓扑**） | 调试、单机演示"多人界面"、**CI 联机 E2E** | ★★★★☆ 顺手做，测试价值大 |

**三条最重要的结论**：

1. **P2P 的瓶颈不在浏览器沙箱，在 NAT。** 本轮实测证明：**七种 iframe 沙箱组合里 `RTCPeerConnection` + DataChannel 全部可用**（含最严的 `sandbox="allow-scripts"` 不透明源）——所以 P2P 不需要动现有沙箱策略；真正的门槛是 ~17.7% 的成功连接必须走 TURN 中继（appear.in 千万级通话统计），**没 TURN 就没有 P2P**。
2. **中继档是唯一 100% 可达且不暴露玩家 IP 的方案**，而且它今天就能落地：站上**还没有任何 WebSocket**（全仓 0 处），但 CF 前置**实测放行 WS 升级**，只需给 nginx 的 `/api/` 补 `Upgrade/Connection` 头 + 后端加一个 WS 路由。后端 `--workers 1`（`backend/Dockerfile:21`）意味着**房间状态可以放进程内存，不需要 Redis**。
3. **联机能力对本站的真正价值是"零后端作者"**：现在 demo 作者要联机就得自己租服务器；站点提供「建房 / 房间号 / 邀请链接 / 信令 / 中继」后，作者只管游戏逻辑。这也是 itch.io / Newgrounds **完全不提供**、Poki **提供且免费托管信令+TURN** 的那个分界线。

## 2. 浏览器沙箱实测矩阵（本轮新增，7 组合 × 每项真跑）

复现：`node .tmp-cdp-profile/net-spike/spike.mjs`（单进程起两个源模拟主站 + 预览子域，父页当信令服务器，逐组合真建 DataChannel 并收发消息）。
原始数据：`.tmp-cdp-profile/net-spike/events.json`。

| # | 沙箱 / `allow` | 文档源 | localStorage | RTC 建连 | **DataChannel 双向** | WS 的 `Origin` 头 | 麦克风 | 跨标签 BroadcastChannel |
|---|---|---|---|---|---|---|---|---|
| 1 | 无 sandbox（同源） | `http://…:5399` | ok | ok | ✅ | `http://…:5399` | ✅ | ✅ |
| 2 | `allow-scripts` **不透明源**（= 当前生产默认） | **`null`** | ❌SecurityError | ok | ✅ | **`null`** | ❌SecurityError | ❌ 完全孤立 |
| 3 | 同 2 + `allow="camera;microphone"` | `null` | ❌ | ok | ✅ | `null` | ❌ **仍未解锁** | ❌ |
| 4 | 同源 + `allow-same-origin` | `http://…:5399` | ok | ok | ✅ | `http://…:5399` | ✅ | ✅ |
| 5 | **跨源 + `allow-same-origin`（= `demo.deepdemos.top` 生产拓扑）** | `http://…:5398` | ok | ok | ✅ | `http://…:5398` | ✅ | ✅ **跨标签可达** |
| 6 | 同 5 但 `allow="fullscreen"` | `http://…:5398` | ok | ok | ✅ | `http://…:5398` | ❌**NotAllowedError** | ✅ |
| 7 | 跨源无沙箱 | `http://…:5398` | ok | ok | ✅ | `http://…:5398` | ✅ | ✅ |

**从矩阵读出的五条硬结论**：

1. **P2P 数据联机不需要改沙箱**：`RTCPeerConnection` 与 DataChannel 不受 Permissions Policy 管辖，不透明源里照样通（第 2 行）。这否掉了"必须先放宽沙箱才能联机"的担心。
2. **父页代管信令可行**：父页通过 `postMessage` 中继 SDP/ICE、子页只当 answerer，在**全部七种组合**里握手成功（`ice=connected`）。即"站点持有网络身份，demo 只拿句柄"的桥接设计在技术上成立——这是安全上最讨巧的形态。
3. **语音/摄像头必须走预览子域**：不透明源里 `getUserMedia` 抛 `SecurityError`，**加 `allow` 属性也救不回来**（第 3 行）；跨源模式下还**额外**需要父页 `allow="camera; microphone"`（第 6 行 `NotAllowedError` → 第 5 行 ✅）。
4. **信令鉴权不能只靠 `Origin` 白名单**：不透明源的 WS/fetch 一律 `Origin: null`（第 2、3 行），而跨源模式给的是真实预览源（第 5、6、7 行）。⇒ 必须用 ticket/短时凭证做真实鉴权，`Origin` 只能作为跨源模式下的附加校验。
5. **同机多标签"本地局域网"只在预览子域拓扑下可用**：不透明源与任何上下文都不通（第 2 行 `bcFrom=[]`）；真实源（同源或预览子域）可跨标签页互相发现（第 5 行收到了另一个标签页 `tabB-5298` 与同页另两个 iframe）。与外部文档「BroadcastChannel 限定同源 + 同 storage partition」一致。

**中继档（路径 A）的浏览器侧无障碍**：七种组合的 WebSocket 全部 `open`，且客户端发的文本帧被服务端逐条解出（`op=1` + 原文，8/8 条，含 `Origin: null` 的源）。⇒ 中继档**没有任何浏览器侧前置改造**。

**线上 WebSocket 链路实测**（只读，一次握手）：`wss://deepdemos.top/api/v1/__ws_upgrade_probe__` → **HTTP 404 且 `cf-mitigated=-`**，即升级请求被 CF 转发到源站、由源站应答 404 ⇒ **Cloudflare 不拦 WebSocket 升级**。复现：`node .tmp-cdp-profile/net-spike/ws-status-probe.mjs`（原 `ws-status.txt`）。
⚠️ 但 CF 对 WS **空闲超时未公布秒数**（社区一致口径 ~100s，自定义仅 Enterprise）⇒ 上线必须带 ping/pong 心跳。

## 3. 三条路径逐一拆解

### 路径 A：服务器中继房间（建议先做）

- **机制**：后端 `WS /api/v1/rooms/{code}/ws`。房间在进程内存（`{code: {peers, meta, lastSeen}}`），消息按 `broadcast` / `to(peerId)` 转发；房间有 TTL 与人数上限，空闲自动回收。前端大厅：创建房间 → 短码 + 邀请链接 `?room=XXXX` → 房内玩家列表。
- **实现要点**：
  - nginx `/api/` 补 `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection $connection_upgrade; proxy_read_timeout 3600s;`（配 `map $http_upgrade $connection_upgrade`）。
  - 鉴权：`POST /api/v1/rooms` 建房需登录；加入凭 **ticket**（HMAC 短时签名，含 `room`、`exp`、可选 `uid`、`demo_slug`），因为预览源没有 Cookie（§1）。
  - 防护：单 IP 连接数、单房间人数（建议 8–16）、消息大小上限（如 16KB）、每秒消息数上限、房间 TTL（如 30 分钟无活动回收）、`code` 用足够熵避免爆破（6 位 base32 约 10 亿，配合加入限流即可）。
- **成本**：回合制/小状态几 KB/s；就算 100 个房间同时在线也是可忽略量级。**不花额外钱，不需要新服务。**
- **优点**：100% 连通（无 NAT 问题）、玩家 IP 互相不可见、可留日志可审核、可在同一连接上做"服务器权威"逻辑（反作弊、状态校验）。
- **缺点**：带宽走你的机器（高频状态或语音就贵）；房间态在单进程内存（重启即清、worker 数不能加）。
- **适配度**：★★★★★。它同时把「大厅 UI / 房间号 / 邀请链接 / 鉴权 / 限流」这套**与传输无关**的产品面全部做完，P2P 阶段只需换传输层。

### 路径 B：服务器信令 + WebRTC P2P（你的原方案）

- **机制**：wss 只用于交换 SDP/ICE + 房间成员；媒体/数据走 `RTCPeerConnection`（DTLS 加密）。拓扑建议**房主中继星型**（房主权威并转发），每人只维持 1 条连接，8 人量级够用；≤4 人可用全网状。
- **实现要点**：
  - **必须配 TURN**：`iceServers` = STUN(免费公共) + TURN(自建 coturn 或托管)。没有 TURN ⇒ 稳定损失约 1/5 的连接（§4）。
  - 自建 coturn：`use-auth-secret`（TURN REST 短时凭证，由后端 `/api/v1/rooms/{code}/ice` 下发）+ 配额（`user-quota`/`total-quota`/`max-bps`）+ `denied-peer-ip` 白名单外全拒；**配额默认是 0 = 无限制**，不配就是给全网当免费代理。
  - **网络拓扑硬约束**：CF 橙云**只代理 HTTP/HTTPS 端口，不转发任意 UDP** ⇒ coturn 的 `3478/udp` 与 `49152-65535/udp` 过不去，**必须加一条灰云（DNS only）记录**（如 `turn.deepdemos.top`）并暴露源站 IP；或用 `turn:…:443?transport=tcp` 走 TLS 变体（能过橙云，但牺牲 UDP 的延迟与效率）。
  - DataChannel 细节：可靠有序是默认；高频状态显式开 `{ordered:false, maxRetransmits:0}`；单条消息**按 16 KiB 分片**（社区实证：Chromium 超 256 KiB 直接因 EMSGSIZE 关通道）；用 `bufferedAmountLowThreshold` 做背压（默认 0，规范无推荐值）。`maxMessageSize` 在 `pc.sctp`（SDP 缺省按 64 KB 处理）。
- **优点**：延迟最低、不花你的带宽、天然加密、大量玩家时你的成本不变。
- **缺点**：**~1/5 的人必须经 TURN**（成本与源站 IP 暴露）；**玩家 IP 对彼此可见**（WebRTC 本质，藏不住）；内容端到端加密，**你审不了也留不了证**；调试链路长（ICE 失败排查）。
- **适配度**：★★★★☆。建议在 A 落地、大厅与鉴权稳定后再加，作为**同一套 API 的传输升级**，作者代码不变。

### 路径 C：真·虚拟局域网（WireGuard/headscale）

- **机制**：headscale（开源自托管控制面）+ WireGuard，玩家装客户端后彼此像同局域网。浏览器里**没有 TUN 设备**，所以网页 demo 用不上。
- **只有当出现"非网页作品"时才值得**（Unity/Godot 原生包、Python 脚本联机、需要 UDP 广播发现的服务端）。
- **成本**：内核模块/TUN、UDP 端口、每端安装与排障、证书/密钥轮转、玩家"装软件"的转化损失。
- **适配度**：★☆☆☆☆。**与本站"打开网页就能玩"的形态冲突**，除非明确要托管原生多人程序。

## 4. 外部生态与成本（引用清单见配套文档）

**TURN 是 P2P 的入场券（数字）**
- appear.in（千万级通话）：**已连通通话中 17.7% 最终走 TURN 中继**（TURN/UDP 12.1%、TURN/TCP 5%、TURN/TLS 0.5%）。
- TokBox/OpenTok（10 万通话）：ICE 失败 2.0%、真正连接失败 0.2%（多数失败源于企业代理拿不到 TURN 候选）。
- 网络侧根因：CGNAT 覆盖 **17–18% 的家庭宽带 AS**，蜂窝网络 AS **>90% 部署 CGN**。
- ⇒ **只做直连会稳定损失约五分之一的用户**，且这些人往往在企业网/移动网络里。

**橙云（Cloudflare）的边界**
- WebSocket：**所有套餐支持**（本站实测放行，见 §2）；空闲超时官方未公布（社区口径 ~100s）⇒ 心跳必需。
- **UDP 不代理**：橙云只覆盖 HTTP/HTTPS 端口；非 HTTP 服务官方建议改灰云；全端口 UDP 代理属 Spectrum/Enterprise。⇒ **coturn 必须灰云**。

**托管替代（不想暴露源站 IP 时的选项）**

| 服务 | 免费额度 | 付费 | 备注 |
|---|---|---|---|
| Cloudflare Realtime TURN | 与 SFU 共享 1000 GB | $0.05/GB（与 SFU 同用则免费） | 支持 `3478/udp`、`5349/tcp`、`443/tcp` + TURN REST；**不含 Cloudflare 中国网络**；不需企业计划 |
| Metered TURN | 500 MB/月 | $99/150GB 起，超量 $0.40/GB | — |
| LiveKit Cloud | 5,000 分钟 / 100 并发 / 50 GB | $50/月起 | 偏 SFU（语音/视频） |
| coturn 自建 | — | 只花流量 + 运维 | 单机可数千会话；**必须做凭证与配额** |
| 国内可用的托管 TURN/SFU | **未找到官方定价页** | — | 需自行接洽 |

**8 人房 1 小时的量级**：语音（Opus 32 kbps/人/向）≈ **0.92 GB/小时**（全走 TURN 同值）→ CF ≈ $0.046，Metered 超量 ≈ $0.37。
⇒ **语音不是带宽问题，是审核与国家/地区可用性问题**。

**平台先例（同类站点怎么做）**
- **itch.io / Newgrounds：完全不提供联机设施**（无信令、无中继）。
- **Poki：唯一官方支持 P2P** —— Netlib 用 DataChannel，**免费托管信令 + Cloudflare TURN**，直连失败自动回落中继；但 **CSP 默认封禁一切外部请求**、**聊天一律禁止**（建议用 emoji）。
- **CrazyGames：SDK 不含传输层**，只给房间/邀请元数据（"房间可视为玩家直连"），**有 chat 必须上审核**，平台可一键 `disableChat`。
- **Steam：SDR 中继网络**（认证/信令/中继一体）。
⇒ 行业共识是：**传输可以 P2P，但"可说话的内容"必须可控或直接禁掉。**

## 5. 安全与滥用边界（必须先定，再动手）

1. **TURN 绝不能是开放中继**：coturn 的 `user-quota` / `total-quota` / `max-bps` **默认全为 0 = 无限制**；真实案例有 Slack TURN 被滥用（$3,500 赏金），TURN 还能被用作约 **4× 放大的反射攻击**。必做：`use-auth-secret` + 短时凭证 + `denied-peer-ip`（含 `::ffff:` 段）+ 配额 + `unauthorized-ratelimit` + 最新版本。
2. **鉴权靠 ticket，不靠 `Origin`**：不透明源一律 `Origin: null`（实测），跨源模式才有真实源。ticket 要短时、限房间、限 demo。
3. **预览源是共享的**：所有 demo 同在 `demo.deepdemos.top` ⇒ 任一 demo 能读同源其他 demo 的 localStorage。联机 demo（尤其涉及房间凭证/身份）建议走 `{slug}.demo.deepdemos.top` 通配子域 + 通配证书。
4. **不可审核的内容是政策决定，不是技术决定**：P2P 是端到端加密的，你看不到内容也留不了证；中继档能留日志。建议：**数据联机默认开，文字/语音聊天默认关**（与 Poki 禁聊、CrazyGames 强制审核一致），需要时走中继档以便可审核。
5. **合规（待确认，需专业咨询）**：境内提供"端到端双向实时话音/视频/信息即时交互"在《电信业务分类目录》里对应 **B25 信息服务业务**口径，中继转发第三方流量是否单独构成增值电信业务**官方未明确**；含 UGC + 用户间通信的站点等保定级**待确认**。⇒ 上语音/大规模中继前先做备案/等保/内容安全三项咨询。

## 6. 推荐落地路线（分阶段，每阶段可独立验收）

| 阶段 | 范围 | 关键改动点 | 验收（可实测） |
|---|---|---|---|

**给作者的最小 API（草案，作者只写这些）**：
```js
const net = DSNet.join()                 // 从 URL 的 ?room= 自动取房间与 ticket；无房间则为单机
net.on('peer-join', p => …)              // 成员变化
net.on('message', (from, data) => …)     // 收到消息（ArrayBuffer/JSON 透明）
net.send(data)                           // 广播
net.sendTo(peerId, data)                 // 定向
net.isHost                              // 是否房主（星型拓扑下由站点决定）
net.leave()
```
传输（中继/P2P）由站点按 demo 声明与网络状况决定，**作者无感**。

**建议同步加的门禁**（沿用现有 `frontend/tests/designSystem.test.ts` 风格）：
- `IframePreview.vue` 若声明支持语音，`allow` 必须含 `camera; microphone`（当前**实测是坏的**，正好用一条断言钉死）。
- 房间服务单测：TTL 回收、人数上限、消息大小/频率上限、ticket 过期与错房间拒绝。
- 联机 E2E：用同机 `BroadcastChannel` / loopback DataChannel 在 CI 跑通"两端互发"，零外网依赖。

## 7. 待拍板的决策点

1. **先中继还是一步到 P2P**（我建议先中继，理由是它把所有与传输无关的产品面先做完，且 100% 可达）。
2. **开放范围**：白名单作者 / 全部已上架 demo / 先只给你自己的 demo（决定要不要同时做审核与被举报流程）。
3. **语音与聊天**：要不要（决定 TURN 带宽预算、审核成本、合规咨询前置）。数据联机没有这些负担。
4. **TURN 归属**：自建 coturn（暴露源站 IP、只花流量）还是托管（CF Realtime TURN $0.05/GB，但**不含中国网络**）。
5. **预览源是否拆通配子域**（联机 demo 的身份隔离；一次性成本，长期收益）。
