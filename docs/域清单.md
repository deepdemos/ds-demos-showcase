# 域清单

> **本文件回答三个问题**：这个项目一共有几个业务域；每个域的设计到哪一步了；离「能被实现」还差哪几份设计。
>
> **本文件是索引，不是事实源**：
> - **要做什么**以 [`项目需求.md`](项目需求.md) 为准（18 域 / 296 条）；
> - 表结构以 [`db/schema/*.sql`](../db/schema/) 为准；
> - 跨域共享取值以 [`标准对象.md`](标准对象.md) 为准。
>
> **本文件的 523 条是哪来的**：来自 [`全站业务需求`](ai-fullstack-eval/组织者资料/现站需求核对-20261021/修订前-v1.0-全站业务需求.md)（v1.0 快照）的 **523 条需求 ID**（31 个含 ID 的章节、42 个需求族），逐条归域，合计恰好 523 条，没有「其他」这一格。**它问的是「旧站的需求落在哪些域」，不是「我们要做什么」**——后者见 `项目需求.md`。
>
> **两套条数不能混用**：本文件的「需求章节 · 条数」是**老稿归域统计**（523 条，用来判断哪个域被需求压得最重）；总表新增的「新稿条数」是 **`项目需求.md` 里实际写了多少条**（296 条，用来判断哪个域写得最细）。两者不等是正常的：老稿 §29 的 13 条在本文件里算在设置域头上，而 `项目需求.md` 把 OPS 五条 + 用户偏好归成 SET 10 条，其余落在别的域。
>
> **用的是哪一版需求稿**：本文件统计的对象是仓库里唯一在库的 **v1.0 快照**（`修订前-v1.0-全站业务需求.md`）。现行 **v1.1 从未入库**（`git log --all --diff-filter=A -- "*DeepDemos-全站业务需求*"` 为空），`文档核对结果.json` 记录其为 **560 条 / 32 章 / 18 项待确认**。所以本文件的绝对条数（523）**小于**现行稿，但**域归属关系不受影响**——新增的 49 条全部落在既有族里，没有产生新族。等 v1.1 入库后按同样方法重算一遍即可。
>
> **状态怎么判的**：看设计文档里有没有独立文档、有没有表定义、有没有不变量。「未设计」必须有原文明说；没有原文的一律记为「未提及」——这两个词在本文件里是不同性质，不能混用。

### 3.4 一处两份事实源在打架

`db/schema/10-identity.sql` **有 `exp_events` 表**，而 `身份服务模型设计.md` 文件头写着「Q5：`exp_events` **整表删除**」。两个事实源在这张表上直接冲突。

按 `db/schema/README.md` 自己定的规则「文档与 SQL 冲突 → 以 SQL 为准，同时把文档那句话改掉」，二者只能留一个：

- **A**：把 `exp_events` 从 schema 删掉 —— Q5 生效，成长/积分域接管等级事实源，第 11 域存在；
- **B**：把「整表删除」那句撤回 —— 等级事实源留在身份域，第 11 域不必存在。

这条不定下来，第 11 域「成长 / 积分」到底存不存在就悬着，而那又决定了第 1 域 `accounts.level` 是不是一个永远指向空处的投影。

> 这是本文件里唯一一处「两份事实源互相矛盾」，其余地方都只是「有 / 没有」的差别。
>
> **2026-11-01 更新**：`项目需求.md` 把它登记成 **附录 C1（仍开放）**，没有替任何人拍板。所以第 11 域的存在性至今悬着。

这一句把上面整张表的性质改了：

| 前置能力 | 裁决后的现状 |
|---|---|
| 平台调用模型 | **不再需要**。平台只提供接入接口（凭据 key + OAuth 两种都要），用户本地 agent 调它自己的模型，轮询与长连接都支持，一个 agent 绑一个**用户的**模型，不要求平台收录。所以「推理网关 / 密钥托管 / 成本控制」这三件事**整个消失** |

**排序提醒（裁决后更新）**：原本说「对战是唯一一个会反过来改架构的域」，理由是推理网关与任务队列。**裁决后这个理由去掉了一半**——不用调模型就没有推理网关和成本控制。剩下的麻烦只有三件：对局状态机、超时回收、匿名投票防刷。这三件都是可以后补的，不再要求「排最前」。
