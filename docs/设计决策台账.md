## G1 · 公开可见谓词与 tombstone（2026-10-28）

**结论**

1. **列表 / 计数 / 榜单**（发现）只算：
   `moderation_state='approved' AND lifecycle_state='published' AND deleted_at IS NULL`
   `AND EXISTS (SELECT 1 FROM demo_channels c WHERE c.demo_id=d.id AND c.channel=:channel AND c.visibility='listed')`
2. **按 slug 直访**（定位）分档：
   - `published` + `approved` + 未删除 → 200，完整内容
   - `archived`（作者下架）→ **200 + tombstone**：slug / 标题 / 下架时间 /「作者已下架该作品」；可执行动作 = 查看作者其它作品、返回列表（作者本人另有「恢复发布」）
   - `removed`（违规下架）→ **200 + tombstone**：slug / 标题 / 处理时间 /「该作品因违规被移除」/ 依据条款；可执行动作 = **提交申诉**、查看社区规范
   - `pending` / `rejected` / `draft` / `deleted` → **404**；作者本人与管理员走**带权限读路径**，不套公开谓词
   - tombstone 页一律不出：内容、预览、下载、评分、评论/讨论入口、会话日志、时间线

**为什么**

- 「发现」与「定位」是两种语义：列表不该出现下架作品；但旧链接直接 404 会让分享链接与搜索结果变成死链，所以用 tombstone 承接。
- 渠道条件不是新概念：astra 已是独立视区（`deep` / `astra` 由请求 Host 判定），`DemoChannel` 有真实数据。
- 两类 tombstone 必须内容不同：`archived` 是作者自主行为（可恢复、无申诉），`removed` 是平台处置（有申诉、有条款）——合成一个页面会让用户既不知道能不能申诉，也不知道作品会不会回来。

**放弃的方案**：只看 `moderation_state`（会把 draft/archived/removed 列进列表）；不带渠道（astra 橱窗会串味）；用 404 / 410 替代 tombstone（死链）。

**影响面**：实体域 §5.0（谓词定义）与 §5.1–§5.3、§6.2；Demo 域 §6.2 / §6.4；标签域 §5.2–§5.5；模型域读路径；前端详情页与预览页。

**回退**：谓词是查询条件，无数据迁移；tombstone 是响应形态，可退回 404。

## G7 · 题归属只按当前 revision 判定（2026-10-28，原实体域 §11 D2）

**结论**：`demo_tasks` 视图 = `demos ⋈ demo_revisions(当前) ⋈ task_prompts`。改 prompt = 新 revision = 换题；**历史 revision 的题归属不提供**。

**为什么**：①「题归属」的产品语义是「这件作品**现在**能不能当这道题的样本」；②「所有 revision 都算」拿不到真历史——`task_prompts` 本身可变（合并/取消归类），UNION 出来的是「旧 prompt 现在归哪题」，是假历史，却要付计数虚高的代价；③ 真历史应由显式归属事实表承担，那是独立需求。

**放弃的方案**：B 所有 revision UNION（计数虚高 + 假历史）；C 归属事实表（本期不做，留作将来追溯需求）。

**影响面**：实体域 §1.3/§3.6/§4.4/§5/§6；Demo 域 `demo_tasks` 需标注为视图。

**回退**：视图定义可改；归属事实表将来可增量补。

## G8 · 带权限读路径（2026-10-28）

**结论**：作者本人与管理员读自己的 `draft` / `pending` / `rejected` 作品，走**带权限读路径**（校验作者身份或管理员角色），**不套公开可见谓词**；其他人拿这些作品的 slug 访问 → 404。

**为什么**：公开谓词是「陌生人能看到什么」的口径；作者需要在上传后、审核前预览自己的作品（现状线上事故也说明详情页对匿名访客要静默处理，不能弹登录）。两条路径分开，才不会为了作者预览而把未公开作品泄露给所有人。

**放弃的方案**：把 `pending` 也算进公开可见（等于未审先公开）；或让作者用另一套 URL（多一套路由与权限面）。

**影响面**：实体域 §5.0；Demo 域 §6.4；鉴权中间件与详情页/预览页路由。

**回退**：纯读路径开关。

## G9 · 提案 kind 扩展：半开放实体走提案（2026-10-28）

**结论**

1. 新增 4 个 kind：`new_classification`（payload `{dimension, slug, label}`）、**`new_platform`（`{slug, name, is_harness, forms[]}`——2026-10-28 按 G17 更新：平台已无 `kind`，必填子集含 `is_harness` 与非空 `forms`）**、`new_platform_config`（`{kind, slug, name, platform_slug?}`）、`new_skill`（`{slug, name}`）。
2. `new_tag_value` **保留在 CHECK 里但转为「仅存量兼容」**：新写入不再产生（标签域新模型下没有 tag 值可提）。
3. 「半开放」的准确含义：**用户不能内联创建**（打标时 422），但**可以提案**；管理员审核通过后才建行。`vendor` / `url` / `platform_id` 归属等字段由管理员在审核时补——这正是提案层存在的意义。
4. 存量 `tag_value_suggestions` **按旧 key 分流**：`type` / `category` → `new_classification`；`model` → `new_model` / `model_alias`；`plugin` / `preset` → `new_platform_config`；`skills` → `new_skill`；`platform` → `new_platform`（仅当线上该键 mode 为 `fixed`）。
5. **这张表里不可能出现的键（2026-10-28 读 `main` 源码核过，非推断）**：`game` / `platform`（open）、`rounds` / `time`（int）。依据：用户提交端点只收 `mode='fixed'`（`backend/app/routers/tags.py:181-182`）；另两条写入路径硬编码 `key='model'`（`tags.py:309` / `tags.py:507` / `scripts/sync_models_from_modelsdev.py:70`）；seed 里 `game`=open、`rounds`=int（`main.py:669-670`），`time`=int、`platform`=open 由管理员后加（`tests/test_run_meta_v2.py:21-28` 夹具写明）；表与校验由**同一 commit**（`f6e37e1`）引入——不存在「校验之前的老数据」。所以「`rounds`/`time` 的建议行」**不成立**，原先写的「丢弃」分支是多余的（已从实体域 §6.8 删掉）。
6. **迁移因此只需 4 个分支**（不是 6 个）：`type`/`category` → `new_classification`；`plugin`/`preset` → `new_platform_config`；`skills` → `new_skill`；`model` → `new_model`。`new_platform` kind 仍保留（新系统里用户可直接提交提案），但**没有迁移来源**。
7. **旧栈打标规则（供迁移参考）**：`fixed` 键必须已存在（否则 422）；`open` / `int` 键**自动建值**（`demos.py:161-184`）。所以旧栈里 `platform` 是**可内联创建**的，新模型改成不自动建——这是**有意变更**，不是旧行为。
6. **作品上的轮数/耗时不受影响**：`rounds` / `time` 在旧栈是标签 + 列双写（`sync_run_meta`），迁移走**列**路径（`demo_revisions.gen_rounds` / `gen_minutes`），194 / 111 件的数据一条不丢。**被讨论的「丢弃」从来只指「建议行」，不指作品数据。**

**为什么**：标签域把 4 组旧键升级成了 4 个实体（`classifications` / `platforms` / `platform_configs` / `skills`），它们的值来源都是「半开」——用户能提、管理员能审。若不建这些 kind，用户想加一个平台或插件就只能绕过提案（或者根本提不了）。

**放弃的方案**：只加 `new_classification`、其余丢弃（用户无法提出新平台/插件/技能）；让 `platform_configs` 自动建（会造出没有描述、没有厂商、没有讨论的空页面）。

**影响面**：实体域 §3.10（kind CHECK / payload CHECK / dedupe_key / 执行表）、§6.8（存量迁移映射）、§10.1（取数清单 **③ / ④ / ⑤**）；标签域 §4.3 / §4.7 / §9.6；模型域（`new_model` / `model_alias` 已有）。

**回退**：kind 是 CHECK 值，未落库前随时可增删；已落库的提案按 kind 保留。

## G10 · `vendors` 升级为跨域共享主数据；提案「接口给全 + 审核兜底」（2026-10-28）

**结论**

1. `vendors` 从「模型域的厂商表」升级为**跨域共享主数据**：模型域 `models.vendor_id` 与平台域 `platforms.vendor_id` 指向同一张表。标签域 `platforms` 的 `vendor text` 列**删除**。
2. 提案 payload **字段给全**（提交端提供完整表单：`slug` / `name` / `kind` / `vendor_id` / `url` / `description`），但 payload CHECK **只强制必填子集**（见实体域 §3.10 的字段表）。
3. **审核兜底**：审核界面必须能补可选字段；**缺运营必填字段（`platform_id`、`vendor_id` 等）时不允许批准**。
4. **厂商不由用户提**：用户在表单里**选择**已有厂商（下拉），不自由填字符串；缺哪个厂商由管理员先建。**不设 `new_vendor` kind**。

**为什么**

- 平台域原本用 `vendor text`，而模型域已经把厂商实体化，理由是「靠字符串比对必然出错」——同一个概念两个域两种存法，统计口径必然分裂（`Zcode = GLM 专武`、`qoder = 阿里`、`Codebuddy = 字节` 这些归属关系靠字符串存不住）。
- 「只带名字的提案」会落库一条空实体：详情页没有厂商、没有描述、没有讨论。标签域 §4.3 反对自动建的理由（「会造出空页面」）同样适用于**审核环节**，所以审核界面必须挡住。
- 厂商是运营数据、不是用户内容：让用户提厂商会引入大量重复与拼写变体，管理员建一次即可。

**放弃的方案**：保持 `vendor text`（口径分裂）；只带名字的提案（空实体）；用户自由填厂商名（重复与变体）；加 `new_vendor` kind（运营数据不该走用户提案）。

**影响面**：标签域 §3.5 / §4.3 / §5.3 / §8 / §9.3 / §9.6；实体域 §3.10（payload 字段表 + 审核兜底）；模型域 §3.4（标注共享）；前端表单需要一个厂商下拉（`GET /vendors`）。

**回退**：`vendor_id` 可空；退回自由文本只需加回一列并回填。

## G11 · revision 的「内容不可变、运行元数据可更正」（2026-10-28）

**结论**：`DemoRevision` 的**内容列**（`manifest_hash` / `file_count` / `total_bytes` / `entry_path` / `demo_type` / `single_file` / `external_url` / `title` / `description` / `cover_url` / `prompt` / `prompt_id`）不可变；**运行元数据列**（`gen_rounds` / `gen_minutes` / `gen_platform` / `model_hint`）**允许作者本人更正**，每次更正写 `audit_log`，不触发重新审核。

**为什么**：`gen_*` 是「这一次生成跑了多少轮 / 多久 / 用什么平台」的**录入记录**，不是内容本身。用户填错了：让它新建一个「内容完全相同的 revision」是错的（污染版本号语义），而只让管理员改库是漏设计（用户连自己填错的数字都改不了）。

**放弃的方案**：更正即新建 revision（版本语义被污染）；加提案 kind `fix_run_meta`（改自己的录入错误还要走提案，太重）；不设计、靠管理员改库（现状）。

**影响面**：Demo 域 §3.2（字段表标注）/ §6.3（状态机 note）/ 新增 §6.5；写契约需要一个「更正运行元数据」端点（`PATCH /demos/{slug}/revisions/{rev_no}/run-meta` 或并入编辑接口）。

**回退**：白名单收紧即可；audit_log 里的更正记录保留。

## G16 · 文档分层原则：正文只放目标态，过渡态下沉（2026-10-28）

**结论**：设计文档的**正文（§0–§9 的目标态章节）只放目标态**；凡「只在过渡期存在」或「只在旧栈成立」的东西，一律下沉到文末独立一节（正文最后一节，命名「**§N 过渡期与退役（非目标态）**」，位置在附录之前）。

**判定标准（四类，命中即下沉）**

| 类 | 例子 |
|---|---|

| ④ 一次性留痕物 | 归档表（`model_tag_archive`）· 迁移专用列（`_src_suggestion_id`）· 作废 kind（`report`） |

**留在正文的**：§1「为什么改」的**论证**（问题是什么、为什么必须改）——它是设计的理由，不是过渡态；但**旧结构的具体定义**要下沉。

**不允许改的**：目标态定义（表 / 列 / 约束 / 不变量）· 决策编号与理由 · 跨文档引用 · 迁移路线的顺序与前置条件。**只搬位置，不改内容，不删信息。**

**验收**：① 目标章节里搜不到四类关键词；② 文末新节逐条收纳，并给出「从哪搬到哪」；③ 围栏偶数、mermaid 语义不变（目标图里若画了过渡对象，从图中移除并在新节保留一张「过渡期图」）；④ 版本头 +1 并写明本版变更。

| D1 | **完整 RBAC**：`roles` / `permissions` / `role_permissions` + 账号挂角色（单角色，岗位语义）；permission 到「域.动作」粒度（**19 个**——v1.5 起「未设计域的权限不预先占位」，`announcement.write` / `setting.write` 已移除，`report.handle` 作为恢复内建举报的显式预留保留）；CI 拦「端点未声明 permission」 |
| D2 | 用户状态 **4 态**（`active` / `suspended` / `banned` / `deleted`），每个迁移都有端点；**单一入口** `POST /admin/users/{id}/status`；`deleted` **只能用户自删**；解封回 `previous_status` |
| D3 | 删除一律**软删**；派生物（目录 / OSS / blob）入 `gc_queue`，**30 天**后真删 |
| D4 | 审核**一表一语义、一套动作**：`proposals`（实体域）· `demos.moderation_state`（Demo 域）· 举报**作废**（论坛外置，实体域 §12.10）；统一入口 `POST /admin/reviews/{kind}/{id}` |
| D5 | 列分三类：内容列（**只能发新版本**）/ 展示列（管理员可改 + 审计）/ 治理列（管理员专属） |
| D6 | `audit_log` **治理域独占**；**`actor_role` 快照取代本条目原定的 `admin_override` 布尔**（角色会变，布尔会失真）；`action` / `entity_type` 用 **目录表 + FK**（`audit_actions` / `audit_entity_types`）——**2026-10-29 反转**：原定 DB 层 `CHECK`，因加枚举值要在最大表上取 `ACCESS EXCLUSIVE` 而改 |
| D7 | 写路径强制 service/store：`store.WithAudit(...)` / `store.WithAuditTx(...)` 包住写事务；**CI 拦裸 `tx.Commit()` 与裸 `INSERT INTO audit_log`** |
| D8 | 批量逐条独立提交 + 固定返回 `{batch_id, ok, failed, results[]}` + 上限 **200** |

**原「未定」项的结论**：① **admin 改内容列** → 只能走「重建 → 发新版本」，**G11 不加例外**；② **可覆盖表白名单** → 见文档 §10.1 的三类列；③ **二次确认** → 保留为**待定 Q12**（倾向服务端要求 `confirm: true`）。

**沿用未变的原方向**：可绕过 `proposals` 审核流与状态机；不可绕过唯一约束 / 外键 / `payload` CHECK。

**已定案**：**Q13**（2026-10-29）——`audit.read` 只给 `admin`，`moderator` 不读审计（`before` 快照可能含隐私字段）；**Q15**（2026-10-29，治理域 §5.2 已落 DDL）——`audit_log` 走 `PARTITION BY RANGE (created_at)` + `PRIMARY KEY (id, created_at)` + 默认分区兜底，到期「归档 → `DETACH` → `DROP TABLE`」。**实测修正**：默认分区存在时 PG 18 拒绝 `DETACH ... CONCURRENTLY`（空表也拒），故保留期不用并发摘除，改用毫秒级元数据锁的普通 `DETACH`。

**未收口**：文档 §14 的 Q9–Q12、Q14、Q16（单/多角色、旧审计是否迁、软删行是否真删、二次确认、封禁是否通知、身份域形态 C 的时机）。

**接入协议（v1.6 新增 §16）**：把「扩展性」写成可判定契约——**六项接入清单**（权限 / 审计动作 / 实体类型 / 端点声明 / 写路径 / 派生物回收）+ **四条机器可判定验收**（第一条即「新域 PR 的 diff 不含 `docs/治理域设计.md`」）+ **五条反向约束**（禁直写审计 / 权限表、禁角色布尔、禁自造审核状态机、禁悬空 `entity_id`）。

**§16 点名的两处缺口已在 v1.7 闭合**：`audit_entity_types` 加 `table_name`（`UNIQUE`，一表一类型）/ `route_template`（CHECK：以 `/` 开头且含 `{id}`）——后台审计页不再硬编码 if；`gc_queue.kind` 的 `CHECK` 三值改 `gc_kinds` 目录表 + FK（与 §8.3「加值不 ALTER」自洽）。连带：本域表数 7 → **8**，实体类型种子 14 → **13**（`tag` 删——G4 已定 `tags` / `tag_keys` 退役，无真表可指；`report` 是唯一两列留空的显式预留）。DDL 已在 PostgreSQL 18.6 上跑通 **18/18 断言**。

**跨域债**（需要身份域 B 组拍板时一并改）：① `accounts.role` 的 `CHECK` 改 `REFERENCES roles(key)`；② `accounts.status` 加 `banned`；③ `accounts` 加 `previous_status`。
