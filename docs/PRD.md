> **本文件管什么**：给谁做、第一版装什么、怎么算做成了。**不管**每一条需求的验收口径（在 [`项目需求.md`](项目需求.md)），也不管技术怎么实现（在 [`adr/`](adr/README.md) 与 [`标准对象.md`](标准对象.md)）。
> **版本**：v0.3（2026-11-21）。六处待拍板已于 2026-11-20 拍定；2026-11-21 定位票 #514 落定，见 §8。
> **读者**：人（决定做什么）与 agent（知道边界在哪）。

## 1. 一句话

**社区的作品库：把用 AI 做出来的东西放在一处，别人点开就能跑。**

作者投稿（网页 / 压缩包 / Godot / 图片 / 三维模型 / 外链），站方审核后挂到渠道上，访客浏览、筛选、收藏。

**已定（2026-11-20）**：「点开就能跑」是核心卖点，「可发现」是它的辅助。这决定了沙箱与预览隔离域属于第一版的前置条件（见 §3、§4）。

**已定（2026-11-21，定位票 #514）**：

- **「社区」指人，不指内容流**：作者与读者靠「投稿」这一条关系连起来；站内承载的是**作品**和它的**可发现性**（榜单、分类与模型筛选、作者页、收藏）。
- **野心（不进本版）**：作品、讨论与消息都在这里。**讨论仍在外置论坛**（[`项目需求.md`](项目需求.md) §14 已选型 Discourse + DiscourseConnect）；**聚合类栏目**（工具、友链、小道消息、资讯流）**不在本站下一版范围内 —— 入口页 / 导航页不建**，相关想法只登记在 [`未来展望.md`](未来展望.md)。
- 定位不改变 §3 的第一版范围（10 域 / 190 条），也不改 §4 的优先级；要动范围，走范围票（#519）。

## 2. 用户与核心场景

| 角色 | 他们来干什么 | 对应需求域 |
|---|---|---|
| **作者** | 把自己的作品传上来，看审核状态，改说明，知道「用的是哪个模型/哪一版」 | DEMO / ENT / IDN / MODEL |
| **访客** | 看别人的作品、按分类和模型筛、收藏、看浏览记录 | DEMO / TAG / MODEL / COL / HIST |
| **管理员** | 审作品、管分类词表、管站点参数、裁决提案与申诉 | GOV / LIFE / SET / CUR |

**主路径（一条就够）**：作者投稿 → 审核 → 挂上渠道 → 访客在列表里看到 → 点进去能跑 → 收藏。

**已定（2026-11-20）**：主路径只有这一条。按模型 / 按分类是这条路径上的**筛选条件**，不单列成第二条路径。

## 4. 优先级

按「主路径上离用户最近的一步」排，不按域大小排：

- **P0**：身份（能登录）→ Demo（能投稿、能看）→ 治理（能审）→ 生命周期（能删、墓碑）→ **沙箱与预览隔离（点开能跑）**。
- **P1**：分类与模型（能筛、能说明来源）→ 实体（提案与归属）→ 设置（运营开关）。
- **P2**：收藏 → 浏览历史 → 通知。
- **P3**：策展 → 公告 → 搜索。
- **不做**：见 [`项目需求.md` 附录 B](项目需求.md) 的 13 条。

**已定（2026-11-20）**：以本表为准。提交历史里收藏 / 通知 / 公告先于设置落地，属于**提前实现**，不改变优先级；后续资源回到 P0 与 P1。

## 5. 怎么算成功

**已定（2026-11-20）**：**任一作品详情页都能自解释。**

不点外链、不打开作品本身，页面就要回答四件事：

1. **这是什么** —— 形态（网页 / 压缩包 / Godot / 图片 / 三维模型 / 外链）与类型。
2. **谁做的** —— 作者，以及该账号状态是否正常（封禁作者的作品页该怎么显示）。
3. **用什么做的** —— 声明的模型与版本（这是模型域 + 「用的是哪一版」存在的全部理由）。
4. **现在能不能跑** —— 可达性：能跑 / 只有外链 / 已下架 / 墓碑。

**可验证的形式**：拿任意一个作品，把页面截图给没看过这个站的人，他能答出上面四件事。答不出就是没达标。

这条标准优先于「主路径可跑通」：主路径能跑只证明系统通了，页面能自解释才证明**内容有价值**。

## 9. 新特性从哪进

**本文件不收录新特性。** PRD 只回答「这版做什么、不做什么、怎么算成」，它长一点，就变成第 62 份读不完的文档——那正是这次翻新要治的病。

新特性走三档，一档一档往上：

| 档 | 落在哪 | 一条写什么 | 谁定 |
|---|---|---|---|
| ① 想法 | [`未来展望.md`](未来展望.md) | 是什么 / 为什么值得做 / 卡在哪 | 谁都能记，**记了不等于批准** |
| ② 规格 | GitHub issue（一个特性一个） | 问题 / 目标 / 非目标 / 验收 / 影响面 | 想清楚了才开 |
| ③ 进版本 | 本文件 §3 的范围表 + 一组 ticket | **只加一行指针**，细节在 issue | 产品负责人 |

对应的判据：

- 一个想法**还没想清楚怎么做** → ①，一行就够。
- **想清楚了、能写验收** → ②，开 issue，把号回填到 ①。
- **进了这一版** → ③，在 §3 加一行，并在 §4 排优先级。

**重构基线与新特性是两条线**：`项目需求.md` 的 296 条是「旧站有什么、新站要覆盖什么」的冻结基线；「旧站没有、这版也没有」的一律从 ① 起步，不往需求文档里追加。

**第一版是固定容量的**（10 个域 / 190 条）。要往第一版加一个新特性，必须在同一处写清**它换掉了什么**——换不掉，就说明它该留在 ① 或 ②，不该进 ③。
