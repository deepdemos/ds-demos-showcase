# 标准对象

这份文件只回答一件事：**一个跨域共享的取值，到底在哪里定义。**

起因是具体的。`账号状态` 曾经同时存在于四份文档里——身份域的 DDL、治理域的状态机图、生命周期文档的账号轴、论坛投影的说明——四份里有两份缺 `banned`、一份缺 `pending`、一份多出一条「管理员可删除用户」的边。没有任何一份是错的，它们只是都被写过一次，然后各自漂了。取值域这类东西不属于任何一个域：它是**共享的词汇**，写两遍就是两份事实源，而两份事实源迟早会有一份停在旧版本上。

所以规矩是：取值域、状态迁移、派生判定，**在本文定义一次**；域文档只写本域特有的东西——端点、权限、自保护、为什么这样设计——需要列举取值时引用本文的锚点。这样做的代价很小（多一次跳转），收益是**加一个值只需要改一处**，而且漏改会被门禁抓住。

登记判据只有一条：**两个及以上域必须读到同一个值域**才登记。只被一个域消费的枚举留在本域（`credentials.kind`、`blobs.backend` 这类），登记进来只会变成索引负担。引用写法统一为 `标准对象 §ST-1`；其他文档里出现某个对象的完整取值集合时，那一行（或上一行）必须带这个锚点，否则 `scripts/check-objects.mjs` 报错。编号按类分：`ST` 状态与档位、`EN` 值域、`ID` 标识符、`TS` 时间戳、`P` 派生判定。

文体上它是字典，不是导论：不写背景长文、不画图。图可以留在域文档里（那里讲得清流程），但**图与表冲突时以本文的表为准**。

## §ST-1 账号状态 `AccountStatus`

**它是账号轴上唯一的状态列。** `accounts.status` 是「能不能登录、能不能发言、是否已注销」的唯一表达，同一件事不允许再有第二列或第二张图。落列在身份域（`docs/身份服务模型设计.md` §6.1），迁移的规则由治理域参与制定（`docs/治理域设计.md` §7.1 讲端点与权限），本文只负责**取值与边本身**。

**五个取值，语义按「谁能做什么」定，不按情绪定。**

| 值 | 语义 | 能登录 | 能发言 |
|---|---|---|---|
| `pending` | 已注册、邮箱未验证（**默认值**） | 否 | 否 |
| `active` | 正常 | 是 | 是 |
| `suspended` | 暂停（可恢复，如临时禁言） | 否 | 否 |
| `banned` | 封禁（长期，走申诉） | 否 | 否 |
| `deleted` | 已注销（**终态**，不可恢复） | 否 | 否 |

三个「不能」是有区别的：`pending` 没验证邮箱、`suspended` 是有期限制、`banned` 是无期限制且要申诉、`deleted` 是本人自愿且不可逆。`suspended` 与 `banned` 之所以不合并成一个值，是因为它们对下游传播的语义不同（前者是「过段时间恢复」，后者是「需要申诉」），合并了就再没地方表达这个差别。

`previous_status` **不是状态，是恢复目标**：只在 `suspended` / `banned` 时有值（`suspended` ⇒ 必为 `active`；`banned` ⇒ `active` 或 `suspended`），其余状态必须为 `NULL`，进入 `deleted` 时清空。它存在的唯一理由是「解封回到原处」——没有它，`banned` 解除后就分不清该回 `active` 还是回 `suspended`。

**十一条边，包括入口和一条终态。** 表里「触发者」这一列是有意写得比角色细：`本人` / `持 user.status 者` / `系统任务` / `无`。

| # | 从 | 到 | 触发者 | 前置条件 |
|---|---|---|---|---|
| 1 | — | `pending` | 本人 | 注册成功 |
| 2 | `pending` | `active` | 本人 | 邮箱验证通过 |
| 3 | `pending` | `deleted` | 系统任务 | 注册满 30 天仍未验证 |
| 4 | `active` | `suspended` | 持 `user.status` 者 | `reason` 必填 |
| 5 | `active` | `banned` | 持 `user.status` 者 | `reason` 必填 |
| 6 | `active` | `deleted` | **本人** | 二次确认 `"DELETE"` |
| 7 | `suspended` | `active` | 持 `user.status` 者 | 回到 `previous_status` |
| 8 | `suspended` | `banned` | 持 `user.status` 者 | 升级；`previous_status` 归一到 `active` |
| 9 | `banned` | `active` | 持 `user.status` 者 | 回到 `previous_status` |
| 10 | `banned` | `suspended` | 持 `user.status` 者 | 降级；`previous_status` 归一为 `active` |
| 11 | `deleted` | — | 无 | **终态**，没有出边 |

**不存在的迁移，写了就是 bug**：`suspended → deleted`、`banned → deleted`、`deleted → 任何`、`pending → suspended`。管理员能做的上限是封禁；删账号是用户自己的权利（治理域 **D2**，也是旧栈 P12 事故的修正）。唯一由系统进入 `deleted` 的路径是 #3（注册后 30 天不验证邮箱）。

**三条不变量，是可执行的 SQL 片段**（身份域 §6.1 逐字引用，门禁比对值集）：

```sql
-- 取值域
CHECK (status IN ('pending', 'active', 'suspended', 'banned', 'deleted'))

-- previous_status 与 status 联立（注意 `IS NOT DISTINCT FROM`：NULL 时 `= 'active'` 求值为 NULL，
-- 而 CHECK 只在 FALSE 时拒绝，三值逻辑会把它放过去）
CHECK (
    CASE status
        WHEN 'active'    THEN previous_status IS NULL
        WHEN 'suspended' THEN previous_status IS NOT DISTINCT FROM 'active'
        WHEN 'banned'    THEN previous_status IS NOT NULL
                          AND previous_status IN ('active', 'suspended')
        ELSE previous_status IS NULL
    END
)

-- 注销时刻与终态同生共死（只有 #3 #6 两条边写 closed_at，两者都置 status='deleted'）
CHECK ((status = 'deleted') = (closed_at IS NOT NULL))
```

**谁能改，按边分组而不是按角色分组**——因为「同一个端点覆盖多条边」这件事本身就是容易漏的。

| 迁移组 | 谁 | 端点 |
|---|---|---|
| #2 | 本人 | `POST /me/verify-email` |
| #3 | 系统任务 | 无（定时） |
| #4 #5 #7 #8 #9 #10 | 持 `user.status` 者 | `POST /admin/users/{id}/status` |
| #6 | 本人 | `POST /me/delete`（`body { confirm: "DELETE" }`） |

自保护五条（不能改自己角色 / 不能封自己 / 不能降级最后一个 admin / 不能封 admin / 改状态必填 `reason`）是**操作规则**，不是取值域，仍在治理域 §7.2，不在本文重复。

**「全域统一」在实物上长这样**：

| 层 | 位置 | 形态 |
|---|---|---|
| 数据 | `accounts.status` / `previous_status` / `closed_at` | 列 + 上面三个 CHECK |
| 数据索引 | `ix_accounts_status ON accounts (status) WHERE closed_at IS NULL` | 只索引未注销行 |
| 域文档 | 身份域 §6.1 | 字段表两行 + DDL，带 `标准对象 §ST-1` |
| 域文档 | 身份域 §8.1 | 纯指针（本域不重画状态机） |
| 域文档 | 治理域 §7.1 | mermaid 图 + 端点/权限表（治理视角），表为准于图 |
| 横切 | 生命周期 §3.1 账号轴、§5.1 注销语义 | 指针 |
| 下游 | 论坛投影（`docs/论坛外置选型对比.md`） | 只消费 `active`，其余按「不可登录」处理 |
| 契约 | OpenAPI `AccountStatus`（待建） | 枚举，由本文取值域生成 |
| 代码 | `identity.AccountStatus`（待建） | 常量 + `IsLoginable()` |
| 前端 | 状态文案与颜色（待建） | 一处映射表，不在页面里散写 |

**加一个值要动六处**：① 本文的取值表；② 上面第一个 `CHECK`；③ 若新值带新的 `previous_status` 规则，改第二个 `CHECK`；④ 本文的迁移矩阵与身份域/治理域的图；⑤ 前端文案；⑥ 若涉及历史数据，写 migration 回填。**漏了②** 门禁直接红（值集不一致）；**漏了④** 门禁不报——会留下两条不一致的边，这是已知边界，靠 review 兜。

## 不登记什么

| 类别 | 例子 | 理由 |
|---|---|---|
| 域内私有枚举 | `credentials.kind`、`account_marks.kind`、`clients.kind`、`blobs.backend`、`auth_events.event_type` | 只被一个域消费，登记进来只会变成索引负担 |
| 目录表的种子值 | `audit_actions` 的 25 条、`gc_kinds` 的 3 条 | 权威已经是那张表 + migration，本文只登记「权威在哪」，不复制 |
| 目录表已存在的值域 | `roles` / `permissions` | 同上：本文写指针，值以表为准 |
| 域内操作规则 | 自保护五条、审核动作矩阵 | 属于「谁能做什么」，不是取值域 |
