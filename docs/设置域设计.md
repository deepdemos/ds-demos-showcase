# 设置域设计 v1.0

**适用范围**：本文是**设置域**的目标设计——站点级运营参数、每个用户自己的偏好，以及这两者共用的**参数注册表**。需求来源：[`项目需求.md`](./项目需求.md) §8（SET-001 ~ SET-010）。

- **DDL 见 [`db/schema/15-settings.sql`](../db/schema/15-settings.sql)**，本文不抄 DDL（[`DDL约定.md`](./DDL约定.md) 附录 A′）。冲突以 SQL 为准。
- **权限键 `setting.write`** 落在治理域 [`治理域设计.md`](./治理域设计.md) §4.3；**审计动作与实体类型**落在标准对象 [`标准对象/20-枚举值域.md`](./标准对象/20-枚举值域.md) §EN-5 / §EN-6；**设置键目录**登记为 §EN-9。
- **旧栈等价实现**：`../legacy-main/backend/app/services/settings_service.py`（70 行，三个键）。本文**不复刻**它，只保留其中仍然成立的语义（部分更新、审计留痕），并改掉三处（见 §2 D1 / D6 / D7）。

版本：**v1.0 · 草案（2026-11-01）**

**本版是首版**：设置域此前只有需求没有设计——治理域 v1.5 起把 `setting.write` 与 `setting` 审计实体类型**拿掉**（「设置域未设计」），`audit_log` 的 `entity_key` 也一直悬着（治理域 §14 Q17）。本版把这三件事一起结案：① 加 `setting.write`（§5.6）；② `setting` 重新进审计实体类型枚举（§5.4）；③ **`entity_key` 不加**（§2 D8）。

## 0. 一句话

**设置域只做两件事：把「运营开关」和「个人偏好」变成数据，并且保证这两类值只能从登记过的键写进来。** 它不执行任何开关的效果——`demo.auto_approve` 是 Demo 域在审核流程里读的，`history.record` 是浏览历史域在写记录前读的；本域**只负责存、负责校验、负责留痕**。

## 1. 设计理念

### 1.1 设置是「被别的域读」的数据，不是行为

需求里 SET-001 的验收是「新增一项参数不改接口形状」，SET-004 的验收是「打开自动上架后，已存在的 `pending` 作品不会被批量改成 `approved`」。这两条指向同一个结论：**设置域没有自己的业务动作**。它没有状态机、没有生命周期、不产生任何对其它域表的写。

因此本域的设计压力全部落在**约束**上，而不是流程上：

| 问题 | 本域的答案 | 落点 |
|---|---|---|
| 谁能写？ | 站点参数要 `setting.write`；个人偏好只能是本人 | §5.6 / §6.2 |
| 能写哪些键？ | 只能写注册表里有的 | §2 D3 / §6.1 |
| 值是什么类型？ | 注册表声明，值行必须匹配 | §4.2 |
| 站点参数会不会写进用户偏好？ | 不会，`scope` 是常量列 + 复合外键 | §2 D4 |
| 改了要留痕吗？ | 站点参数留；个人偏好不留 | §5.4 / §6.6 |
| 改了会影响历史数据吗？ | 不会，本域不产生任何回填 | §5.5 |

### 1.2 唯一事实源：默认值只写一次

旧栈把三个键的默认值写在 Python 常量里（`KEY_AUTO_APPROVE = "auto_approve"` 等），同时数据库里也有一行。**两个地方都能改，就一定会漂。** 本域把默认值收进 `setting_keys.default_value` 一列，代码里**不许**再出现第二份默认值——读取路径永远是「值行 ⋈ 注册表，缺行就用 `COALESCE(value, default_value)`」（§5.2）。

### 1.3 白名单必须是数据库约束，不是 `if`

SET-010 的验收是「写一个未登记的 key 被拒」。应用层 `if (!ALLOWED.has(key)) return 400` 也能过这条验收，但治理域 §4.4 已经记过旧栈的账：白名单放在 Python 常量里，`tag` / `user` / `setting` **各漏过一次**。本域用**复合外键**把「值行必须落在已登记的 `(key, scope, value_type)` 上」变成数据库不变量（§2 D3）——绕过应用层也写不进去。

## 2. 决策摘要

| # | 结论 | 为什么 | 放弃了什么 |
|---|---|---|---|
| **D1** | **三张表，不是需求里说的两张**：加 `setting_keys` 参数注册表 | SET-001 要求「新增一项参数 = 注册表加一行 + 白名单」——**注册表本身就是需求要求的东西**，它不是实现细节 | 两张表 + 代码常量白名单（旧栈做法，已漏 4 次） |
| **D2** | 值用 **`jsonb`** 一列，不按参数各开一列 | 加参数不改表结构；SET-001 的「不改接口形状」才有表结构层面的对应物 | 每键一列（加参数要 migration 改表）；`text` 存 JSON 字符串（丢类型校验） |
| **D3** | 白名单由**复合外键**强制：`(key, scope, value_type)` → `setting_keys` | §1.3。绕过应用层也写不进去 | 应用层白名单判断；`CHECK` 里硬编码键名（加参数要改约束） |
| **D4** | `scope` 是**常量列**（`site_settings` 恒 `'site'`，`user_preferences` 恒 `'user'`）+ 复合外键 | 站点参数**不可能**写进用户偏好表，反之亦然。这是「两张表」这个形状本身要保证的事 | 一张 `settings` 表带 `scope` 列（少一张表，但没有任何东西阻止写错 scope） |
| **D5** | 值表**不存默认值、不预置行**：缺行 = 用注册表默认值 | 新增参数不需要回填历史行；「管理员改过」与「没改过」在数据上可区分（有行 / 无行） | 建表时把 8 个默认值 INSERT 进值表（加参数就要回填） |
| **D6** | 审计粒度 = **每个被改的键一条**，同一次请求共享 `batch_id`；`before`/`after` = `{"value": 旧}` / `{"value": 新}` | SET-003 说「记谁、改了什么、改前改后」——「什么」是**键**。整表快照会让「改了 A」和「改了 B」在审计里长得一样 | 一次请求一条审计 + 整表快照（旧栈做法，无法回答「谁改了这个键」） |
| **D7** | 审计动作用 **`update`**，**不加域前缀**；靠 `entity_type='setting'` 区分 | 标准对象 §ID-5 通则③：动作键不加域前缀，否则 `audit_actions` 会膨胀成「动作 × 实体」的笛卡尔积 | `setting.update`（**需求 SET-003 原文这么写，与本条冲突**——已按标准对象改需求，见 §11） |
| **D8** | `audit_log` **不加 `entity_key`**（治理域 §14 Q17 结案） | 唯一会用到 `entity_key` 的是「主键是 text 的实体」。本域 `site_settings` 有 bigint 代理主键，审计指向**值行**；键名在 `before`/`after` 里，本来就在 | 加一列 + 一条 CHECK（为一张表加一列，且键名在快照里已经有了） |
| **D9** | **用户偏好不落审计** | 只影响本人可见结果，没有第三方受损；且「浏览历史开关」本身是**隐私声明**——给它记一份审计，等于把「我关掉了历史记录」变成可追溯的操作记录，与 SET-008 的意图相反 | 用户偏好也记审计（旧栈只记站点设置，本域沿用） |
| **D10** | `healthz` **不读设置表** | SET-006 要求「返回 200 时不带任何配置值」。读设置表还会让健康检查依赖设置表可用性——健康检查挂了才知道设置表挂了，是本末倒置 | 健康检查里报告当前配置（泄露运营参数） |
| **D11** | 设置变更**不触发任何批量回填**，代码里没有「设置变更 → 批量改历史状态」这条路径 | SET-004。旧栈也是这么做的，但**没有写成不变量**，所以没人能验证它 | 打开自动上架时把存量 `pending` 批量放行（用户明确要求不做） |
| **D12** | 值行**永不物理删除**；参数退役 = `setting_keys.is_active = false` | 标准对象 §ID-5 通则①「键只增不改，用 `is_active` 停用」。值行删了，审计里的 `before`/`after` 就指向一个不存在的键 | 删值行 / 删注册行（审计失去锚点） |
| **D13** | **上限分两类**：运营性上限（改了立刻生效、不需要重算、不会让旧数据自相矛盾）进 `setting_keys`；结构性上限（要 migration、改了旧数据要重判）登记进 `docs/运行手册-可变常量.md`，**不进设置** | GEN-012 要求「上限只在一处定义」，但一处不等于「都在设置里」。把结构性上限做成运行时配置，等于让管理员能一键制造「新数据合法、旧数据非法」的状态——这正是 D11 / SET-004 要防的事 | 所有能改的数都进 `setting_keys`（会让 `setting_keys` 变成一张「什么都往里塞」的表，且每次调整都要考虑存量数据是否要回填） |

## 3. 数据模型

### 3.1 三张表与它们的关系

```
setting_keys（注册表：白名单 + 类型 + 默认值）
   │  (key, scope, value_type)  ← 复合外键，两张值表都指过来
   ├── site_settings      （站点级取值，一键一行，scope 恒 'site'）
   └── user_preferences   （用户级取值，一人一键一行，scope 恒 'user'）
```

三张表都属 [`DDL约定.md`](./DDL约定.md) §7.1 的**主数据表**：不要 `deleted_at` / `erased_at`，删除走 `status` / `is_active`。

### 3.2 `setting_keys` —— 参数注册表

| 列 | 语义 |
|---|---|
| `key` | 键名，格式 `域.键`（小写 `snake_case`，至少一个点）。**域段是「这个参数影响哪个域」，不是设置域自己**——`demo.auto_approve` 由 Demo 域读，`history.record` 由浏览历史域读 |
| `scope` | `'site'` / `'user'`。**主键是 `(key, scope)`**：同一个语义允许在两级各有一行（`notify.retention_days` 就是） |
| `value_type` | `'boolean'` / `'number'` / `'string'` / `'json'`。值行的 JSON 类型必须与它一致（`CHECK` 用 `jsonb_typeof`） |
| `default_value` | **全仓唯一的默认值**（§1.2）。`jsonb`，`null` 不是合法默认值 |
| `description` | 中文说明，管理端直接展示 |
| `is_active` | 退役开关。`false` = 键还在、值还在、审计还能对上，但新写入被拒（§7 不变量 I6） |

**为什么 `value_type` 要进复合外键**：值行带着 `value_type` 列，改注册表的类型就必须同步改所有值行——否则值行的 `CHECK` 与注册表声明会不一致。外键让「改类型」变成一次显式的、会失败的写操作，而不是悄悄漂。

### 3.3 `site_settings` —— 站点级取值

| 列 | 语义 |
|---|---|
| `id` | bigint 代理主键。**审计的 `entity_id` 指向它**（D8） |
| `key` / `scope` / `value_type` | `scope` 恒 `'site'`；三列一起构成指向注册表的复合外键 |
| `value` | 当前值，`jsonb`。**没有行 = 没改过**，读出来是注册表的 `default_value`（D5） |
| `updated_at` / `updated_by` | 谁在什么时候改的。`updated_by` 可空（系统 migration 改的没有操作者） |

`UNIQUE (key)`：站点级每个键最多一行。

### 3.4 `user_preferences` —— 用户级取值

| 列 | 语义 |
|---|---|
| `account_id` / `key` | 联合主键。`account_id` 外键 → `accounts(id)`，`ON DELETE CASCADE`（账号注销后偏好没有保留价值） |
| `scope` / `value_type` | `scope` 恒 `'user'`；与 `key` 一起构成指向注册表的复合外键 |
| `value` | 当前值。**没有行 = 用默认值**（D5） |
| `updated_at` | 最后修改时间 |

**没有 `updated_by`**：这一行只可能由本人写（SET-009），加一列恒等于 `account_id` 的字段没有信息量。

### 3.5 为什么值用 `jsonb` 而不是每键一列（D2）

SET-001 的验收是「新增一项参数不改接口形状」。如果每个参数一列，加参数就要 `ALTER TABLE` + 改 DTO + 改前端表单——**接口形状一定变**。`jsonb` 一列 + 注册表声明类型，加参数只动数据。

代价是**类型检查从列类型挪到了 `CHECK`**：`CASE value_type WHEN 'boolean' THEN jsonb_typeof(value) = 'boolean' …`。这是有意的代价——换来的是「加参数不改表」。

| # | 判据 | 反例 |
|---|---|---|

这些常量没有消失，全部登记在 [`运行手册-可变常量.md`](运行手册-可变常量.md) 里，标明唯一改动点。

### 4.2 两处容易读错的语义

1. `demo.anonymous_auto_approve` 管的是**匿名提交的作品是否跳过审核**，不是「是否允许匿名提交」。允许匿名提交是 Demo 域的提交入口策略，与本键无关。
2. `collection.public_default` **不影响默认收藏夹**——COL-002 明写「默认夹保持私密，不能改名、删除或转公开」。本键只给**新建的自定义收藏夹**定默认值。

### 4.3 不在本表里的上限

`demo.cover_inline_max_bytes`（32 KiB）这类**结构性上限**不进注册表：它由 `db/schema/30-demo.sql` 的
`CHECK` 约束表达，改它要一条 migration，而且改了之后存量封面可能一夜之间变成非法数据。
同理还有 `username` 3–20、`slug` 1–128、分类树 20 层、`accounts.level` 的下界。
它们的唯一改动点是运行手册 §1「结构性上限」。

## 5. 站点级参数

### 5.1 读取：缺行 = 默认值（SET-002 的合并语义）

读取路径只有一条：

```
site_settings ⋈ setting_keys  ON (key, scope, value_type)
WHERE setting_keys.scope = 'site' AND setting_keys.is_active
→ 每行返回 COALESCE(site_settings.value, setting_keys.default_value)
```

所以「合并」不是把两次 PUT 的结果拼起来，而是**值表本来就只有被改过的键**。SET-002 的验收（先 PUT 改 A，再 PUT 只改 B，事后 A 仍是第一次的值）由「PUT 只写请求里出现的键」直接满足，不需要读-改-写。

### 5.2 写入：只写请求里出现的键

`PUT /api/admin/settings` 的语义：

1. 请求体是 `{ "键": 值, … }`，**只处理出现的键**，未出现的键一个字节都不动（SET-002）。
2. 空对象 → `422`，理由「至少提供一个要修改的设置项」（沿旧栈）。
3. 每个键先查注册表：不存在 → `422`；`is_active = false` → `422`；值类型不匹配 → `422`。**整批要么全成功要么全失败**（一个事务）。
4. 写 `site_settings` 用 upsert（`ON CONFLICT (key) DO UPDATE`），`updated_at = now()`、`updated_by = 当前账号`。

### 5.3 审计（SET-003）

**每个被改的键一条** `audit_log` 行（D6）：

| 列 | 值 |
|---|---|
| `action` | `update`（**不加域前缀**，D7） |
| `entity_type` | `setting` |
| `entity_id` | 该键对应的 `site_settings.id`（D8） |
| `before` | `{"key": "demo.auto_approve", "value": false}` |
| `after` | `{"key": "demo.auto_approve", "value": true}` |
| `actor_id` | 当前账号 |
| `batch_id` | 同一次 PUT 的所有行共享同一个值（可空列，治理域 §8 已具备） |

**为什么 `before`/`after` 里还要带 `key`**：`entity_id` 指向值行，但值行可能被后续 migration 重建；`key` 是稳定标识，审计要能自解释。D8 不加 `entity_key` 列，是因为键名在这里已经有了。

**审计行的跳转目标**：`audit_entity_types` 里 `setting` 的 `route_template` 是 `/admin/settings/{id}`，`{id}` = `site_settings.id`。治理域 `ck_audit_entity_route` 要求模板必须含 `{id}`（「点审计行要能跳回被改的那个对象」）；设置页本身是单页，没有天然的「某一行」地址，所以约定 `/admin/settings/{id}` 打开设置页时**滚动到并高亮该行**。不带 `{id}` 的 `/admin/settings` 仍是不高亮的普通入口。

**值没变的键不写审计**：PUT 一个与当前值相同的值，不产生审计行（否则「点一次保存」会淹没真正的变更）。这一条是 SET-003「每次修改落一条审计」的实现口径——**没有修改就没有审计**。

### 5.4 只影响后续（SET-004）

本域**不产生任何对其它域表的写**（D11）。`demo.auto_approve` 从 `false` 改成 `true` 之后：

- 新提交的作品走自动上架分支；
- 已存在的 `pending` 作品**一条都不动**。

代码层面这是「没有那条路径」，不是「有路径但被 `if` 挡住」。验收方式：改完设置后 `SELECT count(*) FROM demos WHERE status = 'pending'` 不变。

### 5.5 权限（SET-005）

| 端点 | 要求 |
|---|---|
| `GET /api/admin/settings` | **只要求登录**，不校验 `setting.write` |
| `PUT /api/admin/settings` | `setting.write` |

读不要权限是 SET-005 的原文（「读站点参数不需要权限」），验收是「普通用户 PUT 返回 403，GET 返回 200」。**为什么读不设权限**：返回的是运营开关（自动上架开没开），不含密钥、不含账号、不含私有配置；把它设成 `setting.write` 会让「谁能改」和「谁能看」绑死，而需求明确要分开。

`setting.write` 的落地：`db/schema/20-governance.sql` 的 `permissions` 种子（20 → 21 条）+ `role_permissions` 给 `admin` 绑（`admin` 的绑定是 `SELECT 'admin', key FROM permissions`，自动带上）。治理域 §4.3 的权限表同步加一行、标题 `20 个` → `21 个`。

### 5.6 healthz 口径（SET-006）

`GET /healthz` 返回 200 时**不带任何配置值**（D10）。它检查的是「进程活着 + 数据库连得上」，不读设置表。

「能识别核心资料暂不可访问」这一句由 healthz 的**依赖检查**承担（数据库 / OSS 可达性），不由设置域承担——设置域没有「核心资料」。

## 6. 用户级偏好

### 6.1 白名单由外键强制（SET-010）

写 `user_preferences` 时，`(key, scope='user', value_type)` 必须命中 `setting_keys` 里 `scope='user'` 的一行。写一个未登记的键 → 外键违例 → 数据库拒绝（应用层翻成 `422`）。

**这就是 SET-010 的验收方式**：不是「应用层返回 400」，而是「绕过应用层也写不进去」。

### 6.2 只由本人读写（SET-009）

端点**不接受目标 `account_id`**：

| 端点 | 身份来源 |
|---|---|
| `GET /api/me/preferences` | 会话 |
| `PUT /api/me/preferences` | 会话 |

路由里没有 `{account_id}` 段，所以「用他人 token 读该用户偏好」在路由层面就不存在——不是靠权限判断挡住的。管理端**也没有**读他人偏好的端点：偏好只影响本人可见结果，运营不需要它（D9 同理）。

### 6.3 浏览历史开关（SET-007 / SET-008）

`history.record`（user，boolean，默认 `true`）。

- 关闭 = 浏览历史域**停止形成新记录**。
- **不删除已有记录**（SET-008）。本域只存这个布尔值，删除逻辑不在本域——浏览历史域也没有「关闭即清空」的路径。
- 关闭后再打开，中间那段不补记。

### 6.4 收藏夹默认公开（SET-007）

`collection.public_default`（user，boolean，默认 `false`）。

- 只影响**新建的自定义收藏夹**的默认可见性；
- **不影响默认收藏夹**——COL-002 规定默认夹永远私密；
- 不影响**已存在**的收藏夹的可见性（改这个键不批量改历史，D11 同理）。

### 6.5 通知保留天数：站点默认 + 用户只能更短（NTF-008）

`notify.retention_days` 在两级各有一行：

- `site` 行 = 站点默认（90 天）；
- `user` 行 = 用户覆盖，**只允许配得比站点值更短**。

「只能更短」是**写入时的校验**，不是数据库约束：校验要读站点行，而 `CHECK` 不能跨表。落点：`PUT /api/me/preferences` 收到 `notify.retention_days` 时，先读站点值，`user > site` → `422`。

**为什么允许用户更短、不允许更长**：保留更久是站点的存储成本，用户没有替站点做这个决定的权利；保留更短是用户自己的隐私选择。

### 6.6 用户偏好不落审计（D9）

理由见 D9。**可验证的形式**：`audit_log` 里不存在 `entity_type = 'account_preference'` 这类行；`user_preferences` 的写入路径不调用审计写入。

## 7. 不变量

| # | 不变量 | 可验证的形式 |
|---|---|---|
| **I1** | 站点参数的读取只经过「值表 ⋈ 注册表」，不存在第二处默认值 | 代码里 `grep` 不到硬编码的 `30` / `60` / `90` / `false` 作为这些键的默认值 |
| **I2** | 值行永不物理删除 | 代码里没有 `DELETE FROM site_settings` / `DELETE FROM user_preferences`；只有 `account_id` 级联删除 |
| **I3** | 一次 PUT = 一个事务 = 每个被改的键一条审计；审计与值写入同事务 | 事务回滚后，值行与审计行**同时**不存在 |
| **I4** | 设置变更不产生任何对其它域表的写 | 设置域的写路径里没有跨域 `UPDATE` / `INSERT` |
| **I5** | 用户偏好的读写在服务端由会话身份决定，端点不接受目标 `account_id` | 路由表里没有 `/api/me/preferences/{id}` |
| **I6** | 未登记 / 已停用的键写不进去 | 绕过应用层直接 `INSERT` 未登记键 → 外键违例；`is_active = false` 的键 → 应用层 `422` |
| **I7** | 站点参数不可能出现在 `user_preferences`，反之亦然 | `scope` 常量列 + 复合外键；直接 `INSERT` 错 scope → 外键违例 |
| **I8** | 值行的 JSON 类型与注册表声明一致 | 两张值表的 `CHECK`（`jsonb_typeof`） |
| **I9** | `is_active = false` 只停新写入，不删值、不影响已读 | 停用后 `GET` 仍返回该键的当前值（或默认值），`PUT` 被拒 |

## 8. 端点

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `GET` | `/api/admin/settings` | 登录 | 返回全部 `scope='site'` 且 `is_active` 的键（合并后的值） |
| `PUT` | `/api/admin/settings` | `setting.write` | 部分更新；空对象 422；整批一个事务 |
| `GET` | `/api/me/preferences` | 登录 | 返回全部 `scope='user'` 且 `is_active` 的键（合并后的值） |
| `PUT` | `/api/me/preferences` | 登录 | 部分更新；`notify.retention_days` 额外校验「不短于站点值」 |
| `GET` | `/healthz` | 公开 | 不含任何配置值 |

**路径前缀 `admin` 与「GET 不设权限」的关系**：`/api/admin/settings` 的 GET 只要求登录，不要求 `setting.write`（SET-005 的验收是「普通用户 GET 返回 200」）。这是需求明确要求的，不是遗漏。

## 9. 边界：不归本域

| 事 | 归谁 |
|---|---|
| 作品状态（`pending` / `approved` / …） | Demo 域 |
| 「谁能改」的权限模型、角色绑定 | 治理域 |
| 作品资源同步 | Demo 域 |
| 浏览历史记录的写入与删除 | 浏览历史域 |
| 收藏夹的可见性判定 | 收藏域 |
| 通知的清理任务 | 通知域 + 生命周期域（`gc_queue`） |
| 登录限流的**执行** | 身份域（本域只存阈值） |

**一句话**：本域存值、校验、留痕；**效果在别的域**。
