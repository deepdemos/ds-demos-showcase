# DeepDemos AI 实战：视频形态策划

版本：v0.2（按单模型持续更新调整）  
日期：2026-10-07  
当前交付：节目形态、首期结构、画面方案与取材清单。尚未运行参赛模型、录制或制作成片；文中台词均为示例，不代表已发生的结果。

## 1. 推荐形态：新模型来交一次作业

用户确定按新模型发布逐期测试，目前预算不支持把所有模型测完。每期围绕一个新模型：你是产品负责人、真实用户和验收者，让它在 DSH 中接固定版本的委托，从空工程开始交付。观众跟着你看制作、首次成果、试玩、问题与修复。

一期产生一份报告、一条开发轨迹和一支视频。旧模型的工程、结果和录屏留作历史参考，不要求全部补测，也不在每次更新时全部重跑。具体测哪个模型、何时测由用户决定；本方案不启动模型调用或发布监控。

第一期的问题可以很具体：

> 今天让这个新模型接我的真实网站项目：从零做一个作品库。它交回来的站，能搜到作品、打开就玩，并且重启后还在吗？

这句话交代真实素材、任务与可见结果。本站的游戏和网页是输入内容；AI 要实现网站的前后端与托管，不要求重新生成这些游戏。

首期主线只取 P1“作品库”，常规正片目标 10–12 分钟。第一期可多留时间介绍网站；以后简短回顾固定考题即可。第一次用一个模型预演，规则变动产生的调试记录单独标注，不强制再付费测试第二个模型。

## 2. 故事的几个揭晓点

| 环节 | 观众在等待什么 | 画面怎么给出答案 |
|---|---|---|
| 出题 | 这个网站需要做到什么，任务为什么有难度？ | 原站完成一条用户旅程，再给出本轮三张任务卡 |
| 制作 | 选手怎样下手，会碰到什么？ | 每个选手保留影响交付的两三个真实节点 |
| 首次交付 | 我喜欢它做出的页面吗？ | 展示首页、详情和手机画面，给观众一点观察时间 |
| 验收 | 看过的页面，实际能用吗？ | 固定任务依次检查，结果当场呈现 |
| 修复 | 它能理解反馈并解决问题吗？ | 回到原失败步骤复验，再检查旧功能 |
| 评价 | 这次能交到我手里吗，花了多少？ | 功能证据、实际耗时/费用/人工介入和人工体验分别呈现；有可比历史记录再补对照 |

先让观众看页面、形成偏好，再揭晓功能结果，能让两部分评价相互关联。功能表现不替观众决定审美；审美也不替代功能证据。

## 3. 单模型一期，约 12 分钟的结构

以下是剪辑目标，实际时长根据已发生的事件调整。

| 时间 | 内容 | 主要画面 | 讲述重点 |
|---|---|---|---|
| 0:00–0:20 | 提前露出一个结果片段 | 本轮实际试玩中的关键瞬间，暂留最终结果 | 给观众一个具体悬念 |
| 0:20–1:20 | 新模型与委托 | 一句交代本期模型，再示范原站任务 | 今天测谁，它要交付什么；第一期可延长介绍 |
| 1:20–1:50 | 发题与条件 | 三张任务卡、DSH、空目录、公开预算与条件卡 | 使用哪个题目版本；停止与反馈规则是什么 |
| 1:50–4:00 | AI 制作 | 进度跳转、首次启动、关键修正，少量 DSH 真实画面 | 本期模型做了什么，出现哪些真实变化 |
| 4:00–5:00 | 首次成果展示 | 首页、详情页与手机画面 | 邀请观众形成自己的页面评价，暂留功能结果 |
| 5:00–8:00 | 收货验收 | 搜索、运行、持久化三个旅程 | 逐项揭晓是否完成 |
| 8:00–9:30 | 一次反馈后的修复 | 反馈摘要、关键改动、原失败步骤复验 | 是否解决，原功能有没有回归 |
| 9:30–11:30 | 本期评价 | 结果卡、费用/时间、体验点评；有可比数据再加简短历史对照 | 本期交付的能力和代价 |
| 11:30–12:00 | 后续预告 | 留一个本期未完成的问题或下一次候选方向 | 新模型继续接同一版本任务；扩展关卡另作专题 |

开头从本期真实事件里选：可以是加载失败、某个功能意外顺畅、预算即将耗尽时出现进展，或者你在试玩后修正了初看页面的评价。没有失败也可以成立，不为片头制造故障。

原有[约两分钟介绍脚本](./网站与考题介绍片段.md)可作为系列介绍或独立前导片。P1 正片取其中与浏览、搜索、预览有关的镜头；社区、审核等完整站点能力在后续对应阶段展开。

## 4. 出题怎样让人听懂

正片先展示用户想做的事情，文档承担精确字段与协议。

P1 的三张任务卡可以写成：

- **找得到：**把真实内容放进作品库，支持搜索、标签和分页。
- **跑得起来：**打开作品后资源能加载，规定的操作能完成。
- **留得住：**导入后的作品能持久保存，服务重启后仍可访问。

存档展示作为“跑得起来”的代表操作：作品刷新后能继续读取自身存档。它和站点重启后的内容持久化分别解释、分别验收。

给每张卡配一个原站或组织者基准的完整动作。比如说到“跑得起来”，立刻操作 ASCII FPV；说到“留得住”，用“重启服务以后再打开”把后端要求变成观众看得见的事情。

示例台词：

> 列表里出现作品只是开始。我要能搜到它，点开后能操作，重启这个站以后作品还在。

本轮数据规模以冻结后的输入包为准。原站拥有上千件内容，本次 Top 50 采集后有 42 条启动候选，不能把这一轮说成已经验证全部上千件或完整生产负载。

## 5. 制作过程怎样取材

为每个选手记录完整过程，正片挑能解释结果的节点：

1. **它准备怎样做。**从实际方案里选一个和后续有关的决定，例如先导入数据、先写接口或先搭页面；用一句通俗旁白解释。
2. **第一次变成可运行成果。**从空目录切到能启动的站点，标明实际经过的时间。
3. **遇到什么并怎样处理。**从真实失败、诊断或修正里选一个能看懂的事件；也可展示一次明显成功的实现。

DSH 画面出现几秒，用于证明实际发题、运行或修改。涉及代码时只放大与事件有关的几行，并说明它影响了哪次用户操作。

各期沿用基本展示任务和录制条件。片长可以随实际事件不同，但不能通过截掉有效操作、挑选失败或改变等待条件来制造不实比较。

旁白复述模型实际说过或做过的内容。需要表达你的猜测时直接说“我当时猜……”，不给模型编造心理或台词。

屏幕上标明时间压缩。首次启动、完成交付和费用只使用记录中真实取得的值；没有用量数据时标为不可得。

## 6. 验收可以拍成三次收货

### 收货一：我要找一件作品

先说明关键词与标签的预期，再在本期实现执行固定任务。结果出来以后显示简短状态：“通过”“失败”或“本次无法判定”，必要时说明原因。

搜索结果不对时，把预期数量与实际数量并排展示。观众无需理解数据库查询，也能理解找作品出了什么问题。

### 收货二：我要把它玩起来

用同一份已验证内容，打开详情并执行固定动作。

- ASCII FPV：进入预览、加速、暂停，观察操作是否有效。
- HTML 杀戮尖塔：开始一局、刷新、继续，检查作品存档。
- 科幻太空船：在公开范围允许时，展示本地模块与 3D 内容的加载。

这些是组织者已有代表证据的演示候选，仍需随最终 WebGL 等范围冻结。缺少资源的原始作品不拿来秘密考选手。

### 收货三：我要在重启后接着用

标注“重启服务”，在相同规定条件下重新访问作品库，检查内容和资源。画面用操作前后对应的作品与数量解释结果。

详细机器验收照常完成，正片用这些旅程解释关键结果。末尾结果卡包含完整验收摘要与报告入口，不能用三个精选任务冒充全部测试。

本期任务以全屏演示为主，细小文字、游戏操作和错误信息局部放大。有同条件历史素材时，可以短暂并排回放相同动作，标明模型、运行日期与题目版本；不为这个镜头重新调用旧模型。

有悬念的点击可以短暂停顿，让结果自然出现。暂停、回放、放大都不改变事件本身；结果画面来自同一次操作。

## 7. 修复怎样成为下一次揭晓

首先保存首次交付快照和验收结果，随后按已经公布的粒度给一次反馈，在固定修复预算内继续。

观众版可以说：

> 首次交付收完了。现在按同样规则反馈发现的问题，修复结束后，我会回到刚才那一步再试。

反馈镜头交代实际给了什么信息。展示一条真实修复过程，然后重放原来失败的动作，并补一次相关旧功能检查。

结果表同时保留首次与修复后表现。选手首次全部通过时，记录事实和使用的预算；不追加未约定的故障来凑修复剧情。后续追加需求进入预先说明的下一阶段，并统一发给所有选手。

## 8. 评价怎样呈现

结果卡分成几个直观字段：

| 字段 | 表达方式 |
|---|---|
| 首次交付 | 冻结场景的通过情况、关键门槛、主要未完成项 |
| 修复后 | 同一批规则下的结果及回归情况 |
| 实际投入 | 开发与修复耗时、可核对费用、人工介入 |
| 页面与体验 | 同样任务下的实际画面，你的具体点评与观众选择 |

技术分数沿用正式冻结规则；尚未冻结的权重不进入成片成绩。审美使用文字点评与实际展示，不编一个机械“颜值分”。

人工点评落到具体使用上，例如：“我喜欢这个作品卡片，但搜索入口需要找一下”“这个版本打开作品的步骤少”“手机上的标题更容易读”。观众可以持不同偏好。

本期模型身份开头就交代，不做 A/B/C 身份揭晓。观众可以先给页面留下评价，验收之后再判断自己的感受是否改变。积累足够历史素材后，匿名页面对比可独立制作，不增加模型开发调用。

作品文件是所有选手共享的输入，不能把其中游戏的美术水平归给参赛 AI 的站点设计。审美比较关注网站布局、信息组织、预览容器和使用体验。

结论限定在本次模型、提供方、DSH 条件和 P1 任务。第一次小规模预演主要说明这次交付结果，不据此发布稳定的全行业排名。

## 9. 系列怎样按新模型持续

常规更新以单模型为单位，逐次积累结果：

| 内容类型 | 本期问题 | 执行安排 |
|---|---|---|
| 新模型常规期 | 这个模型能完成固定作品库任务吗？ | 每期只运行本期模型；首轮从 P1 建立版本化基准 |
| 历史回顾 | 几期结果有哪些具体差异？ | 复用报告、工程快照与录屏；不要求旧模型重跑 |
| 发布与升级专题 | 加上传或改需求后表现如何？ | 有单独预算时，选模型沿用自身工程进入 P2/P3；成绩与 P1 分开 |
| 后续治理与交接 | 能处理角色边界、恢复和部署吗？ | 作为选定模型的扩展专题，不默认每个新模型跑完整赛季 |

第一次视频独立成立：交代任务、展示制作、验收和体验，不需要先有对手成绩。后续视频最多用一小段回顾可比历史结果，主线仍是本期模型。

历史比较须核对题目、数据、验收规则、DSH/工具、资源条件与预算政策。条件不同的记录分版本呈现；若改题，不强制补测全部旧模型。费用按当时实际记录标注，不能把不同时间的价格变化直接解释为模型能力变化。

每个模型保留独立空工程起点及自己的代码轨迹。扩展关卡接着自己的工程做，其他模型的实现不作为其输入。

## 10. 控制每期成本

- 首期只建立 P1 的可运行流程；新模型常规期先执行同版本 P1，P2/P3 需要另定专题预算。
- 跑前确定开发、修复和接入诊断的总预算上限与时间上限，安排一次反馈；记录实际停止原因。金额尚未确定，不自动付费开跑。
- 每个模型默认保留一次完整开发轨迹。预算内的一次修复仍属这次轨迹，不当作独立重复实验。
- 不为挑出更好看的结果反复从零重跑。设施故障导致的必要重试单独记录，再按规则处理。
- 复用考题介绍、任务卡、验收动作与剪辑模板；每期主要新增模型过程、成果和结论。
- 单次结果只描述这次交付；有额外预算才安排独立重复运行，并如实标注次数。

## 11. 第一支片子的制作负担

基础配置可以是屏幕录制、你的旁白、任务卡和少量结果标注。露脸属于可选项。先靠具体任务和真实揭晓撑起节奏，再根据需要加音乐、音效和动画。

从运行前开始留这些素材：

- 原站或组织者基准的相同任务录屏。
- 每个选手完整开发与验收录屏，带真实时间与对应 run ID。
- 第一次可运行成果，以及首次交付的固定页面镜头。
- 每个关键成功、失败和修复的完整前后操作。
- 相同桌面/手机视口下的作品库与详情页展示。
- 需求版本、原始测试结果、实际反馈、耗时/费用和人工介入记录。
- 你在第一次尝试时的反应，或者事后明确标注的复盘点评。

开发录屏很长时先记事件时间点；剪辑围绕事件取片段。真人反应与结果可分轨录制，后配复盘不用假装成现场。

标题草案：

> 新模型 X 来接我的真实网站项目｜DeepDemos 实战第 N 期

本期模型名和结果产生后再填具体信息。片中写明“本期测试 P1 作品库”，后续升级关卡单独说明。下一步可以把首期结构拆成正式旁白与逐镜头录制表；当前不需要修改站点代码。
