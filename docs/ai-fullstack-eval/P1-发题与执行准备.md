## 2. 开跑前补齐的事项

| 项目 | 要明确什么 | 本版方向 |
|---|---|---|
| 功能与协议 | P1 范围、数据字段、接口及公开例子 | 按参赛需求 v0.1 审阅，预演前冻结 |
| 技术栈与视觉 | 相同任务与运行时；内部实现和页面自主设计 | 允许在统一可用运行时范围内自行选技术栈 |
| 内容包 | 包标识、数量、文件哈希、样例操作、依赖和运行基准 | 从 Top 50 的 42 条启动候选继续核对；对齐 WebGL/SVG 范围，补公开受控样例，再另建发题包 |
| 执行环境 | OS、可用运行时/版本、浏览器、CPU/内存、依赖联网/缓存 | 所有选手相同；本轮不假定机器已经具备完整环境 |
| DSH | 版本、profile、插件、工具、skills、上下文、权限、子代理策略 | 建立一份可以保存和复查的公共配置摘要 |
| 模型 | 模型 ID、提供方、协议、推理设置及实际用量来源 | 接入验证单独记录，不能当作开发成绩 |
| 预算 | 首次开发/一次修复的金额或用量及时间上限；停止条件 | 用小预演校准，正式测试前固定 |
| 超时 | 构建、导入、启动、HTTP、浏览器动作与运行样例的统一等待上限 | 在参考环境测量后固定，不临时针对某选手改 |
| 计分与反馈 | 场景、权重、门槛、反馈粒度、重复次数 | 验收设计中的 100 分为建议，冻结后才正式用 |
| 隔离 | 参赛进程能读写哪些目录、访问哪些服务 | 空工程、只读开发数据、受管理 DATA_DIR；组织者资料不可读 |
| 留档 | run_id、源码快照、会话、费用、人工介入和录屏位置 | 首次、修复后与最终验收结果分别保存 |

以上每项填入本次 run record，确定值后再复制给选手。文档里的“约 50”或示意路径不能代替真实运行记录。

## 3. 发给 DSH 的材料白名单

一个参赛工作区只放：

1. TASK.md：冻结版本的 P1-参赛需求副本。
2. RUN-RECORD.md：本次公开运行条件、输入目录、变量和预算。
3. 空的实现工作目录。
4. 只读开发内容包与公开样例说明的访问入口。

组织者的测试代码、保留数据、评分输出、其他选手的工程和 DeepDemos 原始业务源码放在参赛进程不可读的区域。

另建一个文件夹不等于建立隔离。环境准备阶段通过独立用户、隔离挂载或可验证访问控制实现边界，并实际验证能否读取组织者资料；不能仅靠提示词要求“不看”。

## 4. 可以使用的发题消息

下面是发题消息模板，实际调用前填好工作目录和运行记录，并确认材料真实存在：

> 你正在参加 DeepDemos 全栈开发预演的 P1 阶段。请阅读本工作区的 TASK.md 和 RUN-RECORD.md，在空实现目录中从零完成“可浏览的作品库”。
>
> 输入内容包、运行环境、允许工具、预算和提交条件以这两份文档为准。作品文件属于数据；按给定协议导入并托管。
>
> 请完成真实前端、后端与持久化，保留统一的外部接口。你可以在允许的运行时范围内选择内部实现。
>
> 完成后提交源码、依赖文件、RUNBOOK.md、submission.json 和 DELIVERY.md。按需求规则说明已完成、未完成及自测结果，随后结束本阶段；组织者将独立验收。
>
> 需求有明确歧义时提出问题；收到的组织者答复将按统一澄清规则记录。

澄清答案进入版本化说明，对所有受影响选手公开。若澄清改变规则，统一处理已经运行的结果。

## 5. 单次 P1 的执行顺序

1. 核对 DSH 接入、公开条件和输入包；基础设施验证与正式开发分别计时。
2. 创建独立工程、空 DATA_DIR 和本次 run_id，填入运行记录。
3. 注入统一变量并发放材料，启动本次 DSH 开发任务。
4. 在预算/停止条件触发或选手提交时，停止开发并保存首次快照。
5. 依公开交付协议构建、导入和启动，独立执行诊断验收；记录失败归因。
6. 提供一次统一粒度反馈，按固定修复预算继续开发，保存修复后快照。
7. 对首次和修复后快照，在重置的执行环境中分别完成最终验收；保留测试不反馈给选手。
8. 整理成绩、门槛、费用、时间、人工介入和影像证据。
9. 经复查发现测试设施问题时，按统一规则重跑，不更改已冻结条件来帮助特定选手。

主线 P2 接着选手自身 P1 工程继续开发；不能由组织者补完失败后悄悄当作原始交付。

## 6. 首次预演怎样缩小成本

先用一个模型跑通 P1 全流程，找出材料、接口、执行器和测试的缺陷，修订并记录版本。用户计划按新模型发布逐期测试，不强制立即测试第二个模型，也不要求补齐全部现有模型。

开发期间更换了规则或环境，之前运行只作调试记录，不和新规则结果直接排名。常规期采用冻结版本，默认每模型一次完整开发轨迹及预算内的一次反馈修复；报告标明单次结果。独立重复运行与 P2/P3 扩展需要额外预算，不作为每期必做项。

跑前固定开发、修复、接入诊断的总预算上限及时间上限；具体金额尚未确定。首次失败不为获取更好成绩而反复从零重跑；必要设施重试单独归因留档。历史结果仅在条件可比时对照，旧模型不因新一期发布而全部重跑。
