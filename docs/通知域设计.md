> 状态：**已落地（2026-11-18）**：审核结果 + 评分两类事件、未读与已读、列表页与导航角标、保留期读时清理。

> 表结构见 [0035_notifications.sql](../db/migrations/0035_notifications.sql) 与

## 1. 事件类型由注册表驱动（NTF-003）

`notification_kinds` 是事件类型的注册表：加一类通知 = 插一行，不改 `notifications` 结构。
目前注册七类，每类自带它指向的**对象类型**（`object_type`，见 §2）：

| key | 触发 | `object_type` | payload |
|---|---|---|---|
| `review.approved` | 作品审核通过 | `demo` | `{}` |
| `review.rejected` | 作品被驳回 | `demo` | `{"reason":"…"}` |
| `rating.received` | 作品第一次收到某个人的评分 | `demo` | `{"score":4}` |
| `appeal.approved` | 作品申诉通过 | `demo` | `{"reason":"…"}` |
| `appeal.rejected` | 作品申诉被驳回 | `demo` | `{"reason":"…"}` |
| `model.proposal.approved` | 收录模型的提案通过（此时模型已建出） | `model` | `{}` |
| `model.proposal.rejected` | 收录模型的提案被驳回（此时还没有模型） | `proposal` | `{"reason":"…"}` |

后两条由模型写路径那条线注册（#591），**发通知的写入方在 #593 / #595**——注册与触发分开，
是因为事件类型是注册表（加类型 = 插行），不会有人因为「还没有触发点」而去改表结构。
申诉两条是 `0037_appeal_notifications.sql` 后来加的，之前漏记在本表里。

通知本身不存「渲染好的句子」：文案是前端的事，服务端只给 kind + payload + 对象快照。
这样改文案不用回填历史数据。

## 2. 对象快照与墓碑（NTF-007）

通知里存**对象类型 + 对象键 + 当时的标题**，不存外键：

| 列 | 语义 | 取值 |
|---|---|---|
| `object_type` | 对象是哪一类 | `demo` / `model` / `proposal`（与事件类型注册表的 `object_type` 一致） |
| `object_key` | 拿它能不能找到那个对象 | 作品与模型是 slug，提案是提案 id 的十进制串 |
| `object_title` | 事件发生时的标题快照 | 对象删除后仍能显示 |

不存外键是刻意的：外键 CASCADE 会让「作品删了，通知也没了」，正好违反 NTF-007。

注册表里的 `notification_kinds.object_type` 和行内的 `notifications.object_type` 之间**没有
数据库约束**：两者靠写入方保持一致（写通知时按事件类型取）。加这条约束要改注册表结构
（复合唯一键 + 复合外键），加事件类型就不再是「插一行」，所以本票明确不碰——枚举一致性
由 review 与「写入方只有 `InsertNotification` 一处」来兜。

因此列表查询顺带算一个 `accessible`，判据**按对象类型分支**：

- `demo`：作品当前在不在公开视图 `demo_public_demos` 里（软删 / 下架 / 擦除后 false）。
  前端 true 给 `/demos/{object_key}`，false 显示「该作品已不可访问」且不给跳转。
- `model` / `proposal`：**不套作品可见性**——它们的读取入口由各自域决定（模型页对下架与已合并
  也照常可开）。当前是过渡口径：对象键非空即视为可访问；各自域的判据落地时在
  `ListNotifications` 那条 SQL 里加分支。

### 2.1 旧列保留一版（expand，2026-11-26）

对象泛化之前只有作品：`notifications.demo_slug` / `demo_title` 两列，`demo_slug` 还是
`NOT NULL`，所以模型 / 提案类事件根本写不进去。这次按 expand 走：

1. 加三列并**回填**既有行（`object_type='demo'`、`object_key=demo_slug`、`object_title=demo_title`）；
2. 读路径全部改看新列（`GET /api/v1/notifications` 已经不再读旧列）；
3. 旧列**保留一版**：作品类事件仍双写，留出回滚窗口；
4. 放开 `demo_slug` 的 `NOT NULL`（长度闸改成「空值放行，非空仍要 1..128」）。

**旧列是用户可见的历史**：改名 + 删列放在同一条迁移里，一旦回滚就丢数据——所以这条只加不删。
删列由下一条迁移负责（#592），届时本文的这节注记一起删掉。
契约里的 `demoSlug` / `demoTitle` 同理：本版保留、标注为过渡期展示缓存，读的人应当改用对象字段。

## 3. 谁产生、谁收到

| 事件 | 接收者 | 跳过 |
|---|---|---|
| 审核通过 / 驳回 | 作品作者（`demos.author_id → users.sub → accounts`） | 操作者就是作者时不发（NTF-004） |
| 收到评分 | 作品作者 | 自己给自己打分不发；匿名评分照发 |
| 申诉通过 / 驳回 | 作品作者 | 操作者就是作者时不发 |
| 模型提案通过 | 提案提交人（即来源作品的作者）；对象是**模型** | 操作者就是作者时不发。写入方在 #593 |
| 模型提案驳回 | 同一接收者；对象是**提案**，payload 带驳回理由 | 同上。写入方在 #595 |

作品类事件（前三行）的接收者由 `demos` 反查（`GetDemoNotifyTarget`）；模型 / 提案那两条
没有作品可查，接收者由调用方给（提案的 `created_by`）——两者最终都写同一处 `notifyObject`。

评分只在**第一次**产生通知：改分是 UPDATE，同一个人反复改分不该刷屏。撤销评分不发通知。

## 4. 未读与已读（NTF-001、NTF-006）

- `GET /api/v1/notifications` 返回当页 + `total` + `unreadCount`。
- `GET /api/v1/notifications/unread-count` 给导航角标用，不拉列表。
- `POST /api/v1/notifications/{id}/read` 单项已读，幂等；不是自己的 id 回 404。
- `POST /api/v1/notifications/read-all` 全部已读。

已读只写 `read_at`，不删行（NTF-001：已读后仍可回看）。

## 5. 保留期（NTF-008）

站点参数 `notification.retention_days`，默认 90。当前实现是**读时清理**：列表与未读计数
先按这个天数删掉过期行，再返回。这样不需要常驻调度器，过期通知也不会被看到。
用户自定义更短保留期与定时任务留给页面那一轮（需要设置入口与 UI）。

## 6. 不做 / 边界

- 论坛的回复、提及、关注、互动与管理员待审提醒（NTF-002 前半）：对应域还没实现，
  注册表已经能接，等那些事件有写入点再注册。
- 不做通知偏好 / 免打扰（需求明确不做）。
- 不做邮件 / 站外推送。
- 不做「一条通知多人」：每人一行，未读计数简单、已读状态独立。
- 不做「一条通知多个对象」：一条通知就一个「类型 + 键」，要指两个对象就发两条。

## 7. 错误口径

- 未登录：401。
- 通知 id 不是自己的：404（不承认存在）。
- 重复标记已读：204。
