# 运行手册 · 可变常量

> **这份文件解决什么问题**：仓库里有一批「会变、但改法不是改设置」的数。
> 它们散在 SQL 约束、安全章节、运维参数里，过去要改一个数得先翻源码或翻 1500 行的设计文档。
> 这份手册把它们的**唯一改动点**集中登记，并且由 `scripts/check-constants.mjs` 在 CI 里校验
> 「登记的这个锚点还在不在」——锚点被删或被改名，CI 直接红。
>
> 版本 v1.2（2026-11-01）。共登记 **42 条**。

## 0. 什么进这份手册，什么进设置

| 想去哪儿 | 判据 | 例子 |
|---|---|---|
| **设置域**（`db/schema/15-settings.sql` 的 `setting_keys`） | 改了**立刻生效**、不需要 migration、不需要重算、不会让历史数据自相矛盾 | 上传包大小上限、收藏夹数量上限、恢复窗口天数 |
| **这份手册** | 改了要 migration / 要改代码 / 要重算存量 / 要动部署配置 | 封面内联 32 KiB、密码长度、GC 单批 50 |
| **标准对象**（`docs/标准对象.md`） | 是**跨域共享的取值域**（枚举值集合、状态档位、时间约定） | 账号状态、内容可见性、权限键 |

一句话：**设置是给运营的旋钮，手册是给开发的说明书，标准对象是给全仓的字典。**
三者不重叠。设置域的完整清单见 [`设置域设计.md`](设置域设计.md) §4。

**怎么读这张表**：「唯一改动点」一格里的第一个反引号片段是文件路径，第二个是**必须出现在那个文件里的锚点**
（约束名 / 章节号 / 字段名）。CI 就是按这两个东西校验的。

## 1. 结构性上限（改 = 一条 migration）

这些数由 `db/schema/` 里的 `CHECK` 约束表达。改它们不是改一个数，是改表结构；
而且**改了之后存量数据可能一夜之间变成非法**，所以必须先想清楚回填。

| # | 常量 | 值 | 唯一改动点 | 改了会怎样 |
|---|---|---|---|---|
| 1 | 作品 slug 长度 | 1–128 | `db/schema/30-demo.sql` · `ck_demos_slug_len` | 加 migration。放宽容易，收紧要先处理超长存量行 |
| 2 | 作品标题长度 | ≤200 | `db/schema/30-demo.sql` · `ck_demos_title_len` | 同上 |
| 3 | 封面图 URL 长度 | ≤500 | `db/schema/30-demo.sql` · `ck_demos_cover_len` | 同上。缩略图 URL 有独立一条 `ck_demos_thumb_len`，两条要同改 |

## 9. 怎么验这份手册没烂掉

```bash
node scripts/check-constants.mjs
```

它做三件事：

1. 每行「唯一改动点」里的第一个反引号片段必须是一个**存在的仓库相对路径**；
2. 同一格里的第二个反引号片段必须**真的出现在那个文件里**（约束名、章节号、字段名）；
3. 行数必须等于文首声明的条数。

**它能证明什么、不能证明什么**——这两条必须分开说：

- **能证明**：登记的文件还在；那个锚点字符串还在这个文件里（约束名、章节号、字段名）。删掉 `ck_demos_slug_len`、
  把某节的标题从 `11.4` 改成别的、把 `registry.yaml` 那段话删掉，CI 会红。
- **不能证明**：**值没变**。把 `32768` 改成 `65536`、把「≤20 层」改成「≤30 层」，门禁**不会红**（实测）。
  也不同证明锚点指对了对象——`实体合并链 20 层` 和「分类树 20 层」是两个东西，锚点字符串都在，门禁分不出来。

所以它是「**链接没断**」的证明，不是「**文档与代码一致**」的证明。值与文档的一致性只能靠 review。
