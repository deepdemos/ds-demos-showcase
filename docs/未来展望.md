# 未来展望

> **本文件是唯一的「规划项」容器。** 这里的一切都是**规划中，不承诺**——不是功能入口，不是既定能力，不得出现在产品界面里当作既有承诺（见 `项目需求.md` GEN-007 与 GEN-013）。
>
> 与 `docs/项目需求.md` 的分工：需求文档写**要做什么**；本文件写**可能做什么**。任何一条从本文件毕业进入需求文档，才算进入实现范围。

## 怎么用这份文件

**两条线，别混**：

- **重构基线** = [`项目需求.md`](项目需求.md) 的 296 条。它记录「旧站有什么、新站要覆盖什么」，**已冻结，不再追加新条目**。
- **新特性** = 本文件。任何「旧站没有、这一版也没有」的东西，先进这里，不进需求文档。

**新特性分三档往前走**，每次只走一档：

| 档 | 写在哪 | 一条要写什么 | 谁能推它往前走 |
|---|---|---|---|
| **① 想法** | 本文件，对应分组里加一行 | 是什么 / 为什么值得做 / 卡在哪 | 任何人（含 AI）都能记，但**记了不等于批准** |
| **② 规格** | GitHub issue（一个特性一个 issue） | 问题 / 目标 / 非目标 / 验收标准 / 影响面 | 想清楚了才开；开完把 issue 号回填到本文件那一行 |
| **③ 进版本** | [`PRD.md`](PRD.md) §3 的范围表 + 一组 ticket | PRD 只加**一行**指针，细节全在 issue | 只有产品负责人能拍 |

**硬规矩**：本文件里的一切都是**规划中，不承诺**——不是功能入口，不是既定能力，不得出现在产品界面里当作既有承诺（见 `项目需求.md` GEN-007 与 GEN-013）。**别人（含 AI）不得因为本文件写了某件事，就当作已批准的需求。**

### 已实现但有明确欠账的

这些不是「未设计」，是**已经跑起来但少一块**，且缺的那块有 issue 跟踪。列在这里是为了
不让「已经在用」被误读成「已经完整」。

| 项 | 现状 | 欠什么 | 跟踪 |
|---|---|---|---|
| 邮箱验证 | 注册即 `active`，`account_emails.verified_at` 恒为 NULL；表上的 `DEFAULT 'pending'` 没有路径会用到 | 发码端点（`PurposeVerifyEmail`）→ 验证端点 → 改邮箱时旧码失效 → 未验证账号的可见行为，四条齐了才敢把注册改成写 `pending` | issue #169 · `已知松点.md` 第 20 条 |
| 封禁的会话吊销 | 封禁后登录与 `/me` 都回 403（读 `accounts` 当前状态），**效果对** | `web_sessions` 的行没被写 `revoked_at`，事后查不出会话是哪一刻被踢的 | `已知松点.md` 第 19 条 |

## 三、更远的事

### 想法档（一行一条，不承诺）

| 想法 | 为什么值得做 | 卡在哪 |
|---|---|---|
| **每日 AI 新闻**（资讯流） | 让站点有「每天来一次」的理由，是「生态入口」定位最便宜的拉新手段 | 内容从哪来（人工编辑 / 抓 RSS / 用户投递）、要不要审核、与论坛的边界 |
| **Game 专区** | 互动内容比静态展示更能留人；与已有 demo 形态有交集 | 是栏目还是新域；游戏要不要可运行（依赖沙箱）；与「作品」的边界怎么划 |

> 这两条来自 2026-11-21 的一份外部架构建议，只被当作**想法**登记 —— 没进需求、没排期、没批准。


### 本组怎么写

一行一条，不写方案：

```text
| 想法一句话 | 为什么值得做（一句） | 卡在哪（技术 / 依赖 / 决策） |
```

不写「怎么做」——那是 ② 档（issue 里的规格）的事。**这一组的价值是「不丢」，不是「想清楚」。**
