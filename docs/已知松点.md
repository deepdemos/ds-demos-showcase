# 已知松点台账

> **这份文件登记「我们知道它不牢靠、但当前选择先接受」的地方。**
>
> 和 bug 的区别：bug 是「本该对但错了」，松点是「它只在某个范围内成立，超出范围就不保证」。
> 和 TODO 的区别：TODO 是「还没做」，松点是「做了，但只做到这里」。
>
> **每条都写清三件事**：它现在能保证什么、不能保证什么、什么信号出现时该回来加固。
> 不写「以后优化」——那种话等于没写。

## 怎么用

- 发现一处「知道不完美但先这样」的地方 → 加一条，写清上面三件事。
- 加固了 → 划掉并注明日期与 PR，不要直接删（删了就没人知道它曾经是个问题）。
- **review 时如果发现某条已经不成立，先问「是不是已经悄悄固化了」，再决定删还是标。**

## 1. 用户名规则定义在两处，没有门禁比对

| | |
| --- | --- |
| 在哪 | `backend/internal/domain/identity/account.go` 的 `usernamePattern`（`^[A-Za-z0-9_-]{3,20}$`）<br>`db/schema/10-identity.sql` 的 `profiles` 表 CHECK |
| 能保证 | 两处**现在**一致；两边各有一组测试钉住当前取值 |
| 不能保证 | 将来改一处忘另一处。结果是「400 还是 500 取决于哪边更严」——这类不一致最难查，因为它取决于用户填了什么 |
| 什么时候修 | 出现第一个「改用户名规则」的需求时。修法：门禁读 Go 里的正则、读 `pg_get_constraintdef` 里的 CHECK，比对字符集与长度 |
| 现在靠什么兜 | `account_test.go` 与 `verify-schema.mjs` 各钉一半，但**没有任何东西比对它们** |

## 2. `check-constants` 只证明锚点字符串还在

| | |
| --- | --- |
| 在哪 | `scripts/check-constants.mjs` |
| 能保证 | 运行手册里每条「唯一改动点」的文件还在、锚点字符串还在文件里 |
| 不能保证 | **值没变**。实测：把 `db/schema/30-demo.sql` 的 `32768` 改成 `65536`，门禁与 `check-schema` 都仍绿。也分不清「实体合并链 20 层」与「分类树 20 层」 |
| 什么时候修 | 当同一条锚点被两条常量共用、或有人报告「手册写的值和代码不一致」时 |
| 现在靠什么兜 | 无。这正是它被写进 `docs/运行手册-可变常量.md`「能证明什么／不能证明什么」两段的原因 |

## 3. `check-api-compat` 抓不到三类破坏

| | |
| --- | --- |
| 在哪 | `scripts/check-api-compat.mjs` / `api/COMPATIBILITY.md` |
| 能保证 | 结构层面：删字段、删枚举值、可空变必填、删端点、改类型都会红 |
| 不能保证 | ① **同名改语义**（`page` 从 1 起改 0 起，类型还是 `int`）；② **约束收紧**（`maxLength` / `maximum` 不进 Go 类型）；③ **加枚举值导致客户端 `switch` 不穷尽**（只给 ⚠️，但客户端运行时真会炸） |
| 什么时候修 | 第 ③ 条出现第一次线上/联通事故时；①② 靠 review，出现漏网时再考虑加语义断言 |
| 现在靠什么兜 | 判定表写进 `api/COMPATIBILITY.md`，`docs/development-workflow.md` 的「三类校验」表也点了名 |

## 4. `check-layering` 只证明 import 方向没写错

| | |
| --- | --- |
| 在哪 | `scripts/check-layering.mjs` / `docs/后端分层约定.md` |
| 能保证 | `platform` 不 import 业务、`domain` 不 import `net/http` 与生成物、域之间不互相 import、生成物不 import 本仓库其它包 |
| 不能保证 | ① 这个包是不是**真的只做这一层的事**——`httpapi` 里完全可以写满业务规则而不违反任何一条；② 调用是否绕了远路（`httpapi` 直接调 `store` 而不经过 `domain`，今天对、下月可能错）；③ 包内文件之间的职责划分 |
| 什么时候修 | 当 `domain/` 出现第二个包、或某条业务规则被两个入口复用时 |
| 现在靠什么兜 | 无。它只扫**非测试**文件；测试可以随便 import |

## 5. `web_sessions.verified_at` 的语义是临时的

| | |
| --- | --- |
| 在哪 | `db/schema/10-identity.sql` 的 `web_sessions`；设计出处 `docs/身份服务模型设计.md` §7 |
| 能保证 | 会话是服务端的、能立刻吊销（登出不是只清 cookie） |
| 不能保证 | 这一列**目前**记的是「本地密码校验时刻」。设计里它记的是「上次向 IdP 校验的时刻」。也就是说现在没有 IdP，语义被借用了 |
| 什么时候修 | 真接 IdP 的那一刀。届时要么改语义、要么加一列区分 |
| 现在靠什么兜 | 只在 issue #140 与提交信息里写了，**没有任何门禁或测试能发现它被误解** |

## 6. `api.gen.go` 会随端点数线性增长

| | |
| --- | --- |
| 在哪 | `backend/internal/api/api.gen.go`（生成物） |
| 能保证 | 契约与 Go 类型永远一致（CI 重新生成并比对） |
| 不能保证 | 这**一个文件**会越来越长。实测：3 个端点 390 行，加 `/me` 后 4 个端点 **463 行**（仍在 500 警告线以下，`file-size` 目前只报了 `checks.test.mjs` 一条警告）。按每端点 40–70 行推算，**再多一两个端点就会触发 500 行警告**，到 800 行直接失败 |
| 什么时候修 | 下一次 `file-size` 报 error 时。修法是 `oapi-codegen` 的 `output-options` 按 tag 拆多文件，不是删端点 |
| 现在靠什么兜 | 无。它是生成物，但 `check-file-size` 不区分生成物 |

## 7. `--update` 重签契约基线可以被用来「让 CI 绿」

| | |
| --- | --- |
| 在哪 | `scripts/check-api-compat.mjs --update`（`npm run seal:api-compat`） |
| 能保证 | 重签是个显式动作，会进 diff、会被 review |
| 不能保证 | 它**不拒绝**破坏性变更。有人为了过 CI 直接 `--update`，破坏性变更就被悄悄吸收了 |
| 什么时候修 | 第一次真的有人这么做时。修法是加 `--allow-breaking` 开关并要求在 PR 里引用 |
| 现在靠什么兜 | `api/COMPATIBILITY.md` 写了「不要为了 CI 绿而重签」——**这是约定，不是强制** |

## 8. 本地 PostgreSQL 与 CI 同版本但不同部署

| | |
| --- | --- |
| 在哪 | `docs/开发环境.md` |
| 能保证 | 版本号一致（18.6），schema 能跑通 |
| 不能保证 | 部署形态一致：CI 是 `postgres:18` 容器，本地可能是 WSL2 里的包安装（集群参数、locale、`pg_hba` 都不同）。**在本地绿了不等于 CI 会绿**，反之亦然 |
| 什么时候修 | 出现「本地过了 CI 红」且原因与部署差异有关时。修法是本地也用容器 |
| 现在靠什么兜 | 唯一的真库断言在 CI 跑（`contract` job 的 `verify-schema`） |
