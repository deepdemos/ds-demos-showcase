# 已知松点台账

> **这份文件登记「我们知道它不牢靠、但当前选择先接受」的地方。**
>
> 和 bug 的区别：bug 是「本该对但错了」，松点是「它只在某个范围内成立，超出范围就不保证」。
> 和 TODO 的区别：TODO 是「还没做」，松点是「做了，但只做到这里」。
>
> **每条都写清三件事**：它现在能保证什么、不能保证什么、什么信号出现时该回来加固。
> 不写「以后优化」——那种话等于没写。

## 怎么用

- 发现一处「知道不完美但先这样」的地方 → 加一条，写清上面三件事。
- 加固了 → 划掉并注明日期与 PR，不要直接删（删了就没人知道它曾经是个问题）。
- **review 时如果发现某条已经不成立，先问「是不是已经悄悄固化了」，再决定删还是标。**

## 9. 第②层限流：验证码发送频率是「生成前判定」

`kernel/verification` 的 `Issue` 先查 `CountRecentVerificationCodes`，通过才生成。
两个并发请求可能同时看到「还没发过」，各生成一个码——**最新那条才有效**
（`LatestVerificationCode` 取 id 最大），所以不是安全漏洞，只是多写一行。

严格的修法是把「同用途 + 同标识符 + 分钟桶」做成唯一索引。那会把存储绑死在
「分钟」这个粒度上，而频率策略本身是可调的，所以暂时不这么做。

## 10. 第②层限流：错误尝试计数不是原子的

`BumpVerificationAttempts` 是 `UPDATE ... SET attempts = attempts + 1 RETURNING attempts`，
并发下两个请求可能读到同一个新值，导致真正作废的时刻略晚于 5 次。

影响有限（作废仍会发生，只是晚一两次），严格做法是 `UPDATE ... WHERE attempts < 5`
把判定和自增合一，返回 `execrows` 判断是否越界。

## 11. 第②层限流：验证码「按标识符」而非「按账号」

`login_attempts.identifier_hash` 存的是**用户输入的那个标识符**的 HMAC，与账号是否存在
无关。这样「不存在的邮箱」也会被要求验证码，避免用响应形状做账号枚举。

代价：同一个人的邮箱和用户名是两个标识符，两条计数互不相通。攻击者如果同时知道
两者，各有 5 次机会（但都受第①层「账号+IP 10 次」约束）。

## 12. 重置密码：验证码先消费、后开事务

`ResetPassword` 的顺序是「消费验证码 → 查目标 → 开事务改哈希并踢会话」。

消费成功但后续步骤失败时，用户**已经用掉了一次验证码**却没能改密码，得重新申请。
取舍方向是对的（宁可让用户重来一次，也不让一个验证码可以被反复试），但失败率不是零：
数据库连接抖动、`UpdatePasswordHash` 撞上约束，都会走到这条路径。
门禁能证明的只是「消费与使用是分开的两步」，证明不了两者之间不会失败。

## 13. `RevokeSessionsBefore` 用 `<` 而不是 `<=`

撤销条件是 `web_sessions.created_at < rotated_at`。若某个会话的签发时刻与本次
`rotated_at` **落在同一微秒**，它会被漏掉，继续有效。

实际概率极低（Postgres 的 `now()` 是事务开始时刻，而待撤销的会话来自更早的事务），
但不是零。改成 `<=` 会把「本次重置之后新建的会话」也一起踢掉，所以要改得先想清楚
新会话是在同一个事务里建、还是之后建。

## 14. `argon2` 没有并发闸

设计 §11.4 与运行手册第 16 行都写「最多 4 路并发」，代码里没有任何 semaphore 或工作池
（`grep -rn "semaphore\|maxConcurrent" backend/internal/` 为空）。

后果：注册 / 登录 / 重置密码同时打进来时，每个请求 64 MiB，**峰值内存 = 并发 × 64 MiB**。
这不是安全漏洞（不放大攻击收益），是**可用性**风险：一波登录高峰就能把容器 OOM。
修法是在 `HashPassword` / `VerifyPassword` 外面套一个有界信号量，返回「忙」而不是排队。

## 15. 密码哈希没有 rehash 路径

运行手册第 15 行写「登录时按存储参数验证后 rehash」，`grep -rni rehash backend/` 为空。

今天没影响（所有哈希都是同一组参数），但一旦调 m/t/p，老用户会永远停在旧参数上——
而调参数恰恰是「密码强度不够了」时才会做的事。

## 16. 没有弱口令表

设计 §11.4 要求注册时拒绝常见弱口令，代码里没有。今天只有长度（10–128）与格式校验。
`correct-horse-battery` 这种测试密码能注册成功，`1234567890` 也能。

代价是**基线会停在某个历史时刻**：实测它一度只有 3 个端点，而契约已经有 10 个，
`api/openapi.yaml` 头部的描述也跟着停在「三个端点」。没有东西提醒你重签。

本 PR 重签了一次。往后在「加端点」的 PR 里顺手跑 `npm run seal:api-compat` 就行，
但那仍然是人工纪律，不是门禁——真想自动化，得让 CI 在 `surface.json` 缺了新端点时**警告**。

## 19. 封禁不吊销会话行

封禁后 `/me` 立刻 403（它读的是 `accounts` 的当前状态，不是 `web_sessions` 里的快照），
效果是对的。但 `web_sessions` 里的行**没有**被写 `revoked_at`。

缺的是可审计性：事后查不出「这个人的会话是哪一刻被踢的」，只能看到他今天被 403 了。
等有了 ban 端点，吊销应当和状态变更在同一个事务里做。

## 20. ~~注册即 `active`，邮箱从未验证~~（2026-11-04 已修）

`backend/db/queries/identity.sql` 注册时直接写 `status='active'`，`account_emails.verified_at`
一直是 NULL。表上留着的 `DEFAULT 'pending'` 没有任何路径会用。

**为什么这么选**：本期没有邮箱验证流程，写 `pending` 会让所有新用户卡在一个没有界面能解的态上。
取舍本身没错，错的是**只记了「为什么不写 pending」，没记「欠了什么」**。

欠的是一条完整链路：发码端点（`PurposeVerifyEmail`）→ 验证端点 → 改邮箱时旧码失效 →
未验证账号的可见行为 → 才敢把注册改成写 `pending`。

**风险面**：冒用他人邮箱（真正的主人以后注册会撞 `uq_account_emails_email`）；找回密码对这类账号无效
（重置码发到别人的邮箱）；任何「按邮箱认人」的功能都不能信这条数据。

**2026-11-04 已修**（issue #169 结案）：注册写 `pending`、不发会话；
`POST /api/v1/auth/verify-email` 消费验证码后转 `active`；`POST /api/v1/auth/verify-email/resend` 重发；
登录对 `pending` 回 403 + `email_not_verified`，前端给「去验证邮箱」的去处。

留了两处，各自有单独条目：未验证账号 30 天不清理（第 31 条）、验证码重发受限流每分钟一次（第 9 条）。

## 22. 投稿失败补偿会留下孤儿对象

`backend/internal/domain/demo/submit.go` 的顺序是「落库 → 上传文件」，上传失败时
用 `compensate()` 删库行与已上传对象。如果进程恰好在这个窗口里被杀，会出现：
- 库里有 `draft` + `pending` 的行，但没有文件（用户看不到，也不会出现在列表里）
- 或者对象存了、库行没删成（几个无引用的 blob）

**能保证什么**：正常路径（含可预期的上传错误）都会清理干净。
**不能保证什么**：进程被 SIGKILL 的那一瞬间。**没有 GC 扫描**——`gc_queue` 表建好了但没代码。

补充（2026-11-04）：`compensate()` 原先**先删文件再删库**，与它自己注释写的「先删库再删文件」
正好相反 —— 注释里那句「反过来的话会留下一个指向空目录的作品」描述的正是当时的实际行为。
已改成先删库：库删失败时**不删文件**并返回（留着文件，下一次补偿或按 slug 清都能兜住；
此刻删文件只会把「库里有行、磁盘没文件」做实）。
**什么信号出现时该修**：有了 GC worker 时，让它扫「存在超过一段时间、没有 `current_revision_id`
指向或文件缺失」的草稿。

## 23. `users.deleted_at` 还没有同步逻辑

治理域 §727 定：注销时 `accounts.status='deleted'`、`accounts.closed_at=now()`、**`users.deleted_at=now()`（demo 站同步）**。

`users` 投影表现在由注册流程建行（迁移 0007），但**没有任何代码在账号注销时把它标掉**——因为注销流程本身还没实现（`accounts.status='deleted'` 没有任何端点能写）。

**能保证什么**：注册后 `users` 与 `accounts` 一一对应。
**不能保证什么**：注销后 `users.deleted_at` 会被填上。它现在恒为 `NULL`。
**什么信号出现时该修**：实现「用户自助注销」时。判据是「删账号之后 `SELECT count(*) FROM users WHERE deleted_at IS NULL AND sub NOT IN (SELECT sub FROM accounts WHERE status <> 'deleted')` 必须为 0」。

## 24. `demo_revisions` 的「至少一条版本」没有数据库约束

`docs/Demo域设计.md` §9 不变量 #3 要求「每个 `Demo` 至少一条 revision」。**没有落成约束**，理由不是忘了：

投稿事务天然是两阶段的 —— 先 `INSERT demos`（此时还没有 revision），再 `INSERT demo_revisions`。非延迟约束会让第一步直接失败；做成 `DEFERRABLE INITIALLY DEFERRED` 能把检查推到提交，但那会把「建 demo 必须在一个事务里」变成硬约束，挡死「先存草稿、稍后补内容」这类流程。

**能保证什么**：投稿接口在一个事务里建作品与第一条版本。
**不能保证什么**：库里不存在「作品没有版本」的行。手工 `INSERT demos` 就能造出来。
**什么信号出现时该修**：真出现「先存草稿」的需求时，改成显式的 `demo_drafts` 状态，而不是靠延迟约束去猜。

补充（2026-11-04）：擦除那条分支原先是无条件 `RETURN NEW`，等于「擦除」这个动作本身
可以顺手改 `demo_id` / `rev_no` / `created_at` —— `ck_rev_erased_content` 只兜内容列。
现在已在 `0009` 里收窄成「只允许清空内容列」，`verify-schema` 加了两条断言钉住它。

## 25. `verify-schema` 不覆盖触发器之前的存量数据

迁移 0009 的三个触发器只管**之后**的写入。如果某个环境里已经存在违反不变量 #1/#2/#10 的行（比如 A 的指针指着 B 的版本），加触发器**不会**报错，也不会修正 —— 它只保证新写入是对的。

**能保证什么**：上线后新写入的数据自洽。
**不能保证什么**：存量数据自洽。加触发器时就地查过（当时库里有 0 行），但那是 2026-11-03 那一刻的事实。

| --- | --- |
| 在哪 | `backend/internal/domain/demo/blobs.go` 写 `blobs` 与 `demo_revision_files`；全仓没有任何代码删 `blobs` 行或它们在存储里的对象 |
| 为什么现在更要紧 | 旧布局里删作品就删目录，磁盘能回来；现在一份字节可能被多个版本引用，**不能**按 slug 删（会弄坏别人的作品），所以补偿与删除都只清库行，对象留在盘上 |

| **在哪** | `backend/cmd/api/main.go` 的 `http.Server`：设了 `ReadHeaderTimeout` 5 秒、`ReadTimeout` 5 分钟、`IdleTimeout` 120 秒，**没有** `WriteTimeout` |
| **为什么这么做** | `WriteTimeout` 是「整个响应写完」的上限，而 `GET /download/{slug}` 可以传几百 MiB。慢网下几分钟很正常，设一个数就等于给下载功能加了个随机的失败点——而且失败发生在响应头已经发出去之后，客户端只会看到半截文件，比 500 更难查 |
| **能保证** | 慢读**请求头**的客户端 5 秒被踢；keep-alive 空闲连接 120 秒回收；慢传**请求体**的客户端 5 分钟被踢 |
| **不能保证** | 一个发出请求却始终不读响应的客户端，可以在 goroutine 与文件句柄上停留任意久。打开连接数的上限只剩操作系统 fd 限制与反代的并发配置 |
| **什么时候修** | 部署层有 Nginx 时基本不用管（它会缓冲响应并在 `proxy_write_timeout` 之后断开）。真要修：给下载端点 `hijack` 出裸 TCP 自己控超时，或把下载挪到独立 listener 上单独配 `WriteTimeout` |
| **代价** | 独立 listener 要改部署（两个端口或一个 Unix socket）、改契约里的 base URL，并让所有下载相关测试换 host。收益是「不读响应」这类连接被及时清掉——目前没有证据说明它是瓶颈 |
