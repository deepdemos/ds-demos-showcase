# 已知松点台账

> **这份文件登记「我们知道它不牢靠、但当前选择先接受」的地方。**
>
> 和 bug 的区别：bug 是「本该对但错了」，松点是「它只在某个范围内成立，超出范围就不保证」。
> 和 TODO 的区别：TODO 是「还没做」，松点是「做了，但只做到这里」。
>
> **每条都写清三件事**：它现在能保证什么、不能保证什么、什么信号出现时该回来加固。
> 不写「以后优化」——那种话等于没写。

## 怎么用

- 发现一处「知道不完美但先这样」的地方 → 加一条，写清上面三件事。
- 加固了 → 划掉并注明日期与 PR，不要直接删（删了就没人知道它曾经是个问题）。
- **review 时如果发现某条已经不成立，先问「是不是已经悄悄固化了」，再决定删还是标。**

## 9. 第②层限流：验证码发送频率是「生成前判定」

`kernel/verification` 的 `Issue` 先查 `CountRecentVerificationCodes`，通过才生成。
两个并发请求可能同时看到「还没发过」，各生成一个码——**最新那条才有效**
（`LatestVerificationCode` 取 id 最大），所以不是安全漏洞，只是多写一行。

严格的修法是把「同用途 + 同标识符 + 分钟桶」做成唯一索引。那会把存储绑死在
「分钟」这个粒度上，而频率策略本身是可调的，所以暂时不这么做。

## 10. 第②层限流：错误尝试计数不是原子的

`BumpVerificationAttempts` 是 `UPDATE ... SET attempts = attempts + 1 RETURNING attempts`，
并发下两个请求可能读到同一个新值，导致真正作废的时刻略晚于 5 次。

影响有限（作废仍会发生，只是晚一两次），严格做法是 `UPDATE ... WHERE attempts < 5`
把判定和自增合一，返回 `execrows` 判断是否越界。

## 11. 第②层限流：验证码「按标识符」而非「按账号」

`login_attempts.identifier_hash` 存的是**用户输入的那个标识符**的 HMAC，与账号是否存在
无关。这样「不存在的邮箱」也会被要求验证码，避免用响应形状做账号枚举。

代价：同一个人的邮箱和用户名是两个标识符，两条计数互不相通。攻击者如果同时知道
两者，各有 5 次机会（但都受第①层「账号+IP 10 次」约束）。

## 12. 重置密码：验证码先消费、后开事务

`ResetPassword` 的顺序是「消费验证码 → 查目标 → 开事务改哈希并踢会话」。

消费成功但后续步骤失败时，用户**已经用掉了一次验证码**却没能改密码，得重新申请。
取舍方向是对的（宁可让用户重来一次，也不让一个验证码可以被反复试），但失败率不是零：
数据库连接抖动、`UpdatePasswordHash` 撞上约束，都会走到这条路径。
门禁能证明的只是「消费与使用是分开的两步」，证明不了两者之间不会失败。

## 13. `RevokeSessionsBefore` 用 `<` 而不是 `<=`

撤销条件是 `web_sessions.created_at < rotated_at`。若某个会话的签发时刻与本次
`rotated_at` **落在同一微秒**，它会被漏掉，继续有效。

实际概率极低（Postgres 的 `now()` 是事务开始时刻，而待撤销的会话来自更早的事务），
但不是零。改成 `<=` 会把「本次重置之后新建的会话」也一起踢掉，所以要改得先想清楚
新会话是在同一个事务里建、还是之后建。

## 14. `argon2` 没有并发闸

设计 §11.4 与运行手册第 16 行都写「最多 4 路并发」，代码里没有任何 semaphore 或工作池
（`grep -rn "semaphore\|maxConcurrent" backend/internal/` 为空）。

后果：注册 / 登录 / 重置密码同时打进来时，每个请求 64 MiB，**峰值内存 = 并发 × 64 MiB**。
这不是安全漏洞（不放大攻击收益），是**可用性**风险：一波登录高峰就能把容器 OOM。
修法是在 `HashPassword` / `VerifyPassword` 外面套一个有界信号量，返回「忙」而不是排队。

## 15. 密码哈希没有 rehash 路径

运行手册第 15 行写「登录时按存储参数验证后 rehash」，`grep -rni rehash backend/` 为空。

今天没影响（所有哈希都是同一组参数），但一旦调 m/t/p，老用户会永远停在旧参数上——
而调参数恰恰是「密码强度不够了」时才会做的事。

设计 §11.4 要求注册时拒绝常见弱口令，代码里没有。今天只有长度（10–128）与格式校验。
`correct-horse-battery` 这种测试密码能注册成功，`1234567890` 也能。

## 19. 封禁不吊销会话行

封禁后 `/me` 立刻 403（它读的是 `accounts` 的当前状态，不是 `web_sessions` 里的快照），
效果是对的。但 `web_sessions` 里的行**没有**被写 `revoked_at`。

## 20. ~~注册即 `active`，邮箱从未验证~~（2026-11-04 已修）

`backend/db/queries/identity.sql` 注册时直接写 `status='active'`，`account_emails.verified_at`
一直是 NULL。表上留着的 `DEFAULT 'pending'` 没有任何路径会用。

**为什么这么选**：本期没有邮箱验证流程，写 `pending` 会让所有新用户卡在一个没有界面能解的态上。
取舍本身没错，错的是**只记了「为什么不写 pending」，没记「欠了什么」**。

欠的是一条完整链路：发码端点（`PurposeVerifyEmail`）→ 验证端点 → 改邮箱时旧码失效 →
未验证账号的可见行为 → 才敢把注册改成写 `pending`。

**风险面**：冒用他人邮箱（真正的主人以后注册会撞 `uq_account_emails_email`）；找回密码对这类账号无效
（重置码发到别人的邮箱）；任何「按邮箱认人」的功能都不能信这条数据。

**2026-11-04 已修**（issue #169 结案）：注册写 `pending`、不发会话；
`POST /api/v1/auth/verify-email` 消费验证码后转 `active`；`POST /api/v1/auth/verify-email/resend` 重发；
登录对 `pending` 回 403 + `email_not_verified`，前端给「去验证邮箱」的去处。

留了两处，各自有单独条目：未验证账号 30 天不清理（第 31 条）、验证码重发受限流每分钟一次（第 9 条）。

## 22. 投稿失败补偿会留下孤儿对象

`backend/internal/domain/demo/submit.go` 的顺序是「落库 → 上传文件」，上传失败时
用 `compensate()` 删库行与已上传对象。如果进程恰好在这个窗口里被杀，会出现：
- 库里有 `draft` + `pending` 的行，但没有文件（用户看不到，也不会出现在列表里）
- 或者对象存了、库行没删成（几个无引用的 blob）

**能保证什么**：正常路径（含可预期的上传错误）都会清理干净。
**不能保证什么**：进程被 SIGKILL 的那一瞬间。**没有 GC 扫描**——`gc_queue` 表建好了但没代码。

补充（2026-11-04）：`compensate()` 原先**先删文件再删库**，与它自己注释写的「先删库再删文件」
正好相反 —— 注释里那句「反过来的话会留下一个指向空目录的作品」描述的正是当时的实际行为。
已改成先删库：库删失败时**不删文件**并返回（留着文件，下一次补偿或按 slug 清都能兜住；
此刻删文件只会把「库里有行、磁盘没文件」做实）。
**什么信号出现时该修**：有了 GC worker 时，让它扫「存在超过一段时间、没有 `current_revision_id`
指向或文件缺失」的草稿。

## 23. `users.deleted_at` 还没有同步逻辑

治理域 §727 定：注销时 `accounts.status='deleted'`、`accounts.closed_at=now()`、**`users.deleted_at=now()`（demo 站同步）**。

`users` 投影表现在由注册流程建行（迁移 0007），但**没有任何代码在账号注销时把它标掉**——因为注销流程本身还没实现（`accounts.status='deleted'` 没有任何端点能写）。

**能保证什么**：注册后 `users` 与 `accounts` 一一对应。
**不能保证什么**：注销后 `users.deleted_at` 会被填上。它现在恒为 `NULL`。
**什么信号出现时该修**：实现「用户自助注销」时。判据是「删账号之后 `SELECT count(*) FROM users WHERE deleted_at IS NULL AND sub NOT IN (SELECT sub FROM accounts WHERE status <> 'deleted')` 必须为 0」。

## 24. `demo_revisions` 的「至少一条版本」没有数据库约束

`docs/Demo域设计.md` §9 不变量 #3 要求「每个 `Demo` 至少一条 revision」。**没有落成约束**，理由不是忘了：

投稿事务天然是两阶段的 —— 先 `INSERT demos`（此时还没有 revision），再 `INSERT demo_revisions`。非延迟约束会让第一步直接失败；做成 `DEFERRABLE INITIALLY DEFERRED` 能把检查推到提交，但那会把「建 demo 必须在一个事务里」变成硬约束，挡死「先存草稿、稍后补内容」这类流程。

**能保证什么**：投稿接口在一个事务里建作品与第一条版本。
**不能保证什么**：库里不存在「作品没有版本」的行。手工 `INSERT demos` 就能造出来。
**什么信号出现时该修**：真出现「先存草稿」的需求时，改成显式的 `demo_drafts` 状态，而不是靠延迟约束去猜。

补充（2026-11-04）：擦除那条分支原先是无条件 `RETURN NEW`，等于「擦除」这个动作本身
可以顺手改 `demo_id` / `rev_no` / `created_at` —— `ck_rev_erased_content` 只兜内容列。
现在已在 `0009` 里收窄成「只允许清空内容列」，`verify-schema` 加了两条断言钉住它。

## 25. `verify-schema` 不覆盖触发器之前的存量数据

迁移 0009 的三个触发器只管**之后**的写入。如果某个环境里已经存在违反不变量 #1/#2/#10 的行（比如 A 的指针指着 B 的版本），加触发器**不会**报错，也不会修正 —— 它只保证新写入是对的。

**能保证什么**：上线后新写入的数据自洽。
**不能保证什么**：存量数据自洽。加触发器时就地查过（当时库里有 0 行），但那是 2026-11-03 那一刻的事实。

| --- | --- |
| 在哪 | `backend/internal/domain/demo/blobs.go` 写 `blobs` 与 `demo_revision_files`；全仓没有任何代码删 `blobs` 行或它们在存储里的对象 |
| 为什么现在更要紧 | 旧布局里删作品就删目录，磁盘能回来；现在一份字节可能被多个版本引用，**不能**按 slug 删（会弄坏别人的作品），所以补偿与删除都只清库行，对象留在盘上 |

| **为什么不建三元组索引** | 实测：`show_trgm('回滚')` = `{0xbe3b5b, 0x233121, 0x6babfa}`，三个三元组**都带边界空格**；而 `show_trgm('第一版回滚测试')` 与它**零个**公共元素——词在标题中间时索引查不到任何候选行。`show_trgm('回滚真栈')` 与它共享 2 个（词在开头才有效）。三字以上的词有一条内部三元组（`show_trgm('零拷贝')` 有 4 个），位置无关地可用。所以 trgm 对中文中缀搜索只对「长词」有效，本轮按用户裁决先不建 |
| **什么时候修** | 公开作品到五位数、或出现「搜一次好几秒」的反馈时。届时按需求 SCH-006 / SCH-003 一起做：排序要 `demo_stats.view_count`（已有），筛选要维度注册表 |
| **代价** | 换检索方案（trgm 长词 + 短词回退 LIKE、或外挂搜索引擎）意味着改查询构建方式，不只是加个索引；还需要一份「搜不到」的基线数据来验证不退化 |

## 41. 服务端没有 `WriteTimeout`：读响应很慢的客户端能一直占住连接

| | |
| --- | --- |
| **在哪** | `backend/cmd/api/main.go` 的 `http.Server`：设了 `ReadHeaderTimeout` 5 秒、`ReadTimeout` 5 分钟、`IdleTimeout` 120 秒，**没有** `WriteTimeout` |
| **为什么这么做** | `WriteTimeout` 是「整个响应写完」的上限，而 `GET /download/{slug}` 可以传几百 MiB。慢网下几分钟很正常，设一个数就等于给下载功能加了个随机的失败点——而且失败发生在响应头已经发出去之后，客户端只会看到半截文件，比 500 更难查 |
| **能保证** | 慢读**请求头**的客户端 5 秒被踢；keep-alive 空闲连接 120 秒回收；慢传**请求体**的客户端 5 分钟被踢 |
| **不能保证** | 一个发出请求却始终不读响应的客户端，可以在 goroutine 与文件句柄上停留任意久。打开连接数的上限只剩操作系统 fd 限制与反代的并发配置 |
| **什么时候修** | 部署层有 Nginx 时基本不用管（它会缓冲响应并在 `proxy_write_timeout` 之后断开）。真要修：给下载端点 `hijack` 出裸 TCP 自己控超时，或把下载挪到独立 listener 上单独配 `WriteTimeout` |
| **代价** | 独立 listener 要改部署（两个端口或一个 Unix socket）、改契约里的 base URL，并让所有下载相关测试换 host。收益是「不读响应」这类连接被及时清掉——目前没有证据说明它是瓶颈 |

## 43. 时钟回拨期间 `updated_at` 会停在 `created_at` 上

**现状**：八处写 `demos` 时间字段的语句统一取 `GREATEST(now(), created_at)`（见 [Demo域设计](Demo域设计.md) §3.1「落地状态（2026-11-05）」）。时钟正常时它等于 `now()`；时钟往回拨时它顶在 `created_at` 上。

**能保证**：一条合法操作（裁决、发布、软删、恢复、换版本）不再因为时钟回拨变成 503，`updated_at >= created_at` 永远成立。

**不能保证**：回拨期间 `updated_at` 反映的是「天花板」而不是真实时刻——将来若有「按 `updated_at` 排序或展示最近修改」的界面，那段时间的顺序会偏旧。

**什么时候要修**：真有按 `updated_at` 排序的界面且有人抱怨顺序不对。修法是写入时改取 `clock_timestamp()` 再与 `created_at` 取大——它不解决时钟本身，只是把「天花板」的偏差从整天缩到一次写入。

**代价**：一处 SQL 改动 + 一条测试。


## 44. 模型主数据只有开发用的种子，没有导入与维护手段

**现状**：`models` 与 `vendors` / `providers` 是外部目录表（模型域 §「主数据」），本仓库只提供 `db/seeds/0002-dev-models.sql` 的 6 条 DeepSeek 模型（`status='active'`、`resolution='exact'`），供开发环境与 CI 起步；投稿与详情已经真的在读它（`GET /api/v1/models` 只出 `active`，`demo_revision_models` 记录声明）。

**什么时候修**：真正接入生产模型清单时——那一次要同时做导入（`cmd/models-import` 或一次性脚本）、影响面预览、以及合并的最小流程。

**代价**：做导入就要处理「同名不同厂」「同一模型多个 provider」「名字里的版本号」这些口径问题，不是单纯把 CSV 灌进去。

## 45. 自动化上传没有长期凭据：只有浏览器会话 cookie

**现状**：所有写接口的凭据只有 `__Host-demo_session`（`SameSite=Lax`、`Secure`、绝对上限 30 天，见运行手册第 22 条）。契约的 `securitySchemes` 里没有 Bearer，`clients` 表的 `kind` 只有 `oidc` / `discourse_connect`（身份联邦，不能当 API token）。脚本想上传，只能先走登录接口拿 cookie 再带上——能用，但等于把人类会话塞进脚本。

**能保证**：幂等键、审核态读出、429 的 `Retry-After` 三条**自动化真正需要的能力**已经就位（见 Demo域设计 §7.1 的落地状态）。也就是说「脚本重复上传不产生重复作品」「脚本能问出自己那条审没审过」这两件事现在就能做对。

**不能保证**：
1. **凭据的最小权限与可撤销**：会话 cookie 等于人的全部权限，撤不掉单独一个脚本；也做不到「这个 token 只能投稿，不能删作品」。
2. **长期运行**：30 天要重新登录一次，无人值守的流水线得把密码存在某处——这比存一个可撤销的 token 更糟。

**为什么当时不做**：用户裁决（2026-11-05）是「凭据以后再说」。判据是：凭据是**加法**——将来加 Bearer 不动已有的投稿语义；而幂等键是**减法**——晚接一次，就要回头改所有已经发出去的调用方。所以先做后者。

**什么时候修**：真的有人要跑无人值守的上传流水线时。那时要同时定：token 的权限范围（只 `demo.submit`？）、撤销路径、审计里的主体（`audit_log.actor_id` 现在是账号，token 要不要单独一列）。

**代价**：加一套 PAT 意味着多一条鉴权路径（middleware 分流）、多一张表或多一组列、以及「cookie 与 token 权限不一致」这类长期维护成本。

## 50. 作者自由填的模型名会累积成脏数据，归并全靠人工

## 52. 目录同步失败后按固定 10 分钟重试，不做退避

`SyncIfDue` 在「上一次失败」时按 `retryGap = 10 * time.Minute` 重试，而不是等满一个
`sync_interval_hours`（默认 24 小时）。固定间隔而不是指数退避：

- 上游是公开 CDN，长时间不可达基本等于我们自己的出网坏了，退避到几小时反而更糟。
- 定时器本来就是 5 分钟一跳，10 分钟约等于「隔一跳试一次」，不会打爆上游。

**代价**：上游连续挂一整天，就是 144 次失败请求与 144 行 `error` 覆盖（同一个源只有一行，
只保留最后一次原因，所以不会无限长）。真要更讲究，得记连续失败次数并在第 N 次之后退避；
在那之前固定间隔够用。

## 53. 目录同步只覆盖 models.dev，且 `ModelSyncResult.status` 不是枚举

两件小事一起记，因为它们都是「故意不做得更整齐」的取舍：

- **只覆盖一个来源**。`model_catalog_items` 的 `source` 列本来就是为多来源准备的（唯一键是
  `(source, provider_id, external_id)`），但当前只有 models.dev 一个抓取器。接第二个来源要
  加一个 `catalog.Parser` 实现与一个 `source` 常量，不改表。
- **`ModelSyncResult.status` 在契约里是 `string` 而不是 enum**。写成 enum 会让 oapi-codegen
  把全仓枚举常量改成带类型前缀的形式——只要新枚举的值与既有枚举撞名（这次是 `ok` 与
  `Failed`、`stale` 与 `ErrorCodeStale` 这类），30 多处调用会一起编译失败。取值合法性改由
  `model.StatusOK/StatusStale/StatusFailed` 三个常量兜住，服务端只会写这三个值。

**什么时候修**：接第二个上游时一起处理前者；后者等 oapi-codegen 支持枚举命名空间再说。
**代价**：契约的 `status` 没有取值提示，前端只能靠描述文字知道有哪几种。


## 54. 批量导入没有批次 id，回溯只能逐条翻审计

批量导入（`POST /admin/models/import/apply-batch`）只返回 `results[]`，不产生批次记录。
所以「上周那次导入到底动了哪些模型」这个问题，今天只能靠 `audit_log` 里同一次请求的
`entity_id` 逐条找——而请求本身没有任何标识能把这批行串起来。

**为什么先不做**：批次 id 要新建一张表（或给 `audit_log` 加一列）并在所有单条导入路径上
一起传，等于把一个「查询便利」变成接口契约的一部分。当前导入是运维手工动作、量小，
先记着。

**什么时候修**：出现「按批撤销」或「谁在什么时候灌了这批」这类真实诉求时。
**代价**：无法按批回滚，只能逐条手工处理。


## 55. 分类的 `mode=open` 只描述维度，作者自助新增词条没有实现

`classification_dimensions.mode` 有两个取值 `fixed` / `open`，契约里原本写着
「`open` 允许作者提交新词条待审」。**这条路径不存在**：投稿与更新走的
`resolveClassificationSlugs`（`backend/internal/domain/demo/classifications.go`）
只认库里已有的 slug，作者填一个新词条会直接 400。

`open` 现在只表示一件事：这个维度天然会长尾（`subject` 是「对着什么做的」，
没法预先穷举），记录的是**维度属性**，不是作者权限。录入仍由管理员完成。

**为什么先不做**：自助新增会立刻带来一串必须一起解决的问题——新词条的审核队列、
重名与近义合并（旧站实测同一个 DeepSeek V4 Flash 有五种写法，见第 50 条）、
提交者能不能看到自己那条「待审词条」、驳回之后怎么告知。这些都不便宜，
而当前 `subject` 有 56 条、覆盖了绝大多数投稿。

**什么时候修**：出现「作者想标的东西词表里没有」的真实抱怨时。
**代价**：作者只能从现有词表里挑，长尾题材会被塞进相近条目或干脆不标；
契约描述已同步改成不承诺这件事（2026-11-07）。


## 56. 部署配置没有在真实 nginx / systemd 上跑过

`deploy/` 下的三份配置（nginx 主配置、安全头、systemd 单元）是为了让「空机器能不能跑起来」
这件事有据可查，而不是靠当值的人记得住。但**它们一次都没有被真正加载过**：
开发机上没有 nginx、没有 docker，`nginx -t` 与 `systemctl start` 都没跑过。

| 项 | 值 |
|---|---|
| 现状 | `check-deploy.mjs` 只判结构：四段反代、SPA 回退、上传上限、安全头关键字、单元里的 EnvironmentFile/ExecStart |
| 为什么接受 | 一个人做的项目，先把「配置在仓库里、且不会被整段删掉」这一步做实；真机验证要等有部署机 |
| 风险 | 语法错误、`add_header` 继承、TLS 证书路径、systemd 权限硬化项（`ProtectSystem=strict` + `ReadWritePaths`）都可能一次不对 |
| 什么时候修 | 第一次真机部署时，逐条跑 `docs/部署.md` §7 的验证清单，把踩到的写回那篇文档与本条 |
| 代价 | 修的时候要占一台机器 + 一个域名；没有更便宜的路 |

## 57. 安全响应头只配在 nginx 里，Go 服务自己不发

CSP、`Referrer-Policy`、`Permissions-Policy` 都写在 `deploy/nginx/security-headers.conf` 里。
这意味着：**绕过 nginx 直连 API 的请求没有这些头**（开发时打 127.0.0.1:8080、内网里有人直连、
将来若前面换成别的代理而忘了搬这套头）。

| 项 | 值 |
|---|---|
| 现状 | Go 侧只设与内容相关的头（预览/下载的 `nosniff`、`Content-Disposition`、缓存），不设 CSP 一类站点级策略 |
| 为什么接受 | 只有 nginx 面向前端页面，CSP 的收益在「浏览器加载页面」那一刻，API 的 JSON 响应加不加对风险面影响很小；两边各写一份反而容易漂成两套口径 |
| 风险 | 有人把 API 端口直接暴露到公网时，那台机器上没有这些头 |
| 什么时候修 | 出现「不经过 nginx 的对外入口」时（比如独立 API 域名、给第三方直连的端点）；那时用中间件统一发，并把 nginx 那份删掉 |
| 代价 | 一处中间件 + 一条断言「响应里有 CSP」；不难，只是现在没有第二个入口 |

## 60. 压缩过的 glb 打不开：只内置了播放器，没带解码器

`model-viewer` 遇到**压缩过的** glb（`KHR_draco_mesh_compression`、KTX2 贴图、meshopt）
需要额外的解码器文件，默认会去 `gstatic.com` 拉。我们把播放器本体打进二进制，但没带
这三套解码器——不想让预览在运行时依赖外网，也不愿把几 MB 的解码器塞进仓库。

| 项 | 内容 |
| --- | --- |
| 现在会怎样 | 未压缩的 glb 正常；压缩过的会停在加载中，控制台报取解码器失败 |
| 什么时候会露 | 作者从 Blender 导出时勾了 Draco 压缩（很常见的默认项） |
| 现在靠什么兜 | 暂无提示——这是本条要修的点：要么补解码器，要么在查看页给出「这份模型用了压缩，暂不支持」 |
| 什么时候修 | 第一个真实压缩模型出现时：把 draco / basis / meshopt 三套解码器也放进 `previewassets/`，并在查看页设 `dracoDecoderLocation` 等 tiga 个静态路径 |

## 61. `cmd/migrate` 的模式参数只有一条入口被门禁看着，容器 entrypoint 那条没人跑

`cmd/migrate` 现在有两条调用路径：文档与 `package.json` 里的 `npm run db:*`（人手动跑），
以及 `deploy/docker/entrypoint-api.sh` 里的 `migrate status` / `migrate up`（容器每次启动跑）。
2026-11-12 的那次事故出在人手动跑那条——参数写错被静默忽略。修完之后两条都只认位置参数，
但**只有 `cmd/migrate/main_test.go` 钉住解析规则，容器里那个 entrypoint 没有任何测试或门禁覆盖**：
改坏 `entrypoint-api.sh` 的调用形式，CI 全绿，直到有人第一次 `docker compose up` 才发现。

| 项 | 内容 |
| --- | --- |
| 在哪 | `backend/cmd/migrate/main.go`（参数解析）、`deploy/docker/entrypoint-api.sh`（容器调用）、`scripts/check-docker-deploy.mjs` |
| 能保证 | `parseArgs` 的规则被十三条用例钉住：位置参数与 `-mode` 都认、矛盾报错、无默认模式、选项必须写在模式前、选项解析错误只打印一次、`-h` 写在哪里都算求帮助、`--` 不占模式名额 |
| 不能保证 | `entrypoint-api.sh` 里的调用形式与 `parseArgs` 仍然兼容。`check-docker-deploy` 只核对端口 / 健康依赖 / 数据卷 / 非 root，**不看脚本里怎么调 migrate**；本机也没有 Docker，那条路径一次都没跑过 |
| 什么时候修 | 第一次在真 Docker 环境部署时（松点 56 的同一批验证）；那时把 `docker compose up` 的成功与否变成一条可复查的记录。若想提前加门禁，可在 `check-docker-deploy.mjs` 里断言 entrypoint 中的 `migrate` 调用不带被删掉的写法 |
| 现在靠什么兜 | 无。这是本条要修的点 |
