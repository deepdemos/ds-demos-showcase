# 设置域 · 决策记录

> 源：`docs/设置域设计.md` v1.2 §2「决策摘要」D1–D13。
> 本文件把 13 条决策一条不改地迁进 ADR 格式，**全部为 `proposed`**：等拍板后逐条改 `accepted`。
> 实物锚点：`db/schema/15-settings.sql`（三表 + 18 条注册行）· 标准对象 §EN-9 · 契约中的 settings 端点（本分支尚未合入，见各条「证据」注）。

---

## G23 · 加一张参数注册表：三张表，不是两张

- **状态**：proposed（源自 `设置域设计.md` §2 D1）
- **证据**：`db/schema/15-settings.sql`（`setting_keys`）· `标准对象 §EN-9`
- **决策**：除站点取值与用户偏好两张值表外，加第三张 `setting_keys` 参数注册表，登记键名、作用域、值类型、默认值、是否停用。
- **为什么**：SET-001 的验收是「新增一项参数 = 注册表加一行 + 白名单」——注册表本身就是需求要的东西，不是实现细节。
- **放弃了什么**：两张表 + 代码里的常量白名单（旧栈做法，`tag` / `user` / `setting` 各漏过一次）。
- **影响面**：加参数 = `INSERT` 一行 + 一条迁移，不改表结构、不改接口形状；所有读取路径都必须与注册表连接。
- **回退**：删掉注册表、白名单搬回应用层。代价见 G25。

## G24 · 值用 `jsonb` 一列，不按参数各开一列

- **状态**：proposed（源自 §2 D2）
- **证据**：`db/schema/15-settings.sql`（值表的 `value jsonb` + `jsonb_typeof` CHECK）
- **决策**：两张值表都用一列 `jsonb` 存值，类型由注册表的 `value_type` 声明、由 `CHECK` 校验。
- **为什么**：SET-001 要求「新增一项参数不改接口形状」。每参数一列的话，加参数要 `ALTER TABLE` + 改 DTO + 改前端表单，接口形状一定变。
- **放弃了什么**：每键一列（类型检查免费，但加参数要改表）；用 `text` 存 JSON 字符串（丢掉类型校验）。
- **影响面**：类型检查从列类型挪到 `CHECK`；查询值要强转，索引要按表达式建。
- **回退**：给热键拆出独立列，与 `jsonb` 并存；纯回退（改回每键一列）等于重做两张值表。

## G25 · 白名单由数据库强制，不是应用层判断

- **状态**：proposed（源自 §2 D3）
- **证据**：`db/schema/15-settings.sql`（`uq_setting_keys_type` 复合外键）
- **决策**：两张值表通过 `(key, scope, value_type)` 复合外键指向注册表；未登记或已停用的键，绕过应用层直接写也写不进去。
- **为什么**：SET-010 的验收是「写一个未登记的键被拒」。应用层 `if` 也能过这条验收，但旧栈的三次漏记证明它守不住。
- **放弃了什么**：应用层白名单判断；把键名硬编码进 `CHECK`（加参数就要改约束）。
- **影响面**：注册表成为唯一入口；值行必须带 `value_type`，改类型要同步改值行。
- **回退**：删两条复合外键、白名单搬回 Go。代价是失去数据库级不变量——**那正是本条的全部收益**。

## G26 · `scope` 是常量列，不是普通列

- **状态**：proposed（源自 §2 D4）
- **证据**：`db/schema/15-settings.sql`（两张值表的 `scope` 带 `DEFAULT` 与 `CHECK`）
- **决策**：`site_settings.scope` 恒为 `'site'`、`user_preferences.scope` 恒为 `'user'`，两列只为参与复合外键。
- **为什么**：让「站点参数写进用户偏好表」在数据层面不可能，而不只是「代码里没这么写」。
- **放弃了什么**：一张 `settings` 表带 `scope` 列——少一张表，但没有任何东西阻止写错作用域。
- **影响面**：读路径按表名区分作用域，不读 `scope` 列。
- **回退**：合并成一张表并去掉 `CHECK`。合并后要靠应用层守作用域，与 G25 的收益同时消失。

## G27 · 值表不存默认值、不预置行

- **状态**：proposed（源自 §2 D5）
- **证据**：`db/schema/15-settings.sql`（默认值只在 `setting_keys.default_value`；值表无默认值列）
- **决策**：值行缺失即代表「没被改过」，读取用 `COALESCE(value, default_value)`；建表时不预置任何值行。
- **为什么**：新增参数不需要回填历史行；「管理员改过」与「没改过」在数据上可区分（有行 / 无行）。
- **放弃了什么**：建表时把默认值 `INSERT` 进值表（加参数就要回填，且「改成了默认值」与「没改」不可分）。
- **影响面**：所有读取路径必须与注册表连接，不能单独查值表。
- **回退**：把默认值灌进值表并删掉 `COALESCE`。代价是每次加参数都要回填。

## G28 · 审计粒度 = 每个被改的键一条

- **状态**：proposed（源自 §2 D6）
- **证据**：`audit_log.batch_id`（治理域）· `标准对象 §EN-6`（`setting` 实体类型）
- **决策**：一次写入请求内，每个被改的键各写一条审计，同一请求的行共享 `batch_id`；`before` / `after` 记该键的旧值与新值。
- **为什么**：SET-003 要求「记谁、改了什么、改前改后」——「什么」是**键**。整表快照会让「改了 A」和「改了 B」在审计里长得一样。
- **放弃了什么**：一次请求一条审计 + 整表快照（旧栈做法，无法回答「谁改了这个键」）。
- **影响面**：审计行数随被改键数增长；查询侧要按 `batch_id` 聚合才能还原一次操作。
- **回退**：改成整表快照。历史审计行的可读性会一起下降，且不可追溯。

## G29 · 审计动作写 `update`，不加域前缀

- **状态**：proposed（源自 §2 D7）
- **证据**：`标准对象 §EN-5`（审计动作通则③）· `标准对象 §EN-6`（`setting` 实体类型）
- **决策**：设置写入的审计 `action` 记 `update`，靠 `entity_type = 'setting'` 区分域。
- **为什么**：动作键加域前缀会让 `audit_actions` 膨胀成「动作 × 实体」的笛卡尔积。**需求 SET-003 原文写的是 `setting.update`，与本条冲突——以标准对象为准，需求已同步改。**
- **放弃了什么**：`setting.update` 这类带前缀的动作名。
- **影响面**：审计查询按 `entity_type` 过滤，不按 `action`。
- **回退**：没有回退路径——改了动作名会让历史审计行与新行落在两套词表里。

## G30 · `audit_log` 不加 `entity_key`

- **状态**：proposed（源自 §2 D8；结案治理域 §14 Q17）
- **证据**：`audit_log` 的 DDL（无该列）· `标准对象 §EN-6`
- **决策**：审计表不增加 `entity_key` 列；设置键名放在 `before` / `after` 的快照里。
- **为什么**：唯一会用到 `entity_key` 的是「主键是 text 的实体」。设置的值行有 bigint 代理主键，审计指向值行；键名在快照里已经有了。
- **放弃了什么**：加一列 + 一条 `CHECK`，为一张表加列，只为省一次快照读取。
- **影响面**：审计行自解释依赖快照字段；快照字段缺失时无法从审计反查键名。
- **回退**：加列并回填——**历史行回填不出来**，只能从快照里尽力补。

## G31 · 用户偏好不落审计

- **状态**：proposed（源自 §2 D9）
- **证据**：`user_preferences` 的写路径无审计调用 · `标准对象 §EN-6`
- **决策**：站点参数写审计，用户偏好不写。
- **为什么**：偏好只影响本人可见结果，没有第三方受损；而「浏览历史开关」本身是隐私声明——给它记审计，等于把「我关掉了历史」变成可追溯的操作记录，与 SET-008 的意图相反。
- **放弃了什么**：偏好变更也记审计（旧栈只记站点设置，本域沿用）。
- **影响面**：偏好变更不可事后追溯；出问题只能靠用户自述。
- **回退**：加审计并从此开始记——历史变更同样不可追溯。

## G32 · `healthz` 不读设置表

- **状态**：proposed（源自 §2 D10）
- **证据**：`/healthz` 的实现（无设置查询）· 需求 SET-006
- **决策**：健康检查返回 200 时不带任何配置值，也不查询设置表。
- **为什么**：SET-006 要求「返回 200 时不带任何配置值」。读设置表还会让健康检查依赖设置表可用性——健康检查挂了才知道设置表挂了，是本末倒置。
- **放弃了什么**：健康检查里报告当前配置（会泄露运营参数）。
- **影响面**：运维无法通过健康检查确认「当前生效的是哪套参数」。
- **回退**：改成读设置表。代价是健康检查的可用性降到与设置表同级。

## G33 · 设置变更不触发任何批量回填

- **状态**：proposed（源自 §2 D11）
- **证据**：设置域的写路径（无跨域 `UPDATE` / `INSERT`）· 需求 SET-004
- **决策**：代码里不存在「设置变更 → 批量改历史状态」这条路径。
- **为什么**：SET-004 的验收是「打开自动上架后，已存在的待审作品不会被批量放行」。旧栈也是这么做的，但**没有写成不变量**，所以没人能验证它。
- **放弃了什么**：打开自动上架时把存量待审作品批量放行（用户明确要求不做）。
- **影响面**：改开关只影响后续提交；运营想要「立即生效于存量」时必须另开一次显式操作。
- **回退**：加一条批量路径。它会立刻违反 SET-004，且无法区分「用户改开关」与「用户想批量放行」。

## G34 · 值行永不物理删除

- **状态**：proposed（源自 §2 D12）
- **证据**：`db/schema/15-settings.sql`（值表无 `deleted_at` / `erased_at`）· `标准对象 §ID-5` 通则①
- **决策**：参数退役 = `setting_keys.is_active = false`；值行保留，只有账号级联删除会带走偏好行。
- **为什么**：值行删了，审计里的 `before` / `after` 就指向一个不存在的键。键只增不改，用 `is_active` 停用。
- **放弃了什么**：删值行 / 删注册行（审计失去锚点）。
- **影响面**：值表只增不减；停用键的读取仍返回旧值或默认值。
- **回退**：允许删除。历史审计将不可解，且不可逆。

## G35 · 上限分两类：运营性的进设置，结构性的进运行手册

- **状态**：proposed（源自 §2 D13、§4.1 J1–J6）
- **证据**：`setting_keys` 的 18 条注册行（运营性）· `db/schema/30-demo.sql` 的 `CHECK`（结构性）· `docs/运行手册-可变常量.md`
- **决策**：判据只有一条——**改了要不要迁移 / 要不要重算存量**。不要 → 运营性上限，进设置键，运行时可改；要 → 结构性上限，写进 DDL 的 `CHECK`，在运行手册登记唯一改动点。
- **为什么**：GEN-012 要求「上限只在一处定义」，但一处不等于「都在设置里」。把结构性上限做成运行时配置，等于让管理员一键制造「新数据合法、旧数据非法」的状态——这正是 G33 / SET-004 要防的事。
- **放弃了什么**：所有能改的数都进 `setting_keys`（会让注册表变成「什么都往里塞」的表，且每次调整都要判存量是否要回填）。
- **影响面**：**`docs/标准对象.md` 现在把「上限、保留期」整类推给运行手册，与本条冲突**——两份文件都自称「不重叠」。本条是裁决点：以「要不要迁移」为准，不以「是不是上限」为准。
- **回退**：把一条结构性上限改成运营性：先写迁移把它从 `CHECK` 挪进注册表并回填存量，再把手册那行删掉。顺序不能反。
