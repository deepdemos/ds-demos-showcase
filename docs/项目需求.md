>

>
> - **不是旧站现状记录。** 旧站核对面貌在 [`修订前-v1.0-全站业务需求.md`](ai-fullstack-eval/组织者资料/现站需求核对-20261021/修订前-v1.0-全站业务需求.md)（v1.0 快照，523 条）。它只作为**防漏检查表**用：写完一个域，回头扫一遍它对应的族，确认没漏。它描述的 138 行行为在新站已经改了，照抄会写出一个不存在的系统。

> 「→ 做完」那一行是本文件存在的理由。没有它，实现者（尤其 AI）会自己发明验收标准，然后宣布完成。
>
> **编号**：`<域缩写>-<三位数>`，按域重编，与老稿编号无关。老稿 → 本文件的映射见[附录 A](#附录-a-老稿编号映射)。

## 0. 总则

全局规则。任何域的需求与本节冲突时，以本节为准。

- **GEN-001** 平台**至少**有四类参与者：未登录访客、登录账号、作品作者、管理员。**参与者类型是可扩展的**——业务增长后可能出现新的参与者（如外部 agent、合作方运营），新类型的权限与边界必须先在本节与治理域 §6 登记再实现。同一实体可以同时承担多个角色。
  → 做完：权限判定用的是「当前账号 + 当前权限」，不是「进页面那一刻的身份」。
- **GEN-002** 知道某件作品、收藏夹、通知或管理记录的标识，不等于取得对它的修改权限。
  → 做完：把 id 换成别人的，写操作一律 403/404，不出现「猜到了就能改」。
- **GEN-003** 每次写操作都要按**当前**账号状态判定，不能沿用会话建立时的判定。
  → 做完：封禁一个已登录用户后，他下一次写请求立即 403（不等会话过期）。
- **GEN-004** 实际保存的作者归属、公开显示的署名、管理权限是三个独立的东西，不能合并成一项。
  → 做完：改展示名不影响作品归属；匿名署名不是账号；管理员不具有作品所有权。
- **GEN-005** 无法完成身份确认时，不能把正在浏览公开内容的访客无故带离当前页面。
  → 做完：未登录访问任何公开页，不出现登录墙。
- **GEN-006** 任何入口的同一个业务动作，受同一套规则约束。不允许「这个页面查得严、那个接口查得松」。
  → 做完：同一动作在 REST 与表单两条路径上的校验、限流、审计结果一致。
- **GEN-007** 未实现的能力不得作为既有承诺出现在**产品界面**的任何文案里。
  → 做完：站点文案里找不到「即将上线」「敬请期待」这类对未实现功能的陈述。
- **GEN-008** 失败、部分成功、并发冲突必须分开表达。系统不得把没有执行的动作用成功样式返回。
  → 做完：批量操作里有一条失败时，返回体里能逐个看到成功/失败，不是笼统 200。
- **GEN-009** 关联动作失败、重复提交或并发修改时，结果之间必须能相互对照，不能出现两个互相矛盾的响应。
  → 做完：同一作品并发两次编辑，后提交的得到 409 而不是静默覆盖。
- **GEN-010** 所有统计（浏览、下载、评分、访问）允许有延迟，但必须说明「这是延迟数」还是「准确数」。
  → 做完：页面上凡是延迟统计都有一句口径说明，或者干脆不展示。
- **GEN-011** 内容接收一律视为不可信：限制类型、大小、条目数；预览在 iframe 内运行，默认不给 `allow-same-origin`。
  → 做完：上传一个带 `<script>alert(1)</script>` 的 HTML，预览时不弹出；同时**隔离不能以牺牲作品正常功能为代价**——正常作品在收紧后的沙箱里仍能完整运行。
- **GEN-012** 文字、集合、资源的长度与数量上限**分两类，各自只在一处定义**：
  ① **运营性上限**（上传体积、容量、保留期、限流阈值这类「运营想调就能调」的）登记在 `db/schema/15-settings.sql` 的 `setting_keys`，运行时可改，见 [`设置域设计`](设置域设计.md) §4；
  ② **结构性上限**（改了要加 migration、或者旧数据要重判的，如 username 长度、封面内联字节、分类树深度）登记在 [`运行手册-可变常量.md`](运行手册-可变常量.md)。
  页面与接口都从这两处取，不在代码里写死第二份。**分界线**：改了会不会让历史数据自相矛盾——会，就是结构性；不会，就是运营性。
  → 做完：改一个运营性上限只改 `setting_keys` 一行，所有入口同步变化；跑 `node scripts/check-constants.mjs` 能确认每个结构性上限都还在手册里登记着。
- **GEN-013** 对未来的规划只能写在 `docs/未来展望.md`，并逐条标注「规划中，不承诺」；产品界面不得把它当作功能入口或既定能力展示。
  → 做完：`docs/未来展望.md` 里每一条都带「规划中，不承诺」；站点里没有任何一处指向它的功能入口。

## 1. 身份域

**归属**：账号是什么、怎么登录、资料怎么改、账号状态怎么变、注销时数据怎么扩散。
**不归属**：谁能做什么（治理域权限）、作品归属谁（Demo 域）、等级怎么涨（成长/积分域）。
**表**：`accounts` / `profiles` / `auth_events` / `web_sessions` / `clients` / `consents`（见 `db/schema/10-identity.sql`）。
**依赖**：无。被治理域、Demo 域、所有域依赖。

### 1.1 注册与登录

- **IDN-001** 用户能注册账号，提供用户名与密码；已占用的用户名不能再次注册。
  → 做完：重复注册返回 409 且提示「用户名已被占用」，不是 500。
- **IDN-002** 无效输入（长度、字符集）必须说明是哪一条规则不满足。
  → 做完：返回体带字段名 + 规则名，不是笼统「输入有误」。
- **IDN-003** 正确凭据能登录；错误凭据、已注销、已封禁的账号都不能取得有效操作权限。
  → 做完：三种失败返回不同的错误码，且都不返回会话凭证。
- **IDN-004** 用户能看到自己的当前登录状态，刷新后保持有效身份，能主动退出当前环境。
  → 做完：点退出后再访问需要登录的页面，跳转登录页。
- **IDN-005** 同一账号名或同一网络登录失败过频时受限。默认阈值：5 分钟内同账号名 30 次、同网络 60 次。**这两个数值是 `site_settings` 里的可配置项**，不在代码里写死。
  → 做完：5 分钟内同账号名失败 30 次后返回 429；把 `site_settings` 里的阈值调小，行为立刻跟着变。
- **IDN-006** `username`（登录名，不可改）与 `display_name`（展示名，可改）是两个字段，不能混用。
  → 做完：改展示名不改变登录名；作品页显示的始终是展示名。
- **IDN-007** 旧用户名永不释放。即使用户改名，那个登录名也不能被他人注册。
  → 做完：改名后原登录名再注册返回 409。

### 1.2 资料与头像

- **IDN-008** 用户能改自己的展示名、简介、头像；清空头像后账号信息仍可识别。
  → 做完：清空头像后回退到默认图，不出现破图。
- **IDN-009** 头像必须公开可读（不带鉴权即可取），否则他人列表里会全是破图。
  → 做完：未登录 GET 头像 URL 返回 200。
- **IDN-010** 资料文字的长度与格式上限见第 0 章 GEN-012，不在页面里写死。
  → 做完：改 `标准对象` 里的上限，页面提示同步变化。

### 1.3 密码与凭据

- **IDN-011** 用户提供原密码才能改密码；原密码不正确时改不成。
  → 做完：错原密码返回 403，且密码未变。
- **IDN-012** 改密码下限 10 位，不强制大小写数字符号组合；与用户名/邮箱过于相似的口令拒绝。
  → 做完：`Passw0rd!` 通过，`username123` 被拒。
- **IDN-013** 改密码后新密码能登录，旧密码不能。已存在会话是否立即失效见 [LIFE-014](#7-生命周期域)。
  → 做完：改密后用旧密码登录返回 401，新密码能登录。

### 1.4 账号状态与注销

- **IDN-014** 账号状态只有五个：`active` / `suspended` / `banned` / `deleted` / `pending`（完整取值与迁移见 `标准对象 §ST-1`）。
  → 做完：`accounts.status` 的 CHECK 与 `标准对象/10-状态与档位.md` 逐值对齐。
- **IDN-015** 每次状态变更记 `previous_status` 与原因，能回答「这个账号上次为什么被封」。
  → 做完：`accounts` 有 `previous_status` / `status_reason` 列；审计里有对应 `account.status.change`。
- **IDN-016** 用户能注销自己的账号。注销后账号行永久保留（不物理删除），内容列匿名化。
  → 做完：注销后 `accounts.status='deleted'`，`display_name` 被替换成匿名形式，行还在。
- **IDN-017** **封禁用户不能自助注销**。封禁意味着处置尚未结束，自助注销会把处置对象从视野里抹掉。
  → 做完：`banned` 账号调注销接口返回 403，提示「请先联系管理员」。
- **IDN-018** 注销后邮箱只留 HMAC 指纹，不留明文；指纹用于防止同邮箱重复注册。
  → 做完：注销后 `accounts.email IS NULL`、`email_hmac` 有值；同邮箱再注册被拒。
- **IDN-019** 管理员可以代**被封禁**用户执行注销。代注销与自助注销走同一条数据路径（同 IDN-016），但审计必须分别记录「谁执行的」与「注销的是谁」。
  → 做完：管理员代注销后 `accounts.status='deleted'`；`audit_log` 里执行者是管理员、目标是该账号，两者可分别查询。

## 2. Demo 域（作品）

**归属**：作品本体、版本快照、文件清单、渠道发布、评分、统计、slug 永久性、下架与墓碑。
**不归属**：作品属于哪个题目/提示词（实体域）、模型归属（模型域）、分类打标（标签域）、谁能审（治理域）。
**表**：`demos` / `demo_revisions` / `demo_revision_files` / `blobs` / `demo_channels` / `demo_stats` / `demo_ratings` / `demo_timeline` / `demo_slug_history` / `demo_task_overrides` / `demo_capabilities` / `demo_grants`（见 `db/schema/30-demo.sql`）。
**依赖**：身份域（作者）、治理域（审核态）、标签域 / 模型域 / 实体域（revision 级关联）。

### 2.1 接收与发布

- **DEMO-001** 平台接收四类作品：网页（`web`）、文件包（`zip`）、外部链接（`link`）、图像（`image`）。**类型清单是可扩展的**，落在主数据表 `demo_types` 里，`demo_revisions.demo_type` 是指向它的外键——新增一种类型是插一行，不是改 CHECK、不是改代码分支。
  → 做完：`demo_types` 有这四行；`demo_revisions.demo_type` 是外键而非 CHECK；插第五种类型不需要改任何 CHECK。
- **DEMO-002** 单 HTML、单 SVG、多文件网页包都能正确体验；包内相对路径、样式、脚本、图片、字体不因托管而失效。
  → 做完：上传一个带相对路径资源的多文件包，站内预览无 404。
- **DEMO-003** 文件包默认限制：单包 `demo.upload_package_mib`（默认 200 MiB）、累计解压 `demo.upload_extracted_mib`（默认 500 MiB）——**这两个是运营性上限，值在 [`设置域设计`](设置域设计.md) §4，不在代码里**；解压比超过 4 MiB 后不超 100 倍、成员数 2000 是**安全下限**，登记在 [`运行手册-可变常量.md`](运行手册-可变常量.md) §3，不开放给运营改。**超限时不是硬拒绝，而是转入管理员审批**——提交成功但停在待审批，作品不直接上线。
  → 做完：传一个超限的包，提交成功、状态为待审批、返回体写明是哪条超限。
- **DEMO-004** 图像作品兼作封面。下载的是展示用 WebP，最长边 1280，不承诺提供上传原件。
  → 做完：传一张 4000×3000 PNG，详情页展示 WebP，下载得到 1280 长边的 WebP。
- **DEMO-005** 封面限制 `demo.cover_max_megapixels`（默认 40，即 4000 万像素；见 [`设置域设计`](设置域设计.md) §4）；超限拒绝并说明。
  → 做完：把该键调成 10，再传一张 4000 万像素的图，返回 422 并写明上限 10。
- **DEMO-006** 未提供的附加信息留空或者标注缺失，不自动编造提示词、生成日志、制作耗时。
  → 做完：只上传 HTML 的作品，详情页提示词区域显示「未提供」而不是空白或占位文本。
- **DEMO-007** 提交时可声明：模型（可多个，标注「包含此模型」）、平台与配置、技能与 MCP、题目、提示词、生成轮数/耗时、不确定性说明。
  → 做完：这些字段都落库到 revision 级关联表，能在详情页与历史版本页读到。
- **DEMO-008** 同一作品用了多个模型时，文案是「包含此模型」，不作为「某模型独立完成」的证据。
  → 做完：详情页模型区不出现「由 X 完成」的措辞。
- **DEMO-009** 草稿能保存文字与选择；草稿不能假装恢复了已经不存在的文件。
  → 做完：清掉文件后再进草稿，提示「需要重新选择文件」。
- **DEMO-010** 编辑已有作品与新建作品的草稿分开，不能恢复成对错误作品的修改。
  → 做完：先编辑作品 A 存草稿，再打开作品 B，B 的草稿页不出现 A 的内容。
- **DEMO-011** 草稿保存失败不能阻止正常提交。
  → 做完：把草稿接口打成 500，正式提交仍然成功。
- **DEMO-012** 提交失败时保留已填内容，刷新不丢。
  → 做完：提交时断网，重开页面仍能看到已填字段。
- **DEMO-013** 重复提交检测：同一份内容重复提交，给出提示而不是产生两件作品。
  → 做完：同一份内容连点两次提交，作品数仍为 1，第二次返回提示而非新记录。

### 2.2 版本与更新

- **DEMO-014** `DemoRevision` 一旦创建不可修改，编辑产生新的 revision，`rev_no` 从 1 连续递增，不跳号不复用。
  → 做完：连续编辑三次，`rev_no` 是 1/2/3；对已有 revision 做 UPDATE 被数据库拒绝。
- **DEMO-015** 每次编辑可以写更新说明；时间线上能分辨「创建」与「后续更新」。
  → 做完：`demo_timeline` 有对应行，详情页时间线能看出先后与说明。
- **DEMO-016** 作者能选择保留旧版本；旧版与当前版有可识别关系，能从更新过程追溯。
  → 做完：保留旧版后有直达旧版 rev 的入口，旧版内容与当前版不串。
- **DEMO-017** 提交非法新包时拒绝更新，此前可用的作品内容不受影响。
  → 做完：传一个损坏的 zip 更新，返回 400，旧版仍能正常体验。
- **DEMO-018** 作品更新后，体验、下载、评分都取到一致的有效版本。
  → 做完：把作品更新到第 2 版后，体验、下载、评分三处显示的版本一致。
- **DEMO-019** 普通浏览与评分不得被当成「修改了作品内容」而产生新版本。
  → 做完：看十次、评一次分，`rev_no` 不变。
- **DEMO-020** 改名 → 写 `demo_slug_history` 并 301 到新地址；旧 slug 永久唯一，永远不释放。
  → 做完：改 slug 后旧地址 301，且新作品不能用旧 slug。

### 2.3 下架、删除与墓碑

- **DEMO-021** 审核态只有三个：`pending` / `approved` / `rejected`。全局一次，不由作者自己通过。
  → 做完：`demos.moderation_state` 的 CHECK 是这三值；`moderation_state` 在数据层没有「自动通过」这个值——自动放行是**行为逻辑**（SET-001 的站点参数决定提交后落 `approved` 还是 `pending`），不是表里多一个状态。
- **DEMO-022** 生命周期态：`draft` / `published` / `archived` / `removed`。作者能 `archived`；**管理员既能 `archived` 也能 `removed`**（`archived` 不是作者专属动作）。
  → 做完：作者调归档成功、调移除 403；管理员两个动作都成功。
- **DEMO-023** 归档与移除在数据上完全一样：行在、字段在、文件在，对外 **HTTP 200 + 墓碑页**。差别只有谁触发、能不能申诉。**所有「曾经公开过」的内容被删除或归档，对外都是墓碑页（200），不是 404**——这是全站统一口径，判据见 LIFE-008。
  → 做完：两种状态下直访 slug 都是 200，页面显示墓碑文案。
- **DEMO-024** 删除（软删）后不再提供该作品内容，对外返回**墓碑页（200）**而不是 404（曾经公开过，见 LIFE-008）；作者与管理员的删除权按实际归属判定，知道入口不等于能删。
  → 做完：软删后他人访问得到 200 + 墓碑页；作者访问能看到「已删除」状态。
- **DEMO-025** 删除作品后，相关收藏、浏览历史、分类/模型/题目关系按删除事实清理或失去有效引用，不因关联关系而失败。
  → 做完：删一件被 20 人收藏的作品，返回 200，不返回外键错误。
- **DEMO-026** 删除后仍须能辨别目标已不存在；已存在的申请或管理记录不能被改写成另一件作品的记录。
  → 做完：删掉作品后它的审核记录仍指向原 id，读出来显示「目标已删除」。
- **DEMO-027** 内容行永不物理删除。代码里不出现 `DELETE FROM demos` / `DELETE FROM demo_revisions`。
  → 做完：全仓 grep `DELETE FROM demos` 零命中；GC 只删派生物与 `demo_revision_files` 子行。
- **DEMO-028** 归档/移除的作品不出现在任何公开列表、搜索、榜单、计数里。
  → 做完：归档一件作品，列表总数减一，搜索不到。

### 2.4 体验与预览

- **DEMO-029** 网页作品能在站内体验，能进入专门的体验态，减少站点操作对作品的干扰。

- **DEMO-031** 作品需要的键盘鼠标操作有效；站点快捷键不能截获作品输入。
  → 做完：在预览态按站点快捷键（如 `/` 聚焦搜索）不触发。
- **DEMO-032** 需要鼠标锁定/指针锁定的作品能用其能力，用户也能退出该状态。

- **DEMO-034** 刷新后作品能按自身逻辑读到它自己存的进度；平台不承诺替作品加跨设备同步。
  → 做完：作品写入 localStorage 后刷新能自己读回；换设备读不到（平台不补）。
- **DEMO-035** 「加载中 / 已加载 / 疑似失败」分开表达；显示「已加载」不能伪造作品可运行。

- **DEMO-036** 第三方资源失效、原始作品损坏、平台资源提供失败三种原因分别表达，不凭空补功能。

- **DEMO-037** 移动设备能按作品支持的方式进入与退出；作品只支持键盘时说明操作条件。
  → 做完：手机上能进入与退出；只支持键盘的作品在手机上说明「需要键盘」。

## 3. 标签与分类域

**归属**：描述作品的分类项（类型、玩法、类别等）、生成环境（平台 / 平台配置 / 技能 / MCP）、分类维度元数据。
**不归属**：模型归属（模型域）、题目归属（实体域）、谁能改词表（治理域权限）。
**表**：`classifications` / `demo_classifications` / `platforms` / `platform_configs` / `mcp_servers` / `skills` / `classification_dimensions`（见 `db/schema/50-classification.sql`）。
**依赖**：Demo 域（revision 级打标）、模型域（`platform` 的厂商关联）。
**注**：旧站的 `tags` / `tag_keys` / `demo_tags` 三张表**退役删除**，不是迁移。旧标签语义按 `docs/标签域数据结构设计.md` §6.5 阶段④ 落位。

### 3.1 取值形态

- **TAG-001** 分类项按维度组织，每项有名称、说明、重要程度、可选的父项、可选的分组与适用状态。
  → 做完：`classifications` 有 `dimension_id` / `name` / `description` / `weight` / `parent_id` / `group_name` / `status`。
- **TAG-002** 维度分三种取值形态：**预登记**（只能选已有值）、**自由值**（用户可填，仍受文字规则约束）、**整数**（只接受合法整数）。
  → 做完：`classification_dimensions.value_mode` 的 CHECK 是这三个值；对一个整数维度提交 `"abc"` 被拒。
- **TAG-003** 预登记维度缺值要走申请（提案），**不能绕过管理把任意字符串变成正式值**。

- **TAG-004** 平台是预登记维度，**不自动建值**。旧站 open 模式会自动建，新站不这么做——否则会造出一堆没有厂商和描述的空详情页。
  → 做完：提交一个不存在的 `platform` 值，返回 422 或生成 `new_platform` 提案，`classifications` 不新增行。

### 3.2 打标与展示

- **TAG-005** 打标写在 revision 级：每个版本描述自己的分类，历史版本可追溯。
  → 做完：`demo_classifications` 有 `revision_id`；改分类产生新 revision 而不是改旧行。
- **TAG-006** 同一作品同一维度不因重复关联同一值而多计数。
  → 做完：对同一 `(revision_id, classification_id)` 重复写入，计数仍是 1。
- **TAG-007** 分类项可查看上级、下级与对应作品集合；组合查找不丢失标签语义。
  → 做完：点分类项能列出上下级与作品；按它筛选的结果与该项语义一致。
- **TAG-008** 已退役的值有明确状态，不能作为新发布候选；已有历史作品的相关信息仍可解释。
  → 做完：退役一个值后，发布页不再出现它；已有作品的详情页仍显示它并标注「已退役」。

### 3.3 平台、配置与技能

- **TAG-009** 平台（如 DeepSeek 官网、Cherry Studio）、平台配置（插件 / 预设）、技能、MCP 服务器是**四个独立维度**，不能混成一个轴。
  → 做完：`platforms` / `platform_configs` / `skills` / `mcp_servers` 是四张表，四个外键。
- **TAG-010** 平台配置与技能挂在平台上：一个配置属于一个平台，跨平台的技能可以复用。
  → 做完：`platform_configs.platform_id` 非空；`skills` 可被多个平台引用。

### 3.4 治理动作

- **TAG-011** 同一维度内取值唯一，不能建完全重复的值。
  → 做完：同名同维度第二次创建返回 409。
- **TAG-012** 父项必须存在且同维度，层级不能成环。
  → 做完：把 A 的父设成它的孙子，返回 400。
- **TAG-013** 合并**分类项**（不是合并作品）：先把源项的作品关联迁到目标，再**软删源项**（`status='deprecated'` + `merged_into_id`）。旧站是物理删，新站不是。作品之间的合并是另一回事，不在本域。
  → 做完：合并后源项行还在、`merged_into_id` 指向目标、它的作品能通过目标查到；作品行本身零变化。
- **TAG-014** 合并只允许同维度、有效源到有效目标；不支持跨维度合并、不支持带子项的源合并。
  → 做完：跨维度合并返回 422 并说明原因。**为什么不许跨维度**：维度是不同的语义轴（类型 vs 玩法），跨轴合并会让「按类型筛」和「按玩法筛」得到同一批结果，词的语义就塌了。**为什么不许带子项**：源项的子项要先单独决定迁到哪，否则合并会把子树整片挂到不相干的父项下。
- **TAG-015** 删除分类项前判断引用：有作品引用、有子项、有跨维度历史引用时拒绝并说明影响。
  → 做完：删除有作品引用的分类项返回 422 并列出引用数。
- **TAG-016** 词表变更后，发布页可选值与已有作品展示必须相互对应。
  → 做完：改完一个值的名称，发布页与详情页同时是新名称。

### 4.2 作品与模型的关联

- **MODEL-007** 模型关联的唯一事实源是 revision 级 `demo_revision_models`；`demo_models` 是只读视图。
  → 做完：往 `demo_models` 写入失败；读出来的内容随 revision 变化。
- **MODEL-008** 作品可以声明多个参与模型，各模型档案分别体现有效关联，单模型内不重复计作品。
  → 做完：一件声明两个模型的作品，在 A 与 B 两个档案里各算 1，不重复。
- **MODEL-009** 展示时文案是「包含此模型」，不作为「某模型独立完成」的证据。
  → 做完：全站文案里找不到「某模型生成」这类断言。
- **MODEL-010** `match_status='matched'` ⇔ `model_id IS NOT NULL`，这条等价必须由数据库约束保证。
  → 做完：写一条 `matched` 但 `model_id` 为空的记录，被约束拒绝。
- **MODEL-011** 任何业务逻辑不得从旧的 `model:` 标签反推关联。
  → 做完：删掉所有标签数据后，模型关联不丢。

### 4.3 统计与排序

- **MODEL-012** 模型统计只使用其关联的**已公开**作品；退役、合并、重新归属后统计反映有效关系。
  → 做完：把一件作品归档，模型档案的作品数减 1。
- **MODEL-013** 展示均分、社区分、有效票数、样本等级时必须说明各自含义，不能把不同指标混用。
  → 做完：页面上每个数字带一句口径说明，或指向口径说明。
- **MODEL-014** 模型社区分 = `(S + m × C) ÷ (v + m)`，保留两位小数。`v` 有效票数、`S` 分数总和、`C` 票数加权的整体均分、`m` 各有评分模型有效票数的中位数且不小于 1。
  → 做完：用固定输入算出的结果与公式一致（写成一个可跑的测试）。
- **MODEL-015** 样本等级按有效票数：0 票无样本 / 1–9 低 / 10–49 中 / 50+ 较高。样本等级**不等同**型号确认程度。
  → 做完：一个 `active` 模型可以是「无样本」；一个 `candidate` 模型可以是「较高」。
- **MODEL-016** 无评分证据的模型显示「无评分」，不以 0 分或整体先验分冒充自身得分。
  → 做完：零票模型的社区分栏显示「无评分」而不是 0.00。
- **MODEL-017** 社区分相同时优先比有效票数；排序不能依赖用户看不到的额外精度。
  → 做完：两个显示 4.50 的模型，票数多的排前面。

### 4.4 第三方基准

- **MODEL-018** 第三方基准是**新站新增**（旧站与需求稿都没有）。它展示综合分与单榜名次，与站内社区分**分开取数、分开口径说明，不合并成一个总分**。**第三方基准有独立的页面**：用户能在一个页面查看本站收录的全部第三方基准，并从该页面跳转到对应基准的详情。
  → 做完：模型页三个区块（档案 / 站内表现 / 第三方基准）分别取数，页面上不出现「总分」；另有独立页面列出全部已收录基准，每项可点进详情。
- **MODEL-019** 每个 `benchmark_version` 至多一个主榜（`is_primary=true`）。
  → 做完：插第二个 primary 被唯一索引拒绝。
- **MODEL-020** `coverage='partial'` 或 `source_type='self_reported'` 的版本不进入综合分。
  → 做完：构造一个 partial 版本，综合分不变。
- **MODEL-021** 综合分用去头去尾均值，并把偏离用 MAD 标成强/弱。
  → 做完：同一批分数，去掉最高最低后算 mean，与实现一致。

**依赖**：Demo 域（revision 级挂题）、治理域（提案审核权限）。

### 5.1 题目与层级

- **ENT-001** 题目支持**三级**层级（不是两级）：用户能看上级、下级与对应作品集合。
  → 做完：`tasks` 有 `parent_id`；三层嵌套能建、第四层被拒。
- **ENT-002** 同一用户不能建两个同名待审题目；同名有效题目存在时，引导转入已有题目而不是新建。
  → 做完：重复提交同名 → 返回已有题目 id + 提示。
- **ENT-003** 题名去重按归一化后的键（`title_key`），大小写、全半角、空白的差异视为同名。
  → 做完：`"画一只猫"` 与 `"画一只猫 "` 命中同一条。
- **ENT-004** 题目名可改，`tasks.slug` 不可变；改 slug 写 `task_slug_history`。
  → 做完：改题名后旧 URL 仍能到新题名；`tasks.slug` 不变。
- **ENT-005** `Task.status` 只有三个值：`active` / `merged` / `hidden`。旧站的 `candidate` 是死状态（从未写入过），**不迁移**。
  → 做完：CHECK 是这三值；全仓找不到往 `status` 写 `candidate` 的代码。
- **ENT-006** 题目能合并：源题的作品与提示词迁到目标，源题标 `merged` 并记 `merged_into_id`；不能合并到自己、已合并项或形成环。
  → 做完：合并后源题状态为 `merged` 且 `merged_into_id` 指向目标；合并到自己返回 422。
- **ENT-007** 删除题目（`hidden`）前判断引用；**题目本身永不物理删除**，删改靠状态与合并。
  → 做完：代码里没有 `tasks` 的 DELETE；隐藏后题目仍能按 id 查到。

### 5.2 提示词

- **ENT-008** 提示词正文不可变：同样的正文只存一份，收录是另一回事。
  → 做完：`prompts` 按内容哈希去重；改正文等于新建一条。
- **ENT-009** 提示词支持模糊搜索（`pg_trgm`），中文可搜。
  → 做完：搜一个中文片段能命中；索引 `ix_prompts_content_trgm` 存在。
- **ENT-010** 提示词能归到题目（`task_prompts`），也能被收录进提示词库（`prompt_library_entries`）；两者独立。
  → 做完：取消归类不删除提示词本身；取消收录不影响题目归类。
- **ENT-011** 一个提示词可归到多个题目；一个题目可有多个提示词。
  → 做完：一个提示词挂两个题目时，两个题目页都能查到它。
- **ENT-012** 作品通过 `demo_revisions.prompt_id` **弱引用**提示词：提示词不存在时作品仍然可读。
  → 做完：删掉一个没被收录的提示词（或置不可见），作品详情页仍 200，提示词区域显示「已不可用」。

### 5.3 作品挂题

- **ENT-013** `demo_tasks` 是**视图**不是表：它由 `demos.current_revision_id → demo_revisions.prompt_id → task_prompts.prompt_id` 推导。
  → 做完：全仓没有 `CREATE TABLE demo_tasks`；往视图写入失败。
- **ENT-014** 冷门情况下管理员可以覆盖某件作品的题目归属，覆盖记在 `demo_task_overrides`，不改 revision。
  → 做完：覆盖后作品出现在新题目下；作者编辑作品其他字段不会把覆盖冲掉。
- **ENT-015** 作者编辑作品时不能被"退回"到管理员已确认的归属。
  → 做完：管理员确认归属后作者再编辑作品，`demo_tasks` 关联不变。

### 5.4 提案（候选）

- **ENT-016** 提案是旧站「候选收件箱」的正式化。`kind` 覆盖：新模型、模型别名、模型合并、新题目、作品挂题、题目合并、类型调整（+ 半开放实体的提案）。
  → 做完：`proposals.kind` 的 CHECK 列出了全部 kind；每种都能创建并通过。
- **ENT-017** 提案的 `kind` 扩展走注册表，加一种新提案不改表结构。
  → 做完：新增一个 kind 只需在注册表加一行 + 注册 handler。
- **ENT-018** 同一未处理候选的重复产生要**去重**：同一目标、同一来源、同一 payload 不产生第二条。
  → 做完：连点两次提交，`proposals` 只有一行。
- **ENT-019** 提案来源可区分：规则推导 / 用户申请 / 其他来源。
  → 做完：三类来源在提案列表里能分别筛选出来。
- **ENT-020** 提案是**预览**：创建提案不改变任何正式业务数据；只有通过时才写。
  → 做完：创建一个"新模型"提案后，`models` 表零变化。
- **ENT-021** 通过提案时目标对象可能已经存在或已改变：通过动作要能处理「目标已存在」「目标已被合并」两种情况。
  → 做完：两条提案指向同一新模型，第二条通过时提示复用而不是报 500。
- **ENT-022** 提案可以批量处理，待办概况能按 kind 统计。
  → 做完：勾选多条提案一次通过，返回逐条结果；待办概况的 kind 计数与实际一致。
- **ENT-023** 提案被拒要记原因（`reject_reason` 可选），拒绝后不产生正式值、不产生虚假关联。
  → 做完：拒绝一条提案后，对应业务表没有新增行。
- **ENT-024** 目标被合并时，指向它的未处理提案标 `superseded`，不是静默指向新目标。
  → 做完：合并题目后，指向旧题的待处理提案状态变为 `superseded`。

## 6. 治理域

**归属**：角色与权限、审核队列与裁决、审计日志、账号状态管理入口、危险动作的自保护。
**不归属**：论坛治理（论坛外置，见 FRM）、设置项（设置域）、内容本体（各内容域）。
**表**：`roles` / `permissions` / `role_permissions` / `account_roles` / `audit_actions` / `audit_entity_types` / `audit_log` / `gc_queue` / `review_kinds`（见 `db/schema/20-governance.sql`）。
**依赖**：所有域。这是唯一一个"被所有域依赖"的域。

### 6.1 角色与权限

- **GOV-001** 权限模型是三张表 + 账号挂角色，**不是**在账号上存 `role` 枚举。
  → 做完：`accounts` 没有 `role` 列；`role_permissions` 决定谁能做什么。
- **GOV-002** 权限键粒度是「域.动作」，当前 19 个（不是旧站的 2 档 user/admin）。**权限键集合是可扩展的**，加一个权限是往 `permissions` 插一行 + 在代码里声明依赖它的检查点，不是改权限判定逻辑。
  → 做完：`permissions` 有 19 行，键名形如 `demo.moderate` / `account.manage`；新增一个权限键不改判定代码。
- **GOV-003** **未设计域的权限不预先占位**：`announcement.write` 已移除，等策展与运营域落地时随 migration INSERT。`setting.write` 在设置域落地时一并加入（见 SET-005；v1.14 已落地）。
  → 做完：`permissions` 里当前查不到 `announcement.write`。
- **GOV-004** 判定链是：账号 → 角色 → 权限键。不允许在代码里硬编码「是不是管理员」。
  → 做完：全仓 grep 不到 `role == "admin"` 这类判断。
- **GOV-005** 权限变更后立即生效：下一次请求就按新权限判定。
  → 做完：撤掉某人的权限后，他下一个请求立即 403。

### 6.2 审核

- **GOV-006** 所有审核队列统一成一套契约：`POST /admin/reviews/{kind}/{id}` + `review_kinds` 注册表。旧站是四张表、四个入口、四种动作名。
  → 做完：加一个队列 = `review_kinds` INSERT 一行 + 注册 handler，不改路由结构。
- **GOV-007** 审核动作只有三个：通过 / 驳回 / 撤回（附原因）。裁决结果写进目标表的 `moderation_state`，不另建一张"审核结果表"。
  → 做完：一条待审内容只有通过/驳回/撤回三个出口；没有独立的审核结果表。
- **GOV-008** 同一份内容不能同时出现在两个队列。
  → 做完：同一内容不会在两个队列里同时出现。
- **GOV-009** 审核要记：谁审的、什么时候、针对什么、结果、原因。这些进 `audit_log`。
  → 做完：每次审核在 `audit_log` 里有一行，含 actor、时间、目标、结果、原因。
- **GOV-010** 批量审核要么全成要么逐条报告，不出现「以为批量成功实际部分失败」。
  → 做完：批量十条里第三条会失败时，返回体逐条标注，不是笼统 200。

### 6.3 账号管理

- **GOV-011** 账号状态变更**只有一个入口**。旧站的通用 `PATCH /users` 被废掉，因为它允许把状态改成任意值、绕过自保护。
  → 做完：全仓没有 `PATCH /users` 这个路由。
- **GOV-012** 自保护：不能封禁自己、不能降级自己、不能让系统里没有 `admin` 角色。
  → 做完：最后一个持有 `admin` 的账号尝试注销或被降级，被拒绝并说明原因。
- **GOV-013** 状态变更必填原因，并记 `previous_status`。
  → 做完：不填原因改状态返回 422；改状态后 `previous_status` 有值。
- **GOV-014** 危险动作（封禁、删除账号、清空内容）要二次确认，确认动作本身也进审计。
  → 做完：封禁请求缺少确认标志时返回 422；确认动作本身在 `audit_log` 里有一行。

### 6.4 审计

- **GOV-015** 审计只有**一个写入口**：`audit_log` 只能由审计服务写，其他代码不得直接 INSERT。
  → 做完：全仓 grep `INSERT INTO audit_log` 只出现在一处。
- **GOV-016** 审计动作与实体类型是**目录表 + 外键**，不是 Python/TS 常量。旧站的白名单是常量且注释自认漏过 4 次。
  → 做完：写一个未登记的动作，被外键拒绝。
- **GOV-017** 白名单随响应返回，前端不需要硬编码。
  → 做完：前端不写死动作白名单，从接口取。
- **GOV-018** 记什么：所有写操作、状态变更、权限变更、审核裁决、擦除与清空。**不记**：读操作（含管理台列表、审计查询本身）。
  → 做完：查十次列表，`audit_log` 零新增。
- **GOV-019** 审计检索支持按对象类型、对象、动作、reason 关键词筛选；能看人员与时间但**没有**独立的人员/时间范围筛选（旧站也是如此）。
  → 做完：按对象类型 + 动作筛选能得到结果；页面上没有人员下拉框。
- **GOV-020** 审计行永不物理删除，也不随目标内容擦除而消失（只把可识别的个人信息剥离）。
  → 做完：擦除一条被审计过的内容后，`audit_log` 行仍在，可识别的个人信息已剥离。

## 7. 生命周期域

**归属**：数据维度（行 / 字段 / 文件）× 可见性维度（公开 / 墓碑 / 仅作者 / 无人）的六格；注销；擦除；GC 队列。
**不归属**：谁能擦除（治理域权限）、内容本身（各内容域）。
**表**：`gc_queue`（治理域 schema 内）、各内容表的 `deleted_at` / `erased_at` / `purge_after` 列。
**依赖**：所有内容域。每个内容域必须实现本节 §7.2 的五条契约。

### 7.1 六个合法格子

- **LIFE-001** 内容只有六个合法状态组合，其余组合都是非法状态、可以直接写成断言。**格子集合是可扩展的**——新内容域可以增格子，但必须同时补一条非法组合断言。
  → 做完：一条断言能查出非法组合（如 archived 却没有墓碑），正常库返回空集。

  | # | 字段 | 文件 | 可见性 | 日常叫法 |
  |---:|---|---|---|---|
  | 1 | 完整 | 在 | 公开 | 正常 |
  | 2 | 完整 | 在 | 墓碑 | 归档（作者） |
  | 3 | 完整 | 在 | 墓碑 | 移除（管理员） |
  | 4 | 完整 | 在 | 仅作者 | 软删 |
  | 5 | 完整 | 排队 / 已删 | 仅作者 | 软删且文件已清（空壳） |
  | 6 | 清空 | 排队 / 已删 | 无人 | 擦除 |

  → 做完：全仓能 grep 到这四个非法断言的实现：字段清空但公开可见 / 文件已删但公开可读 / 已擦除但作者仍 200 / 行已删除但关联仍解析。
- **LIFE-002** 归档与移除在**数据上完全一样**（行在、字段在、文件在、对外 200 + 墓碑页），差别只有谁触发、能不能申诉。库里不为它们加列。
  → 做完：`lifecycle_state` 只有 `archived` / `removed` 两个墓碑值的区别，`moderation_state` 不参与。
- **LIFE-003** 「墓碑」不是一个动作，「清除（purge）」不是一个状态。它们是形容与事件，不要写成状态机节点。
  → 做完：状态枚举里没有 `tombstoned` 和 `purged`。
- **LIFE-004** 代码里不该出现 `DELETE FROM <内容表>`。「删除」在这里恒等于 `UPDATE`。
  → 做完：全仓 grep `DELETE FROM demos` / `DELETE FROM demo_revisions` / `DELETE FROM prompts` 零命中。

### 7.2 每个内容域必须实现的五条契约

- **LIFE-005** 契约一：内容表有 `deleted_at` + `erased_at` 两个时间戳列，**没有别的**删除标记列。
  → 做完：`demos` / `demo_revisions` / `proposals` / `prompt_library_entries` 都有这两列；没有 `is_deleted` 这类布尔列。
- **LIFE-006** 契约二：三个入口（软删 / 归档 / 擦除），不是每域三个端点。
  → 做完：三个入口共用一套前置判断，不是三份拷贝。
- **LIFE-007** 契约三：公开可见谓词必须**三处同时生效**（列表、详情、搜索/榜单），且谓词里必须同时含 `deleted_at` 与 `erased_at`。
  → 做完：谓词只有一处定义（`标准对象 §ST-2`），三处都引用它；漏 `erased_at` 会被门禁拦下。
- **LIFE-008** 契约四：**对外是 200 墓碑还是 404，判据只有一个——「这份内容曾经公开过吗」**。曾经公开过的（归档、移除、软删）一律 **HTTP 200 + 墓碑页**；从未公开过的（草稿、待审、驳回、擦除后）一律 **404**。
  → 做完：归档/移除/软删三种状态直访 slug 都得 200 + 墓碑页；草稿与待审直访得 404。
- **LIFE-009** 契约五：内容列不得 `NOT NULL`、不得 `DEFAULT ''`，否则擦除后无法与"刚插入的空行"区分。
  → 做完：擦除后 `demos.title IS NULL`，不是空字符串。

### 7.3 擦除

- **LIFE-010** 「擦除」在本站是**逻辑封存，不是物理销毁**：给行打上擦除状态、断开所有读取接口，使内容从此不可访问；**不在业务动作里真正抹掉内容**。状态只能由管理员改变，作者与用户不能自己解封。
  → 做完：擦除后 `erased_at` 非空、对外所有读接口一律 404；数据库里内容仍在、可被管理员审计查询；作者调「取消擦除」返回 403。
- **LIFE-011** 因为擦除只是标状态 + 断访问，它**不需要任务表、不需要分批、不需要事务边界**。任何声称「擦除要排队跑批」的实现都超出本需求。
  → 做完：`db/schema` 里没有 `erase_jobs` 这类表；擦除是一个同步的 `UPDATE`。
- **LIFE-012** 擦除后对外按 slug 直访返回 **404**（不是 200 墓碑）——对公众而言它从未存在过。但数据仍在，管理员可查、可恢复；「永久清除」不是业务动作，只可能出现在运维侧（且必须留审计）。
  → 做完：擦除一条后按 slug 直访 404；管理员后台仍能查到该行与内容；作者无法恢复。
- **LIFE-013** 审计行、`gc_queue` 行等**不许擦除**的内容要显式列出例外，并说明理由。
  → 做完：擦除时 `audit_log` 与 `gc_queue` 的行数不变。

### 7.4 注销

- **LIFE-014** 注销只改账号行字段（`status='deleted'` + 匿名化），**内容格子一格不动**——内容不会因此变成"仅作者"，也不失去文件。
  → 做完：注销后该用户的作品仍公开可见可体验。
- **LIFE-015** 账号行永不物理删除；删掉的只是内容列与个人可识别信息（邮箱留 HMAC 指纹）。
  → 做完：注销账号后 `accounts` 行仍在，邮箱列变成 HMAC 指纹。
- **LIFE-016** 注销后仍可申请擦除自己的内容（LIFE-010~012 同样适用）。
  → 做完：已注销账号仍能发起内容擦除并完成。

### 8.1 站点级运营参数

- **SET-001** 管理员能查看和修改两项站点参数：**全局自动上架**、**是否允许匿名作品直接上架**。**参数集合是可扩展的**——新增一项是往参数注册表加一行 + 白名单，不改接口形状。
  → 做完：`GET /api/admin/settings` 返回这两个键；`PUT` 只更新请求里出现的键；新增一项参数不改接口。
- **SET-002** 提交部分键时，未提交的键保持原值，刷新后看到的是合并结果。
  → 做完：先 PUT 改 A，再 PUT 只改 B，事后 A 仍是第一次的值。
- **SET-003** 每次修改落一条审计，记谁、改了什么、改前改后。

> - 空串与全空格等同「没传」；超过 100 个字返回 400 而不是静默截断（SCH 没写这条，

## 18. 对战域

**归属**：多人 AI 对局的房间、回合、观众投票、对局统计，以及外部 agent 接入本站的凭据与交互通道。
**不归属**：模型档案（模型域）、作品本体（Demo 域）、作品自带的联机能力（`demo_capabilities.realtime`，属沙箱域）、在线生成 demo（不在本域）。
**表**：待设计。归档草稿 `docs/1022-重整/建模.md` §三 给了 5 张表的思路（`arena_matches` / `contenders` / `rounds` / `votes` / `match_stats`），可复用设计思路，**不能照抄**——它假设的 `USER.role` 四值、内置 `public` 匿名账号、`COMMENT` 表、`TAG` 表全部已废。
**状态**：目标已定（用户 2026-10-31 裁决「对战是真目标」），设计里没有。

> **本域的核心立场：平台不调用任何模型，只当裁判。** 参赛方是用户自己在本地跑的 agent，平台只提供接入接口、对局编排、结果判定与展示。平台既不代管 API key，也不替用户付费，也不保证用户用的是什么 AI。

### 18.1 外部 agent 接入

- **ARN-001** 平台**不提供模型调用服务**（至少本域不提供）：平台没有模型端点、没有密钥代管、没有调用计费。平台只提供**接入接口**，参赛方是用户本地运行的 agent，由 agent 主动连上来参与对局。模型的选型与调用完全发生在用户侧。
  → 做完：平台代码里没有任何 LLM SDK 依赖，也没有指向模型厂商的密钥配置；一次完整对局在没有平台侧模型调用的情况下跑通。
- **ARN-002** agent 接入需要**凭据**：用户在站内为自己的一台 agent 生成凭据（可撤销、可看到上次使用时间），agent 凭此接入。**支持 API key 与 OAuth 两种接入方式，两种都要做**——具体用哪种由用户在创建凭据时选择。（本条只确定「两种都要有」这个需求，不规定实现细节。）
  → 做完：能创建与撤销凭据；用 key 接入与用 OAuth 接入各跑通一次完整对局；撤销后旧凭据立刻失效。
- **ARN-003** agent 与模型的对应关系是**一个 agent 绑一个用户的模型**：一个 agent 声明它使用哪个模型，该模型归属**用户的模型**（不要求平台收录、不要求是平台档案里的条目），因为无法保证用户用什么 AI 参战。同一个用户可以创建多个 agent，各绑不同模型。
  → 做完：创建 agent 时必须填模型标识；对局详情页显示「参赛方 X，使用模型 Y」；平台档案里没有这个模型也能参赛。
- **ARN-004** 平台与 agent 之间**两条交互通道都要支持**：**轮询**（agent 定期来问「轮到我了吗」）与**长连接**（agent 保持一条连接，由平台推送事件）。用户按自己的运行环境选，平台两条都得能用。
  → 做完：同一个 agent 分别用轮询和长连接各跑通一次完整对局；两条通道产生同样的对局结果。
- **ARN-005** 平台需要能识别 agent **掉线、超时、拒绝执行**，并让对局进入可解释的终局（判负或作废），不能卡在 `running` 上不结束。
  → 做完：把 agent 进程杀掉，对局在超时后被判负/作废并写进记录，不是永远 `running`。

### 18.2 对局

- **ARN-006** 一次对局有：两个或以上参赛方、一个模式（模型对模型 / 作品对作品 / 人对模型）、一个状态（`waiting` / `running` / `finished` / `aborted`）、一个结果。
  → 做完：状态机的四态与合法迁移写在一处；非法迁移被拒。
- **ARN-007** 参赛方在开赛时**快照**当时的模型标识、提示词与参数；模型之后改名或改档案不影响已结束对局。
  → 做完：改一个模型的名称，历史对局详情页仍显示旧名。
- **ARN-008** 房间的在线状态**不落库**；观众投票是落库的，同一观众对同一对局只计一票。
  → 做完：`votes` 在 `(match_id, voter_key)` 上有唯一约束。
- **ARN-009** 对局结束前 `winner_id` 为空；结束后不再改变。
  → 做完：`running` 状态的对局 `winner_id` 为 NULL；`finished` 后不可改。
- **ARN-010** 对局统计（场次 / 胜场 / 胜率）是**事件投影**，不是真相源，可从对局记录重建。
  → 做完：清空统计表后能从对局记录重建出相同数字。

### 18.3 边界

- **ARN-011** 不得往 `demos` 加 `battle_count` / `win_rate` / `opponent_id` 这类列；对局与作品的关系通过引用表达。
  → 做完：`demos` 表上没有这三列。
- **ARN-012** **在线生成 demo 不在本域范围内**。对局产生的东西如果要做成一件作品，走正常的作品发布流程，不直接插入 `demos`——但「在线生成」本身不属对战域要解决的问题。
  → 做完：对战域的读写路径里没有一条会写 `demos`。

## 附录 D：并列排序规则

|---|---|---|---|
| 平均分 | 平均分高 | 有效评分人数多 | 5 分票多 |
| 5 分票 | 5 分票多 | 平均分高 | —— |
| 1 分票 | 1 分票多 | 平均分低 | —— |
| 净票 | 5 分减 1 分多 | 有效评分人数多 | —— |
| 评分人数 | 有效评分人数多 | 平均分高 | —— |
| 综合热度 | 浏览数 + 2 × 下载数 + 有效评分人数 | —— | —— |
