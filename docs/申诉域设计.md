## 1. 一表一语义：为什么不塞进 proposals

治理域 D4 定的是「提案 · 作品审核 · 举报」动作契约统一，但**一表一语义**：提案是「建议新增/修改」，
申诉是「对一次已经发生的处置提出异议」。两者的状态机、可见性、谁能处理都不同。
把申诉塞进 `proposals` 会让 `kind` 矩阵多出一个只能由被处置人提交的分支，
而提案的「通过 = 写业务表」语义也不成立（申诉通过 = 恢复既有作品）。

所以新表 `demo_appeals`，与 proposals / 审核三线分开。

## 2. 状态机

`pending → approved`（恢复作品）/ `pending → rejected`（维持移除）。

- 同一作品**同时最多一条 pending**（部分唯一索引）；已驳回后可以再提，但界面不鼓励。
- 撤回（withdrawn）这一轮不做：作者没有入口，先不发明。
- 管理员裁决记 `reviewed_by / reviewed_at / decision_reason`；操作写审计（下一轮接线时补）。

## 3. 谁能做什么

| 动作 | 谁 | 条件 |
|---|---|---|
| 提交申诉 | 作品作者 | 当前 `lifecycle_state='removed'`；没有 pending 申诉 |
| 查看申诉状态 | 作品作者 | 任何状态；返回最近一条 |
| 裁决 | 持 `demo.review` 的人 | 下一轮 |
| 查看社区规范 | 所有人 | 静态页 |

非作者读申诉一律 404（不承认存在），与私有收藏夹同一口径。

## 4. removed 之后的恢复

申诉通过 → `lifecycle_state='removed' → 'published'`（Demo 域 §6.2 的唯一边）。
渠道行在移除时原样保留，恢复后继续可见；如果渠道被撤，需要管理员再发布——恢复不等于重新发布。
申诉驳回 → 保持 `removed`，墓碑继续显示「已移除」。

## 5. 写操作闸（409 appeal_pending）

未结申诉期间，作者对作品的写操作返回 **409 + `appeal_pending`**，响应里说明当前可做什么
（等待 / 撤回，撤回下一轮才有入口）。这一轮先接在「更新作品」这一条最常用的写路径上；
其余写路径（生命周期、渠道）在 removed 状态下本来就会被状态机拒绝，下一轮统一成同一错误码。

## 6. 端点

| 端点 | 鉴权 | 做什么 |
|---|---|---|
| `GET /api/v1/demos/{slug}/appeal` | 作者 | 最近一条申诉 + `canSubmit`；没有申诉也 200 |
| `POST /api/v1/demos/{slug}/appeal` | 作者 | 提交（reason 1–2000 字）；已有 pending / 非 removed 回 409 |

管理员列表与裁决（`GET /admin/appeals`、`POST /admin/appeals/{id}/review`）下一轮。

## 7. 时限

代码不硬编码申诉窗口：removed 存续期间都可以提交。运营处理时限（建议 7 个工作日）是 SLA，
不是业务约束；要落成硬窗口时需要 `removed_at` 与站点参数，先不做。

## 8. 不做

- 不做申诉对话 / 补充材料：一条 reason 足够，避免变成客服工单系统。
- 不做公开申诉：只有作者与审核者可见。
- 不做「申诉期间内容恢复可读」：生命周期设计 §6.6 明确申诉期间不给内容。
- 不做举报（论坛外置后作废）。
